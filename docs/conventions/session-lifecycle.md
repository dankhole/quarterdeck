# Session and Terminal Lifecycle

Read this document before changing task-agent startup, stop/resume/restart behavior, startup recovery, hook transitions, session reconciliation, PTY identity, terminal restore, agent adapters, or host-integration launch behavior.

## Ownership model

- Managed task lifecycle gestures enter the server-owned `ProjectTaskLifecycleService`. Do not recreate a browser resource coordinator or compose board persistence, stop/start, and worktree effects in React.
- The runtime composition root's `TaskResourceOperationCoordinator` serializes low-level task-resource effects across clients and UI remounts. Keep worktree-deletion guards against active or in-flight task sessions as defense in depth.
- `src/terminal/session-transition-controller.ts` owns process-side consequences of session state-machine events and active-listener summary fanout. Input, output, restart, recovery, and reconciliation code route raw `provider.hook`, `interaction.response_submitted`, `process.exit`, `interrupt.recovery`, and recovery-failure events through that controller rather than adding transition tables or side effects to `TerminalSessionManager`.
- The controller is the sole author of live native-work confirmation and its launch-scoped `nativeWorkEvidence`; callers cannot assert either. A raw provider event and its metadata are one session-store mutation through `applySessionEvent(...)`, which atomically applies state, review reason, outstanding interaction, work evidence, activity, resume identity, and timestamps. Do not restore compatibility methods with separate replay or error semantics.
- Claude launch permissions are provider-native modes, not Codex reviewer aliases. `inherit` leaves Claude's configuration and supplied arguments untouched; every explicit Quarterdeck mode removes conflicting `--permission-mode`, dangerous-skip, and dangerous-mode-enablement arguments before inserting exactly one launch-scoped `--permission-mode`. The frozen request carries that choice through automatic replacement and startup recovery, while Claude-managed policy remains authoritative.

Keep task-agent terminals and shell terminals separate even when they share xterm or panel plumbing:

- Task-agent terminals are task-scoped viewers for agent sessions and use the shared/pool path.
- Home and detail shell terminals are dedicated workspace-scoped manual shells with different lifecycle, restart, and exit rules.
- If an abstraction makes shell surfaces behave like task-agent terminals, split it instead of relying on comments or task-ID prefixes.

## Reconciliation

Before adding dynamic UI state tied to session lifecycle—status indicators, transient panels, or auto-triggered actions—check `src/terminal/session-reconciliation.ts` and give stale or orphaned instances a cleanup path. The periodic sweep currently owns dead processes, processless sessions, and stale hook metadata. It is a terminal safety net: routine provider input, completion, exit, and replacement sequences must converge through their normal controller events. A processless unresolved interaction becomes explicit `resolution_unknown`; reconciliation must never silently invent Running or clear a real wait.

Reconciliation must stop and surface a live task whose `sessionLaunchPath` disappears so it cannot remain `running` after its agent rejects an invalid cwd.

Terminal output and keyboard submission are not evidence that an agent is working. Claude Code and Codex emit spinners, status redraws, ANSI cursor movement, and Enter-confirmed local actions while idle or waiting. Do not use `lastOutputAt`, output presence, output volume, or submit intent as a work-state heuristic. Only a current launch-scoped native provider hook is authoritative evidence that work resumed. Fix missed state at the hook or ordering layer.

An explicit fresh Start seeds Running after successful PTY ownership handoff, without fabricating native work evidence. Its launch-scoped 45-second work-confirmation deadline moves a still-unconfirmed launch to Review/Unconfirmed while leaving the process available. Metadata-only SessionStart does not cancel this deadline; accepted work, completion, interaction, interruption, exit, or teardown ends the initial pending phase. An exit before confirmation becomes Error and cannot trigger automatic crash recovery. A launch that already produced native work and later returns to Review/Unconfirmed (for example after a Codex conversation switch) is not a launch failure: exit code 0 records Exit. Resumed and replacement native PTYs still seed Review/Unconfirmed (or preserve stronger durable Review/interaction meaning). The first current launch-scoped foreground-start hook (`UserPromptSubmit` for Codex/Claude or `AgentStart` for Pi) immediately establishes Running; a current `PreToolUse` remains the fallback when the start hook is missing. Pi's earlier `input` interception event cannot establish Running because an extension may consume it or preflight may reject it. A reliable state hook that reaches the runtime before the exact PTY completes process-ownership handoff remains unacknowledged so its durable outbox record retries after handoff; never commit its delivery order as an unconfirmed no-op. That admitted foreground execution stays Running through hook silence until a typed root completion, interaction, interruption, process exit, replacement, or recovery event ends or suspends it. `SessionStart` remains metadata-only because resume, compaction, and maintenance can emit it without starting foreground work. Cold hydration invalidates the previous runtime's evidence before startup recovery. After native work is confirmed, wall-clock silence, terminal output, and process liveness are health observations, never lifecycle transitions.

Bare Escape is forwarded to the provider without changing Running, suppressing restart, or fencing queued hooks; it may only record cancellation of an existing actionable input wait and arm an adapter's bounded rendered-interruption detector. Provider interruption evidence owns any resulting Interrupted transition. Ctrl-C synchronously applies Review/Interrupted before its bounded process-exit recovery bookkeeping begins. The later timer retires only pending process-exit recovery bookkeeping; the launch-scoped latest-interrupt timestamp survives timer cleanup and resumed work so delayed pre-interrupt hooks remain rejected. A current post-interrupt working hook may establish Running again, and a current completion hook may converge directly to ordinary Review.

A provider-specific rendered failure may conservatively remove Running only when the supported native hook surface has no equivalent event and the detector requires the complete actionable viewport state, not transcript chunks. Codex's complete "Conversation interrupted", "Selected model is at capacity. Please try a different model.", or "failed to load workspace requirements" results immediately above its newest input prompt are bounded examples. Blank rows and at most one adjacent provider-owned `Tip:` row may separate that result from the composer; newer transcript, work status, or multiple tip rows keep historical interruption text inert. That exact current-launch result may also retire the current foreground Codex permission when it is still `waiting` or `response_submitted`, including after exact-session startup recovery, because the provider has visibly ended the turn and returned to its composer. It cannot rewrite ordinary Review, another provider's interaction, or a background interaction. This compatibility evidence moves the task to interrupted Review; it can never assert Running, and a current launch-scoped provider hook is still required to return the task to Running.

Claude emits no hook for a user interrupt (its `Stop` does not run), so `claude-turn-interruption.ts` recognizes the rendered `⎿  Interrupted · What should Claude do instead?` result as the newest transcript row immediately above Claude's composer frame (a horizontal-rule or box top border followed by a `❯`/`>` input row) in the visible viewport. Only blank rows may separate them; composer content, wrapped narrow-width result text, and footer or status-line rows below the composer are accepted, while a working spinner, tip, newer transcript, quoted text, or partial result keeps the text inert. Inspection is armed only by a bare Escape written while the current launch is Running or holds the current foreground Claude permission wait (`waiting` or `response_submitted`; Escape rejects it without a hook). The arm lasts at most five seconds, fires once, and is cleared when provider evidence establishes Running, so ordinary Running output is not held for screen inspection and stale frames on later turns cannot end them. While any inspected chunk's broadcast is still queued behind the terminal mirror, later chunks are broadcast through the same queue, so listeners always receive output in arrival order even when the inspection predicate changes (this applies to Codex detectors too). Hook ordering records the foreground prompt active at that Escape; if a foreground `UserPromptSubmit` is accepted or a different prompt becomes active before the result renders (type-ahead), the detection is dropped. An applied result moves the task to Review/Interrupted, sets the launch-scoped latest-interrupt fence to the detection time, and closes the interrupted turn in hook ordering: its pending tool identities become completed, its prompt id (when Claude supplies one) is retired, and identity-free work, tool, permission, and elicitation hooks are refused until a new foreground prompt. Delayed hooks from the interrupted turn, including an interrupted `PostToolUseFailure` stamped after detection, therefore cannot revive Running with or without `prompt_id`. A prompt whose completed `Stop` reported unbounded background work stays wakeable: its id is not retired and only the timestamp and tool fences apply. A newer prompt's `UserPromptSubmit` may establish Running, and a current completion converges to ordinary Review.

## Stop, restore, and targeted resume

CLI shutdown suppresses copies of its initial signal for a fixed 750 ms in every launch environment. Executable paths and npm metadata cannot prove that a direct launch receives only one signal. Duplicates never extend this window or the cleanup deadline; a later interrupt or a different signal forces exit. Programmatic shutdown remains idempotent and tolerates any signal racing its initial request.

- Restore from Trash waits for the previous task session to finish exiting through `stopTaskSession(..., { waitForExit: true })` before resuming. A rapid untrash can otherwise call `TerminalSessionManager.startTaskSession()` while the old entry is active, short-circuit on it, and then lose the session when that old process exits.
- Request normalization preserves `waitForExit`. Stop results distinguish `exited` and `not_running` from `timed_out` and `failed`.
- Worktree cleanup, replacement start, and permanent card removal proceed only after a successful stop outcome.
- If an old PTY is still exiting when a start or resume arrives for the same task, fail explicitly and log it. Never silently reuse an old `running` or `awaiting_review` summary while `suppressAutoRestartOnExit` is set.
- Best-effort resume without a stored ID (`codex resume --last` or Claude `--continue`) is checkout-scoped and silent-failure prone. Adapters and the tRPC handler warn whenever they must use it.

Automatic crash and startup recovery require the exact stored provider session ID. A failed targeted resume becomes explicit Review/Error and never replays the original prompt in a fresh conversation. For Codex, Claude, and Pi alike, terminal reconnect never auto-restarts a resume that failed before opening an interactive session (a non-zero stored-id or best-effort failure, or a clean pre-interactive exit), and it never falls back to the launch request's resume id after the summary cleared it. The next explicit start drops a stored id that a non-zero resume already failed and warns that it used the provider's best-effort path; a clean pre-interactive exit keeps its id for that restart. Explicit stops suppress restart before signalling the PTY. Outside coordinator-owned recovery, a final non-zero targeted resume may clear the unusable stored ID so a later explicit user Restart can choose the documented best-effort provider path; the automatic path itself never does.

Claude resume prefers the stored hook `session_id` through `claude --resume <id>`, matching Codex's targeted model. Server-start resume may use `card.workingDirectory` while that worktree still exists. Without a stored Claude ID, untrash/restart falls back to cwd-scoped `--continue` and must warn.

Soft Trash stops the task and detail shell while preserving the complete registered worktree, its exact `workingDirectory`, and the provider resume identity. Permanent deletion owns workspace and legacy-patch cleanup. It renames the stopped, registration-checked workspace into `..pending-delete` under the worktrees home, unregisters only that worktree, and removes the card; the files are deleted afterwards by one background deleter, so locks are never held while a dependency tree is deleted. Shutdown abandons an unfinished delete, and the next start resumes it. A best-effort patch is not a lossless archive: it omits ignored files and index state, can lose clean detached commits, and cannot fence a background daemon writing after capture. Do not reintroduce worktree removal in Trash or its replay/compatibility path without a recoverable archive contract that covers these cases.

Trash releases an isolated worktree's checked-out branch by detaching HEAD at its current commit without changing files, the index, or the branch tip. Save the actual branch and commit durably before detaching; `card.branch` is not proof of the checkout's current branch. An already detached task has no branch to release or automatically restore. Preserve exact registration and managed-path checks, wait for successful task and detail-shell stop, and serialize branch effects with the existing task-resource and worktree locks.

Explicit Restore may reattach only the branch recorded by Trash, while the worktree and branch still point to the saved commit and no other worktree owns that branch. Never reset a moved branch, create a missing branch, switch commits beneath the saved index, or steal another checkout's branch. If reattachment is unavailable, restore the preserved detached workspace with a warning. Automatic startup recovery and ordinary Start must not infer or restore an attachment from task metadata. In-progress Git operations must retain their state rather than have Trash or Restore rewrite HEAD beneath them.

Older versions removed trashed worktrees and cleared `workingDirectory`. Explicit lifecycle restore may move an unregistered, `.git`-less leftover directory from its managed task root to `recovered-task-files` before rebuilding that legacy checkout, only with a surviving task branch or saved patch as recovery evidence. Never overwrite or discard those leftovers; report their preserved location. Retained worktrees and directories with a `.git` entry still require exact registration. A saved patch restores at its original commit; an advanced branch remains untouched. Missing recovery evidence, unavailable saved commits, and patch-restore failures block launch and subsequent reuse rather than silently starting from the base branch.

## Task worktree registration

Branch switching in the shared checkout protects ongoing work, not every retained Review card or idle PTY. Use server-owned task indicators and pending launch/recovery state to keep Running, approval waits, and uncertain starts protected. Completed or interrupted Review tasks may retain an attached agent without blocking checkout. Apply the same check when a task-scoped checkout resolves to the project root; isolated worktrees do not reserve the shared checkout. Other destructive Git operations retain their own guards.

A task folder's existence and a successful `git rev-parse HEAD` do not establish worktree ownership. If Git removes and later reuses an administrative directory, a stale `.git` pointer can silently read another task's HEAD and index. `assertTaskWorktreeRegistration(...)` checks that the administrative `gitdir` backlink resolves to the requesting folder's `.git` file before isolated workspace reuse, Git-path resolution, persisted-path launch, patch capture, or removal. Shared project checkouts are exempt from the linked-worktree check.

Worktree registration changes and submodule initialization share the repository setup lock. Creation-time copying and scripts use a stable per-worktree operation lock in the Git common directory; purge takes that same lock before the repository lock. This prevents removal under a running setup without holding the repository lock for a dependency install. Lock targets must be distinct, not just different lockfile names on one target: proper-lockfile tracks ownership by target path. Missing or mismatched registration fails explicitly and preserves existing task files; never delete and recreate a broken existing folder as automatic recovery. Repair requires independent evidence of the correct registration and preserved task work. The explicit legacy Trash recovery described above preserves the old directory separately and does not weaken registration checks.

Creation marks setup pending in the worktree's Git administrative directory before making the workspace available. Legacy patch restoration first records durable intent in the Git common directory, before creating the checkout, and initializes setup before clearing that intent. Failed or interrupted patch restoration cannot bypass recovery by reusing the newly registered checkout. The setup owner initializes submodules, copies `.worktreeinclude` selections, runs the project-configured script, then records success. Failed/interrupted setup retains files and blocks all launch paths, including persisted working directories. Explicit lifecycle Start/Restart may retry; automatic recovery and replay may not. Successful and legacy unmarked worktrees never rerun creation-time scripts. Setup progress is a lifecycle-operation phase, not a new agent session state. See [worktree setup](../worktree-setup.md) for configuration and user-facing behavior.

A failed `git worktree add` can leave a registered checkout, for example after a failing post-checkout hook. Preserve that directory and record `checkout_failed` with the setup owner. Neither explicit setup retry nor pending patch restoration may treat it as a successful or legacy checkout; checkout repair is required before reuse.

## Startup recovery

`src/server/startup-session-recovery.ts` coordinates automatic startup recovery.

### Bootstrap and discovery

- Validate and hydrate every available indexed project before accepting clients, then queue eligible recovery in the background through the shared global coordinator.
- Startup discovery is read-only. Skip an unavailable path without deleting its index entry or saved board/session state. Browser connections also preserve unavailable projects; only explicit project removal authorizes deletion. See [project management](../project-management.md) for location changes and recovery.
- WebSocket connection, active-project selection, and GUI mount never trigger or gate recovery. Inactive project pills and notification snapshots need the same hydrated truth as the selected project.
- Acquire the lifetime state-home owner before startup writes or process launches. Inspect prior saved session, execution, transaction, and managed-process evidence before cleanup can prune it. Unreadable evidence or a live process whose ownership cannot be established denies startup and preserves the files for diagnosis; never replace that check with an executable-name scan or an unverified kill.
- Prepare each task once through the shared task-start service after recovery admission. During shutdown, fence new intent and drain admitted producers, including availability probes. Then permanently fence new process launches and capture the exact owned process forest before any PTY, structured provider, or language server receives a stop signal. Final persistence must use indexed state without spawning Git after this boundary. Drain started writes and owner-stop attempts before reporting that ownership can be released; a bounded timeout leaves the completion work running and never authorizes release.
- Each covered process launch validates the current lease and durably marks its custody generation before spawning. An unclean dirty generation cannot automatically recover merely because its root PID disappeared. Explicit recovery may record the user's confirmation that remaining agents and detached commands were stopped, after exclusive maintenance admission and successful saved-process inspection. This acknowledgement is scoped to its exact history boundary and boot; it is not a clean release or proof of descendant cleanup. New dirty generations, live saved processes, and unreadable evidence remain blocked. See [desktop ownership and custody](../desktop.md#shutdown-and-recovery).
- On Windows, a task PTY is not handed to the runtime until ConPTY exposes a valid root PID and its protected launch record durably captures the exact runtime/root PID and CIM creation identities after proving the root remains the runtime's direct child. Registration failure, parent mismatch, or bounded PID-readiness failure stops the PTY and fails the launch. Natural exit retires the record; startup skips records owned by an exact live runtime, prunes missing or PID-reused roots, and rechecks an abandoned root's creation identity immediately before tree termination. Shutdown may verify and reclaim the current runtime's registered roots concurrently, but never reintroduce executable-name or command-line cleanup heuristics.
- Serialize and space only actual launch operations globally. Let unrelated tasks wait for readiness concurrently so one hookless TUI cannot block the queue.

### Retry and identity

- Freeze the resolved agent, command, cwd, settings, and resume target. Reuse that exact preparation for one bounded retry after positive failures only.
- A launch-scoped native hook from the current `sessionInstanceId`, plus the expected stored session ID when one exists, confirms identity.
- A live process at the hook deadline is unconfirmed, not failed. Leave it available to the user rather than stopping or replaying it.
- Retry spawn failures, early exits, and identity mismatches. Stop and wait for the exact failed PTY before replacement, never start a third copy, and do not retry deterministic preparation failures.
- Explicit start, stop, or input cancels recovery ownership. Exhausted failures route through the terminal transition owner. Keep hook-receipt accounting separate from launch-hook admission.
- Failures in `resumeInterruptedSessions(...)` are warnings, not debug-only breadcrumbs. Logs distinguish failure to select an interrupted task from failure to start the selected task.

### Persisted meaning

Process recovery eligibility is separate from user-visible task meaning:

- A durable modern interrupted handoff represents previously Running work, but process replacement alone leaves it Interrupted. Only a current launch-scoped native working hook may return it to Running; a current completion hook may take it directly to ordinary Review.
- Valid Review, Needs Input, and Error semantics survive hydration and shutdown while stale PID ownership is cleared.
- Persisted native work evidence never survives runtime ownership replacement. Previously Running work hydrates as Review/Interrupted with a durable recovery handoff until the replacement emits current provider evidence.
- Ineligible recovery policy results carry no launch semantic state. Only ambiguous legacy interrupted persistence remains neutral.
- Restoring a completed `hook` review never fabricates `attention`; only a structured question or permission signal creates Needs Input.
- A legacy `attention` record without that proof remains ineligible even with `startupRecoveryRequired: true`, and hydration clears the stale handoff so it is not persisted again.

## PTY and terminal restore identity

Task PTY exit callbacks bind to the exact spawned `PtySession`, not only the task ID. A delayed exit from an old wrapper or PTY must not finalize and clear a replacement session for the same task.

Terminal restore has several distinct races:

- If a new task session instance (`startedAt` / `pid`) appears before the first control-socket restore finishes, `web-ui/src/terminal/slot-socket-manager.ts` queues the follow-up `request_restore` and replays it from `markRestoreCompleted()`.
- The React-side `sessionStartedAt` reset in `usePersistentTerminalSession` can happen after the control socket already restored the replacement PTY. A pooled task reset immediately requests authoritative restore so the late xterm reset cannot leave a blank pane.
- Once the IO socket is open, a stalled control restore must not keep the loading overlay forever. `terminal-session-handle.ts` uses a readiness fallback for new and reused slots and for delayed IO-open events.
- Do not pair that fallback with speculative restore. A stale or empty snapshot can erase live output already written to xterm.
- When a live session instance changes (`startedAt` with non-null `pid`), drop and reopen pooled terminal sockets rather than queueing restore on an existing control socket; reused active slots can otherwise remain stuck at `restoreCompleted=false`. Do not reconnect for processless stop summaries (`pid: null`).
- When acquiring a pooled viewer or requesting Re-sync, replace both sockets if either is missing, closing, or closed. IO loss invalidates restore readiness even if control remains open; retaining that control socket can queue restore forever. Preserve a healthy connecting pair, and ignore callbacks from replaced sockets.
- Before treating a restore snapshot as empty, `TerminalViewport` drains queued writes; live output can be queued but not yet visible.
- A forced same-size redraw is platform-owned. POSIX may send `SIGWINCH`; Windows must issue one bounded adjacent-row ConPTY resize and immediately restore the requested geometry. Do not signal ConPTY with Unix redraw semantics or leave the nudged size authoritative.

Terminal restore readiness is not browser presentation readiness. Do not clear loading or notify connection-ready subscribers until `TerminalViewport` drains queued writes, resizes, scrolls to bottom across layout frames, and reveals the host. The IO-open fallback uses the same settled reveal path. Claude sessions are especially sensitive to redraw and status output around restore.

Input readiness can precede agent content: a newly spawned provider may restore an empty viewport before drawing its interface. The terminal handle publishes a separate, replayable content-pending presentation state for live task agents. Keep the startup indicator until applied output or restore contains rendered text; process exit, processless summaries, and connection errors end that wait. This presentation signal never establishes provider work or changes durable task state.

A saved Review status describes task meaning, not chat process availability. When the authoritative summary has no PID, task detail keeps the terminal viewer mounted to preserve output and shows an explicit Resume chat action through the existing managed lifecycle path, or progress while a lifecycle operation is pending. The durable startup-recovery flag alone does not prove an operation is active or disable manual resume. Opening a viewer and restoring an empty snapshot must not imply a successful provider resume or trigger a new launch.

Terminal snapshots must preserve mouse encoding together with mouse tracking. xterm's serialize addon restores tracking but omits SGR/SGR-pixel encoding; `TerminalStateMirror` observes DECSET/DECRST and full reset through public parser handlers and appends the encoding to snapshots. Otherwise a restored browser emits legacy mouse bytes that a provider can interpret as composer text. Keep these observers non-consuming so xterm still applies each sequence.

## Hook and input semantics

### Shared rules

- Agent session-identity hooks are metadata-only. Persist `resumeSessionId` from Codex `session_meta` and Claude `SessionStart` without clobbering `latestHookActivity` or changing state twice.
- Raw native hooks enter through `hooks.ingest` (or, for best-effort Claude hooks, the loopback endpoint that calls the same ingest), provider-specific delivery ordering, `TerminalSessionManager.applyProviderHook(...)`, the transition controller, and the pure reducer. Deduplicate delivery IDs; fence session instances; retain Codex turn/tool ordering and Claude prompt/tool ordering separately; and fail closed on missing or ambiguous correlation. Reliable ingest acknowledges only after the semantic mutation plus its bounded content-free ordering receipt are durable. Hydration rebuilds the provider-specific ordering guard from those receipts before replaying the outbox; it must not replace an unreadable session store with empty state. Startup replay adopts every outbox record except those of a project with a pending relocation journal, which stay pending. The live runtime's periodic replay adopts a record immediately once its `hooks ingest` writer marks it abandoned, and otherwise only after it is older, measured from enqueue, than the writer's total delivery budget plus a margin. That makes a minimal replay copy pre-empting the CLI's own full-metadata delivery unlikely, not impossible: a writer stalled past that bound still races replay, and whichever copy arrives second is a duplicate. A duplicate or rejected delivery is acknowledged once already-dirty state is durable without forcing another write.
- Provider-neutral high-level input carries explicit submit intent into `TerminalSessionManager.writeInput(...)` for byte handling and ordering. When a durable interaction is genuinely `waiting`, a successfully written submit, Ctrl-C, or bare Escape changes only the nested status to `response_submitted`; the top-level task remains Review and stops advertising Needs Input. `UserPromptSubmit`, an exactly matched `PostToolUse`/`PostToolUseFailure`/`ElicitationResult`, or a later identity-bearing `PreToolUse` establishes resumed work. A current root `Stop` establishes Review even when the retired wait lacks exact interaction identity. A demonstrably newer foreground turn/prompt may supersede an obsolete wait, but same-turn parallel activity, a different tool's delayed completion, generic activity, notifications, and background-agent hooks are not proof of resumed work.
- Interrupt recovery and an explicit PTY stop can both surface as `awaiting_review/interrupted`, but they are not the same process state. A pending bare Ctrl-C/Escape recovery signal owns an immediate PTY exit even when the process reports code 0; persist Interrupted and suppress auto-restart instead of inferring completion from the exit code. Only an accepted current provider hook carrying that exact PTY's `sessionInstanceId` and a delivery time after the latest interrupt, while `PtySession.wasInterrupted()` is false, may advance or complete the review. Either accepted semantic proof cancels the interrupt timer and clears its one-shot auto-restart suppression, including activity-style `PreToolUse`; permission and notification no-ops cannot do so. Rejected completions cannot publish summary metadata through ingest. Once an explicit stop marks the PTY interrupted, reject further input and provider evidence until a replacement session starts.

### Native terminal input authorization

Terminal IO uses `createNativeTerminalInputWriter`, scoped to one WebSocket and one exact native PTY. Bind the PTY and reserve task-coordinator order before any asynchronous project, path, relocation, or ownership check; otherwise filesystem completion order can reorder keystrokes. Shutdown rejects new input synchronously, while already admitted input remains part of the coordinator's drain. The first ownership check reads the durable journal; subsequent input checks the journal's file identity asynchronously and reuses the store's subscribed observation while that identity is unchanged, without taking the project disk lock or parsing the journal again. `ProjectExecutionOwnershipStore` publishes verified reads and successful commits, invalidates changed ownership before a write, and leaves failed verification unknown. Unrelated task and interaction writes do not revoke a verified observation. After every await, the writer rechecks the exact PTY and current observation, then checks structured ownership and writes synchronously under the task resource coordinator. Disconnect disposes the subscription and prevents queued writes. An attachment made before launch may bind on its first input to an already-existing PTY; bytes received before that PTY exists are discarded, and a bound connection never follows a replacement PTY.

This observation is an input optimization, not lifecycle authority. Start, handoff, and recovery retain durable checks. Runtime admission permits only one writable owner per state home, but local publication alone cannot prove journal freshness: each input compares device/inode/size and nanosecond modification/change timestamps with the token captured under the durable journal lock. External replacement or metadata-check failure invalidates the observation; external changes require durable reverification before writing. Subscription versions prevent a stale asynchronous metadata result from overriding a newer local publication. Backup restore requires exclusive maintenance admission with no live runtime owner.

### Browser terminal input ownership

`terminal-key-policy.ts` resolves Quarterdeck's exact shortcut overrides without browser effects. `TerminalBrowserInput` owns key cancellation, local selection copying, OSC 52 clipboard access, image-paste capture, and user-visible clipboard failures. `TerminalViewport` composes that owner; xterm retains ordinary key encoding, composition, text paste, and bracketed-paste mode handling. Skip already-consumed and composing events, preserve unrelated modifier combinations, and emit shortcut bytes only on keydown. Do not grow individual viewport exceptions into a partial implementation of general Kitty keyboard negotiation.

On macOS, Command+Left/Right/Backspace sends the conventional Ctrl+A/E/U editing bytes. Exact Shift+Enter sends a newline. Copy prefers an xterm selection; the narrowly scoped Codex forwarding below handles provider-owned selections. Ctrl+C stays with xterm and the provider's interrupt behavior.

`TerminalWheelInput`, composed by `TerminalBrowserInput`, normalizes unmodified vertical wheel distance only for fullscreen Codex with wheel-capable mouse tracking. xterm 6's mouse path discards the magnitude returned by its wheel accumulator and sends one report per DOM event; its pixel heuristic also changes at 50 pixels. `terminal-wheel-policy.ts` instead converts CSS pixels, lines, and pages using the measured row height and Codex's [three-row report contract](https://raw.githubusercontent.com/openai/codex/rust-v0.157.0/codex-rs/tui/src/transcript_view/input.rs). It retains fractional distance across pauses so slow wheel ticks and small trackpad movements accumulate, tolerates browser float32 rounding, and resets fractions on direction, task, or buffer changes. The adapter synchronously dispatches discrete line-mode wheel events through xterm's public DOM path, preserving its ownership of mouse coordinates and protocol encoding. It adds no smoothing timer or deferred input queue; an exceptional event is capped at 100 reports. Other providers, normal scrollback, modified gestures, and horizontal-dominant gestures retain xterm behavior. Revalidate the three-row assumption when changing supported Codex behavior; do not copy private xterm mouse encoders or claim pixel-smooth provider scrolling.

`terminal-links.ts`, composed by `TerminalBrowserInput`, owns recognized web-link clicks in fullscreen Codex before xterm forwards their mouse-down. Codex also opens transcript links, but does not handle ordinary footer-link clicks, so blanket browser suppression is incorrect. Capture a hovered link's URI/range and task identity on mouse-down; open a stationary matching release once in the browser. Preserve drags by replaying the withheld mouse-down through xterm's public DOM path before the first drag move, then suppress browser activation for that delegated gesture. Preserve xterm-forced selection (Option on macOS when enabled, Shift elsewhere), non-link input, other providers, and OSC hyperlink confirmation. Redraws can replace hover objects without changing the link; compare URI/range, and cancel pending gestures on task replacement, lost buttons, blur, or disposal.


Image paste captures files and the exact task/project/session writer synchronously before asynchronous reads. The existing task-session input endpoint accepts a separate bounded image request (PNG, JPEG, GIF, or WebP; at most 10 images totaling 20 MB) with a required `sessionInstanceId` and write-only intent. Under the task resource coordinator, the runtime checks native ownership and exact PTY identity, writes private generated files, then rechecks ownership and identity before synchronously delivering one bracketed path paste per image. Never add submit bytes, infer Running, redirect to a replacement session, or send image paths into a shell. Failed deliveries remove their files; successful attachments remain in OS temporary storage, like initial task images, so providers can read them later. Browser failures use content-free messages. The transport does not promise every provider will render an inline image attachment.

### Claude hooks

- Preserve the tested Claude Code 2.1.198 minimum-version compatibility gate for the installed native hook schema. Do not use global Agent View notifications as evidence for a Quarterdeck task session.
- Best-effort Claude hooks—every non-reliable `activity` hook (`Notification`, `SubagentStart`, `PreCompact`, `PostCompact`)—use Claude [`type: "http"` hooks](https://code.claude.com/docs/en/hooks) once the runtime publishes its loopback endpoint after listening, using the listener’s bound literal address (IPv6 bracketed) rather than the configured host name; otherwise, including interface binds, they remain `hooks notify` commands. Reliable hooks, including `SessionStart` (command-only in Claude) and `SubagentStop` (the only evidence that retires a finished or killed subagent's Needs Input wait), always stay `hooks ingest` commands with the durable outbox. HTTP hooks date from Claude Code 2.1.63, so the existing launch gate needs no separate version check. `/api/hooks/notify` admits only a loopback POST without `Origin`, JSON up to 1 MiB, and `event`/`source` query parameters; `event` must be `activity`, because state transitions require the outbox. HTTP hooks use a 1s timeout (command `notify` keeps 5s), and the launch env appends `127.0.0.1,localhost,::1` to the union of inherited `NO_PROXY`/`no_proxy` so a proxy cannot intercept the loopback POST. Identity and an HMAC credential for that exact project/task/session instance, keyed by a per-runtime-process secret, arrive only through headers Claude interpolates from `allowedEnvVars`; never accept a credential in the URL. The endpoint shares `buildHookIngestRequest` with the CLI, validates the `hooks.ingest` schema, answers an empty 204 immediately, and calls the same guarded ingest without waiting, shedding load with 503 above 64 in-flight ingests. Like `hooks notify`, it has no retry or outbox.
- Claude watches settings files, so command and HTTP variants use separate state-home files (`hooks/claude/settings.json` and `settings-http.json`); runtime admission keeps each single-writer. The HTTP file embeds the current port and is rewritten by later launches. A session that outlives its runtime therefore loses best-effort events after a restart or port change (another runtime rejects its credential), and an `allowedHttpHookUrls` or `httpHookAllowedEnvVars` list from any settings source that omits the endpoint or its variables drops them too (`allowManagedHooksOnly` or `disableAllHooks` block every Quarterdeck hook); reliable transitions are unaffected. Those lists merge across all settings files, but Quarterdeck does not add entries: defining either key where no other source does would newly restrict every other HTTP hook in the session. Users or administrators who set them must add the loopback endpoint (`http://127.0.0.1:*/api/hooks/notify*` or the `[::1]` form) and the four `QUARTERDECK_HOOK_*` variables. This provider-to-runtime route does not change the browser protocol version, and the desktop proxy excludes it with the other hook routes.
- `Stop.last_assistant_message` supplies `finalMessage` and the compatibility input `conversationSummaryText`. Accepted foreground completions retain that response in `completedResponses`; no AI summary is generated. Do not parse the lag-prone `transcript_path` file for this response.
- A main-agent `Stop` is incomplete while `session_crons` is non-empty or `background_tasks` contains work expected to wake the turn (subagents, workflows, untyped or unknown entries). Unbounded `shell` and `monitor` tasks such as dev servers do not hold a finished turn in Running: that `Stop` enters Review with completion metadata but carries `unboundedBackgroundWorkPending`, so the ordering guard does not retire its prompt and a same-prompt wake's tool or `Stop` hooks remain admissible (a text-only reply to the wake remains in Review). While incomplete, keep it activity-only, preserve stronger input or permission waits, suppress completion metadata, and wait for a later completed `Stop`.
- `SubagentStop` remains activity-only even when it includes `last_assistant_message`.
- A Claude hook carrying `agent_id` belongs to a subagent. It cannot change foreground task state, the foreground `outstandingInteraction`, native work evidence, or foreground interrupt recovery, replace `latestHookActivity`, or supply the task's completed response.
- Claude renders a subagent's `PermissionRequest`, `Elicitation`, or `AskUserQuestion`/`ExitPlanMode` prompt in the main TUI and blocks on the person while the foreground turn and other subagents keep working. A current launch-scoped request therefore opens a wait keyed by that `agent_id` in the optional `subagentInteractions` list, but only while the foreground turn is Running or blocked on its own interaction in a live process. The shared classifier shows a waiting subagent prompt as Needs Input, with the same approval, notification, and sound semantics as a foreground wait, unless an unanswered foreground interaction takes precedence. Top-level `state` stays the foreground lifecycle, so main-agent hooks keep proving work and the task shows Running again once no subagent prompt is waiting.
- One subagent can queue several prompts from parallel tools; each request is its own wait unless tool or elicitation identity proves it is the same request, and a new request supersedes only that agent's prompts answered before it. A request that cannot be bound to exactly one open same-agent `PreToolUse` keeps every compatible open candidate and resolves only when all of them have completed; when fewer candidates remain open than prompts sharing them, the surplus (answered first) resolves. Only the same `agent_id` clears a wait: the correlated `PostToolUse`, `PostToolUseFailure`, or `PermissionDenied` (with no tool identity at all, the first later completion with a compatible tool name), a later tool's `PreToolUse` that was not a candidate, a matching `ElicitationResult`, or `SubagentStop`. Hooks from other subagents or the main agent never clear it. Claude queues prompts of one kind oldest first, so a direct answer (Enter, a numbered choice on a subagent permission, Escape, or Ctrl-C) marks the oldest unanswered wait of the foreground dialog's kind, foreground or subagent, `response_submitted`; when both a foreground and a subagent prompt wait, the answer fences delayed requests in both domains; an answered subagent prompt stops advertising Needs Input. Manual denial emits no hook, so the subagent's later hooks or `SubagentStop` retire it. Completion, interruption (including Claude's rendered Escape result), stop, exit, replacement, and cold hydration retire every subagent wait with the foreground turn; persisted waits never carry into a replacement process.
- Subagent hooks share only the root-completion fence. Prompt-retirement and interrupted-prompt fences do not apply: a subagent can keep working, and keep its wait, after a new foreground prompt retires the prompt that launched it, and the reducer decides from the foreground lifecycle whether a wait may open. Claude does not document which `prompt_id` a background agent's hooks carry, so subagent ordering must not depend on it. Answered and resolved waits are evicted before waiting ones at the 32-entry cap. Tool correlation, answer boundaries, and stop fences are kept per `agent_id` in launch-scoped memory and never enter the foreground ordering domain or durable ordering receipts, so a subagent cannot borrow foreground tool identity or fence another prompt queued behind its own.
- Reliable `PreToolUse` supplies tool identity for `PermissionRequest`, `AskUserQuestion`, and `ExitPlanMode`; a delayed predecessor may enrich the same wait but cannot claim resumed work. `AskUserQuestion`, `ExitPlanMode`, and MCP `Elicitation` create typed Needs Input waits. Claude `Notification` hooks—including `permission_prompt`, elicitation UI notifications, and legacy background-agent notification types—are presentation-only: they carry human-facing notification text, may duplicate native lifecycle events, and do not provide the exact actionable interaction identity needed to author foreground state. Matching native resolution, later post-response work, a demonstrably newer foreground prompt, or a current completed root `Stop` clears a durable wait; same-prompt parallel events do not.
- Claude `PermissionDenied` is an automatic permission-mode event with `tool_use_id`; correlate it by that exact ID and mark the response pending. Manual denial emits no equivalent hook, so local submit remains pending until later work or Stop evidence. Never simulate a provider hook the real provider does not emit.
- Bound native message/activity text before storage or broadcast. `PostCompact.compact_summary` describes compaction and never populates completed-turn summaries.

Managed Claude tasks retain automatic startup folder-trust confirmation with the same guards as Codex. The dialog is read from the rendered viewport: both trust options must be contiguous rows of one select (a wrapped label may continue onto following rows), and duplicated or ambiguous option text is never selected. Keys require the current launch, Claude's input guard, and the newest rendered frame; any new output cancels a pending key before the mirror applies it. Direct keyboard input or a mouse click while the dialog is visible owns it until it disappears; input before the dialog renders, terminal protocol replies (focus, cursor, device-attribute, keyboard-flag, OSC, and DCS replies), and passive wheel or motion mouse reports do not. The observer stops after an interrupted stop and retires once native work is confirmed. Confirming trust never establishes Running.

Claude launches always use fullscreen, overriding classic renderer environment preferences. Screen-reader launches that require classic rendering fail before PTY creation. Scrolling is application-owned rather than xterm scrollback; `CLAUDE_CODE_SCROLL_SPEED` defaults to `3` while preserving an explicit user override. Do not apply that default to Codex, Pi, or shell terminals. Terminal geometry always uses real viewport rows; attaching or detaching a viewer must not resize the PTY.

### Codex hooks and launch arguments

- Fullscreen Codex owns mouse selections separately from xterm's selection. `TerminalBrowserInput` copies an xterm selection first; otherwise it forwards macOS Command+C as Kitty Super+C (`CSI 99;9u`) or other platforms' Ctrl+Shift+C as `CSI 99;6u`, only for a Codex session with an active alternate screen and mouse tracking. Codex's [selection handler](https://raw.githubusercontent.com/openai/codex/rust-v0.157.0/codex-rs/tui/src/text_selection.rs) accepts these encodings. Never substitute Ctrl+C: without a provider selection it can interrupt work, and Quarterdeck treats it as lifecycle input. Browser-owned clipboard operations use the host-integration boundary. Codex's [clipboard backend](https://raw.githubusercontent.com/openai/codex/rust-v0.157.0/codex-rs/tui/src/clipboard_copy.rs) may instead write directly to the runtime host's native clipboard; browser error reporting cannot observe that path. Do not fabricate SSH/tmux environment markers to force OSC 52 or promise remote-browser clipboard delivery for native provider writes.

- Codex requires 0.157.0 or newer. Native task launches pass `--no-daemon` before `resume` or `fork` so the managed PTY does not attach to Codex's shared background server. Keep this flag out of shared app-server preparation.

- Native Codex task launches enforce `tui.fullscreen_transcript=true`, `tui.alternate_screen="always"`, and `tui.raw_output_mode=false`, replacing conflicting overrides and removing `--no-alt-screen`. Keep these renderer arguments in the native adapter, before `resume` or `fork`; shared app-server preparation does not own TUI rendering. These are launch-scoped settings, not edits to user configuration.

- Managed Codex tasks retain automatic startup folder-trust confirmation. The modern dialog is recognized from the current terminal viewport, including its full disclosure, supported path layout, selected trust option, and footer. Confirmation requires the same active launch and unchanged output; new output or direct user input cancels a pending confirmation. Retire this observer after native work is confirmed. Preserve the legacy recognizer and its exact-launch timer fence. Folder trust is separate from tool approval, and confirming it never establishes Running.

- Codex `/btw` runs in a distinct ephemeral provider thread. Keep native `session_id` scope separate from turn ordering: hooks from that side thread cannot author the main task's state, interaction, completion summary, or `resumeSessionId`. Explicit Codex subagent hooks (below) are also non-foreground. A newer native `SessionStart` with source `startup`, `resume`, or `clear` permits foreground-session navigation even when its transcript path is null; Codex can emit the hook before creating the transcript. A transcript path remains fallback evidence for persistent navigation. A pathless `fork` or `compact` start cannot replace the main identity. Preserve the native start source and content-free transcript-presence metadata through outbox replay and durable ordering receipts, never the transcript path. The provider's [SessionStart contract](https://learn.chatgpt.com/docs/hooks#sessionstart) distinguishes the start source from the hook provider. Do not revive retired main turns merely because a different provider thread emitted a hook.

- Subscribe to Codex `SessionStart` sources `startup|resume|clear`. New-conversation navigation emits `clear`; omitting it leaves the old foreground session ID authoritative and rejects every later working hook. Persistent-session navigation retires the previous session's outstanding interaction and work evidence into Review/Unconfirmed while updating resume identity and ordering ownership together. SessionStart alone never proves new work; subsequent native work establishes Running. Navigation also retires the previous session's subagent waits and per-agent ordering. Keep ephemeral side-thread and explicit subagent fences intact. Codex 0.159 queues SessionStart until a user turn runs, including after exact resume; an idle restored TUI is not expected to emit it immediately. Compatibility checks must retain exact provider/launch identity and then require fresh native hooks after a guarded new turn, never infer work from input or a restored transcript. See the tagged [upstream resume tests](https://github.com/openai/codex/blob/rust-v0.159.0/codex-rs/core/tests/suite/hooks.rs).

- Quarterdeck-managed Codex hooks stay launch-scoped. Never write them to repo-local or user-global hook files.
- Pass hook config inline on the `codex` command line (`-c hooks...` plus `--enable hooks`). Generate matching `hooks.state` trust entries from the same config using `/<session-flags>/config.toml:<event_snake>:<groupIndex>:<handlerIndex>` source keys (`C:\<session-flags>\config.toml` on Windows). Never use `--dangerously-bypass-hook-trust`.
- Preserve the Codex 0.157.0 minimum-version and native-hooks feature gate. Only genuine user-input or approval waits surface as Needs Input.
- Codex permission approval can resume through `PostToolUse` without a separate resolved hook. Because native `PermissionRequest` may omit `tool_use_id`, bind it to exactly one preceding open `PreToolUse` from the same launch and turn, persist that exact identity on the interaction, and accept only its matching completion. This resolves user- or provider-approved waits without inventing local input; same-turn parallel or ambiguous tools fail closed. If exact approval resolution is absent, a strictly later current-launch `UserPromptSubmit` or identity-bearing hook from a different foreground turn may retire the obsolete wait.
- Codex's native `Interrupt` hook is the primary turn-abort signal. Install it with launch-scoped trust, reliable ingest, no matcher, and a three-second timeout (the provider's maximum). Require its main-session and turn identity; apply Review/Interrupted, clear the foreground interaction, activity, and work evidence, and retain exact resume identity without completion summaries, checkpoints, notifications, or sounds. Its durable receipt closes the turn against delayed permission, tool, and Stop hooks; a newer foreground turn may establish Running. A valid pre-exit Interrupt replay can resolve an interaction made `resolution_unknown` by process loss.
- The [documented Interrupt contract](https://learn.chatgpt.com/docs/hooks#interrupt) covers user interruption of an active main-thread turn, not general failure reasons, idle threads, or subagents. Retain the bounded rendered "Conversation interrupted" fallback for hookless failures outside that contract, including foreground permission cancellation without a native terminal hook. It is terminal negative evidence only; output never establishes Running. Do not infer failure causes or claim full wrapper/parser failure granularity from Interrupt.
- Codex emits `PermissionRequest` before routing the decision and does not expose the effective reviewer in the native hook payload. Only an exact Quarterdeck launch configured with `user` treats that native hook as an actionable human wait. For `inherit` (including an omitted reviewer), `auto_review`, and bypass launches, retain it only as ordering/correlation evidence; the narrow rendered approval detector creates the actionable wait when Codex actually presents a choice. Inherited configuration may select automatic review, so unknown reviewer policy must not be promoted into proof that a person must answer. Do not read or guess external Codex configuration to classify the request.
- A carriage return while the shared indicator is `needsInput` records submit ordering so an older delayed `PermissionRequest` cannot restore the wait. Codex's exact single-byte `y` and numbered approval-row shortcuts are also submissions only while the current foreground interaction, or the oldest waiting Codex subagent approval, is a waiting Codex permission; the TUI consumes those hotkeys without Enter. These paths change only the typed interaction status, never Running: Enter can accept `/model`, compaction, an approval choice, or another TUI-local action. Input from ordinary Review, questions, editing, cursor movement, protocol responses, other providers, and PTY output remain semantically neutral.
- Codex dispatches root `Stop` and `SubagentStop` separately; install the review transition only for root `Stop` rather than inferring identity from missing summary fields.
- A thread-spawned Codex subagent's hooks carry `agent_id` (the child thread id) with the root `session_id` and the child's own `turn_id` and transcript path ([hook runtime](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/hook_runtime.rs)). They never author foreground state, interaction, work evidence, activity, completion, `resumeSessionId`, or the conversation source hint. Ordering admits only their `PreToolUse`, `PermissionRequest`, `PostToolUse`, `UserPromptSubmit`, and `SubagentStop` into a launch-scoped per-agent lane, and only when `session_id` equals the known foreground session. Root completion and turn fences do not apply to that lane, and it never enters durable ordering receipts. `/btw` forks are root threads with their own `session_id`, and their thread-spawned children inherit that fork's id; those, unverifiable scope, and root-only events carrying `agent_id` stay `non_foreground_session`.
- A child inherits the launch's live approval policy and reviewer ([child config](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/agent/child_config.rs)), and Codex routes its approval to the main TUI with a `Thread:` label. For an exact `user` launch, a subagent `PermissionRequest` opens a wait keyed by that agent in `subagentInteractions`, with the queueing and candidate rules in [Claude hooks](#claude-hooks), scoped by the agent's turn. Other reviewer modes keep it ordering-only, and the rendered detector owns the wait. The shared classifier shows Needs Input while top-level `state` stays the root lifecycle. Unlike Claude, a Codex subagent outlives its root turn, so root `Stop` and `Interrupt` do not retire its wait; only the live process holds it. The wait is retired by that agent's matching `PostToolUse` (or completion of all its candidates), a strictly later hook from a different turn of the same agent, or that agent's next non-candidate tool even when unanswered, because a denial by an unrecognized key emits no hook. Foreground navigation, process exit, replacement, and cold hydration also retire it. Enter, `y`, numbered rows, Escape, and Ctrl-C answer the oldest unanswered wait of the foreground dialog's kind. A rendered overlay with a `Thread:` header does not open a second, unkeyed wait while a native subagent wait is waiting; an unlabelled overlay is a foreground request. The detector latches per request (title and request rows), so a queued approval that replaces another without an empty frame is detected. Quarterdeck does not subscribe to Codex `SubagentStart`/`SubagentStop`.
- `SessionStart` stays metadata-only. Manual `/compact` uses its `PreCompact` / `PostCompact` pair matched only on `manual`, and both hooks are activity-only; automatic compaction does not change task state either. Do not infer `/resume`, plugin reload, or other TUI-local command state from typed text, prompt redraws, or terminal output.
- Prompt positionals require an explicit `--` after every option and config override. Keep launch-scoped global flags before `resume` or `fork`, and keep the prompt after the resume target and `--`; otherwise a prompt beginning with `-` can be parsed as a resume option during auto-restart.

A visible canonical Codex approval overlay never coexists with a Running task card. Native `PermissionRequest` is primary for explicit `user` launches. Other reviewer modes require the rendered prompt, and nested Code Mode tools may render approval without a native hook in any mode. Preserve the Codex-only rendered-screen fallback: require an official approval title, selected choice, and bottom-anchored confirm/cancel footer after the terminal mirror applies output; accept supported narrow or clipped layouts, including a subagent approval's `Thread:` header and open-thread footer hint, without scanning accumulated transcript text. Codex's "send input to … terminal" approval titles are not yet recognized. Route detection through `SessionTransitionController`, latch against redraws, and reset after every authoritative provider transition to Running. Enter confirmation, the overlay's exact `y` or numbered approval-row hotkey, or bare Escape cancellation moves the typed wait to response-pending; it cannot claim Running before native completion or later causal foreground-work evidence, and process loss becomes `resolution_unknown` instead of leaving Needs Input forever.

### Pi lifecycle extension

- Quarterdeck-managed Pi sessions always load the launch-scoped lifecycle extension. It owns exact session/run/tool identity, lifecycle delivery, and managed-session replacement guards.
- Preserve native Pi execution and trust behavior. The lifecycle extension must not inject project-trust or per-tool approval prompts, block tool calls, or replace user tool and extension configuration.
- The retired `piToolApprovalsEnabled` setting is ignored when loading older configuration and omitted from subsequent config writes. Pi has no Quarterdeck sandbox.

## Agent and host process launch

Quarterdeck inherits the user's shell environment. Agent discovery and task-agent startup use direct PATH checks and direct process launches. Do not spawn `zsh -i`, use shell fallback discovery, or launch a shell and type the command on these hot paths; heavy `conda` or `nvm` initialization can freeze concurrent starts. Interactive shells remain appropriate for explicit shell terminals.

The macOS app imports exported variables and executable paths from the interactive login shell by default, including Finder/Dock launches and setup in `.zshrc`. Settings → Runtime Environment offers an explicit opt-out, preserved across upgrades, which uses inherited environment and bounded executable-folder discovery instead. Shell aliases and functions are not imported. Capture uses a private bounded channel and belongs to desktop launch composition, never to each discovery or task start. Explicit environment refresh requires safe runtime restart; an attached CLI retains its owner's environment. Keep the bundled Node hook invocation separate from user-installed provider executables, and never log or persist inherited environment values. See [desktop environment resolution](../desktop-environment.md).

### Agent availability and launch admission

`src/config/agent-registry.ts` separates display caching from launch admission. Settings/config display reads may use its 30-second stale-while-revalidate cache. Task launches must use `resolveAgentCommandForLaunch(...)`: reuse only a fresh successful result, await refresh for expired entries or cached failures, and preserve `AgentCommandUnavailableError`'s typed reason, transient flag, and user-facing status message. Never cache probe timeouts or execution failures as unavailable-agent results.

Every task launch — explicit Start and startup recovery alike — gets one bounded retry of a transient availability probe (timeout or launcher failure) before it fails the launch; `src/server/task-session-start-service.ts` always passes `retryTransient: true` to `resolveAgentCommandForLaunch(...)`. Missing executables, unsupported versions, and missing required features are deterministic preparation failures and remain non-retryable. This probe retry is separate from the recovery coordinator's bounded process-launch retry.

The agent-availability probe's own timeout (`src/config/agent-registry.ts`) applies to every agent's `--version` check and Codex's `features list` check, with two separate budgets so a hung CLI can't stack latency across layers: display/config reads (Settings agent list, `getConfig`/`saveConfig`) use a 5s budget and never retry, keeping the UI responsive; task launches (`resolveAgentCommandForLaunch`) use a 10s budget with the one bounded retry described above. Codex's version and features probes run concurrently rather than version-then-features, so a slow CLI doesn't double that budget. Both budgets are injectable through `setAgentProbeTimeoutMsForTests(...)`, which overrides either so tests stay deterministic instead of depending on either duration or on host load. A probe timeout or launcher failure is never cached as an unavailable-agent result (see above); Settings agent changes (`assertSelectedAgentRunnable` in `src/config/runtime-config.ts`) surface a transient-probe failure with task-launch-neutral wording ("could not confirm ... is runnable right now ... try again") rather than the launch-oriented "Retry the task" status message.

A probe whose timeout timer fired is a timeout regardless of the child's later exit status, because some launchers (e.g. Codex's npm shim) trap the terminating signal and still exit 0.

Keep availability probe diagnostics metadata-only: `agentId`, probe kind, duration, and typed outcome. Do not include command output, thrown messages, or inherited environment values.

### Host effects

`IRuntimeHostIntegrations`, composed by `createRuntimeHostIntegrations`, is the sole production boundary for server-side file, application, URL, and folder-picker effects. Keep its launch-scoped `RuntimeCapabilities` check ahead of launcher discovery and return discriminated typed outcomes. Open Project sends only an allowlisted target ID; the runtime derives the scoped project path and owns executable and argument construction. Do not restore an arbitrary runtime-command route or browser command builder, and do not bypass the service from a handler.

On headless remote Linux, native pickers such as `zenity` or `kdialog` may be unavailable. Treat that as a supported runtime limitation and use manual path entry rather than requiring desktop packages.
