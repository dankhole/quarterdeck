# M21 — Browser terminal ownership and panels

Baseline: `fb9a34fbc41fb8464dd5133db066120c24eb866c`. Reviewed 2026-09-26. This was a read-only application review using the review-code-smells workflow alongside concurrency, lifecycle, transport and presentation review. No application or permanent test sources were changed.

## Scope and ownership

Read all **65 primary files** in the exact M21 inventory: **45 production files and 20 colocated test files**. Traced pooled and dedicated terminal creation, task/project selection, disconnect and reuse, queued writes and acknowledgements, restore/readiness, renderer/DOM attachment, resize, shell start/close/restart and panel consumers. Read the applicable session-lifecycle, frontend, frontend-hooks, UI-layout, architecture and testing conventions.

The four-slot bound, dedicated project/task registry, staged DOM host, resize invalidation and output batching have distinct contracts. The review did not establish a separate style-only removal or measured performance finding. The three findings below concern missing lifecycle fences at the boundaries between those owners.

## Findings

### M21-F01 — P2 · Lifecycle/concurrency: closing a shell panel does not cancel its pending start

- **Anchor:** [use-terminal-panels.ts](../../web-ui/src/hooks/terminal/use-terminal-panels.ts), home start lines 337–369 and detail start lines 394–436; close paths at lines 252–291. The geometry wait is [terminal-panels.ts](../../web-ui/src/hooks/terminal/terminal-panels.ts), lines 92–103, with a default 300 ms wait in [terminal-geometry-registry.ts](../../web-ui/src/terminal/terminal-geometry-registry.ts), lines 35–60.
- **Trigger:** Open a home or task-detail shell, then close it while start is waiting for geometry or an earlier stop. The close path sends and completes its stop before the pending start reaches `startShellSession.mutate()`.
- **Consequence:** Closing clears panel visibility, clears the ownership ref/map and disposes its dedicated slot, but the start continuation retains the old project/task and launches afterward. Its success unconditionally upserts the session. The backing shell can therefore remain running with its panel closed and ownership already discarded; another Close has no recorded home owner to stop. Selection/context cleanup uses the same close paths. Ignoring only the late UI result would not prevent the process side effect.
- **Evidence:** Two synthetic React tests invoked the actual hook, deferred only geometry, and mocked the RPC/native boundary. Both home and detail traces were `stop(task) → start(task)` with the final panel-open state `false`. The start was not yet sent at Close, and the stop had already resolved before geometry was released. Existing tests supply immediate geometry, so they do not exercise this ordering. This proves the erroneous request sequence; no actual shell process was launched.
- **Smallest remedy:** Give each project/shell open intent a generation that close, context reset and disposal invalidate. Recheck it after every wait and before sending start. Serialize start/close effects or compensate an already-issued successful stale start against its exact returned session identity, without stopping a newer reopen. Keep the existing wait for earlier stop completion.
- **Validation needed:** Cover home/detail close during geometry, reopen during pending stop, context/project switch and unmount, plus close after start was sent but before its result. Assert that a cancelled intent cannot launch and that late completion cannot leave a hidden process or stop a newer owned shell.

### M21-F02 — P2 · Terminal ownership: immediate pool reuse carries old output into the new task

- **Anchor:** [terminal-pool.ts](../../web-ui/src/terminal/terminal-pool.ts), lines 95–103 and 290–294; [terminal-attachment-controller.ts](../../web-ui/src/terminal/terminal-attachment-controller.ts), lines 193–203. The consequences cross [terminal-viewport.ts](../../web-ui/src/terminal/terminal-viewport.ts), lines 266–288, and [slot-write-queue.ts](../../web-ui/src/terminal/slot-write-queue.ts), lines 156–176.
- **Trigger:** Select tasks A, B and C so the pool evicts the older PREVIOUS slot A and immediately assigns that same slot to C. A has existing buffer content or a queued live-output batch. C's initial restore may legitimately be empty, for example before its process has emitted output.
- **Consequence:** Eviction marks the slot FREE and starts an unawaited disconnect. Disconnect closes A's sockets, awaits pending writes, then resets only if the slot is still unassigned. Immediate C assignment makes that condition false, leaving A's buffer in C's terminal. C's empty restore then deliberately skips resetting any nonempty buffer, although those bytes belong to A. Queued A writes also resolve their output subscriber and control-send callbacks through the now-current C session, publishing A's text and sending A's byte acknowledgement over C's control socket. The result is incorrect task attribution and incorrect acknowledgement accounting, not just a temporary renderer artifact.
- **Evidence:** Synthetic tests used the actual pool, slot, session/controller, write queue, viewport and installed xterm parser/buffer. Only WebSocket delivery and the visual renderer boundary were replaced. Acquiring A → B → C reused A's exact slot; after C acknowledged its empty restore, `connectedTaskId` was C but the buffer contained `A_PRIVATE_SYNTHETIC_BUFFER`. A second trace queued `A_OLD_OUTPUT` before eviction and observed C's subscriber receiving it and C's control socket sending `{type:"output_ack",bytes:12}`. No C output was supplied. The server applies acknowledgements to the current viewer at [ws-server.ts](../../src/terminal/ws-server.ts), lines 324–325, and subtracts them from that viewer's outstanding count in [terminal-ws-backpressure-policy.ts](../../src/terminal/terminal-ws-backpressure-policy.ts), lines 150–152. A stalled or memory-exhausted real runtime was not claimed or tested.
- **Smallest remedy:** Make reassignment an explicit ownership boundary: complete or invalidate old writes/restores and clear the old buffer before the new task can own the slot. Bind queued notifications and ACKs to the originating connection/generation, dropping stale completion instead of routing through mutable current-session callbacks. Keep the empty-restore protection only for live output from the same binding. A serialized rebind operation within the attachment owner can preserve the four-slot bound without recreating every terminal.
- **Validation needed:** Use real asynchronous xterm writes for A → B → C, warmup eviction and project release/reacquire. Check empty and nonempty new restores, old queued batches, an accepted restore still awaiting a write, and dispose during drain. Require no old bytes, callbacks or ACKs to reach the new owner and preserve same-binding live-output/empty-restore protection. Pool tests currently mock disconnect as immediately complete and cannot establish this boundary.

### M21-F03 — P2 · Restore ordering: dedicated shell updates erase an already restored prompt

- **Anchor:** [use-persistent-terminal-session.ts](../../web-ui/src/terminal/use-persistent-terminal-session.ts), lines 134–155. Compare the pooled branch's reset-and-restore handling at lines 231–250. [shell-terminal-panel.tsx](../../web-ui/src/components/terminal/shell-terminal-panel.tsx), lines 35–47, supplies `summary.startedAt`, including `null` before the first summary.
- **Trigger:** A dedicated home/detail slot completes its initial or replacement-session restore before the React effect receives the changed `sessionStartedAt`. The effect regards any changed timestamp for the same project/task—including `null` to the first timestamp—as a restart.
- **Consequence:** The effect reuses the existing dedicated slot and resets its buffer after the authoritative prompt was applied. It requests no fresh restore. The terminal can stay blank until new process output or manual re-sync, despite having successfully restored and connected. The pooled branch explicitly handles this same ordering by requesting a new restore after reset; dedicated shells omit that part of the contract. Session-instance reconnection occurs below React in [terminal-attachment-controller.ts](../../web-ui/src/terminal/terminal-attachment-controller.ts), lines 144–176, and summary forwarding occurs separately in [terminal-session-handle.ts](../../web-ui/src/terminal/terminal-session-handle.ts), lines 342–347.
- **Evidence:** A synthetic React test used the real hook, dedicated registry, slot/controller, viewport and xterm buffer with fake sockets/renderer. It mounted with a null timestamp, completed a control restore containing `NEW_SESSION_PROMPT>`, then delivered the first timestamp through props. The same slot's buffer became empty and its control socket sent zero `request_restore` messages. This establishes the permitted delayed-prop ordering and buffer result; it does not measure its frequency in a browser or claim a screenshot-level rendering observation.
- **Smallest remedy:** Preserve the same reset/restore guarantee in the dedicated branch as in the pooled branch, or move reset ordering into the session-instance owner so React cannot erase a newer applied snapshot. Avoid treating a late UI summary as permission to discard authoritative content without recovery.
- **Validation needed:** Cover initial null-to-known timestamps and actual replacement timestamps, with restore completing both before and after the effect. Assert the final buffer contains the current session prompt, pending restores remain bounded, and ordinary hide/remount does not reset an unchanged session.

## Uncertainty, overlap and existing backlog

- F01 is distinct from [M13-F01](./M13.md#m13-f01--p2--resource-ownership-detail-shell-starts-can-run-inside-a-worktree-that-trash-is-deleting): M13 owns server destructive-operation admission; this report demonstrates a browser Close sending stop before its own delayed start, also for a home shell with no Trash operation. [M06-F02](./M06.md#m06-f02--p2--resource-lifecycleconcurrency-shell-starts-lack-pending-ownership-and-can-orphan-a-concurrent-pty) owns concurrent server shell-start publication; F01 does not depend on two simultaneous server starts.
- [M07](./M07.md) owns server restore overlap, missing restore acknowledgement bounds and WebSocket failure handling. F02 concerns one browser slot changing ownership and sending completed writes to a different connection; it does not duplicate the backend restore/backpressure findings.
- The coordinator is evaluating delayed shortcut/input delivery through the task-keyed controller registry under M19. Generic same-ID registry/pool collision is not counted here: project switch has explicit `releaseAll()` cleanup, and a reachable delayed caller needs separate evidence. The analogous delayed card-detail submit path was passed to that owner.
- Accepted old restore continuations also lack a binding generation around the viewport's asynchronous drain/application. F02's remedy and required tests include them, but this pass did not separately reproduce every old-restore/new-restore interleaving. It is not a fourth finding.
- The active [todo](../todo.md) asks whether shells should persist across minimization/context change. Current implementation explicitly treats Close/context change as stop/dispose. F01 violates that implemented contract regardless of the future product choice; the report does not propose implicit persistence.
- Renderer/WebGL/font/DPR recovery, actual PTY backpressure under high output, platform clipboard behavior and real-provider TUI timing were source-reviewed only. No measured performance regression, native compatibility result or visual correctness claim is made.
