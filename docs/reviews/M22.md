## Findings

### M22-F01 — P2 · Scope preservation: Stash & Pull retries a task operation in the home checkout

- **Anchor:** [use-git-actions.ts](../../web-ui/src/hooks/git/use-git-actions.ts), lines 330–335 and 445–483.
- **Trigger:** A pull for a task worktree or an explicitly selected branch fails with `dirtyTree`, and the user chooses **Stash & Pull** in the error dialog. The original request carries `taskScope` and `branch`, but the error state retains neither. Every dirty pull exposes the same retry callback at lines 516–517.
- **Impact:** The retry stashes the home working copy, pulls its default branch, then pops a stash into that checkout. The requested task pull remains undone. If home is clean, the stash step fails instead of helping with the dirty task; if home is dirty, unrelated home changes and its branch are mutated. An explicit home-branch pull also loses its chosen branch.
- **Evidence:** The original call preserves scope/branch at lines 318–322. The retry hardcodes `taskScope: null` for push/pop and sends only `{ action: "pull" }`. Task-scoped pulls are reachable from [App.tsx](../../web-ui/src/App.tsx), line 517, and the task repository toolbar in [task-detail-repository-surface.tsx](../../web-ui/src/components/task/task-detail-repository-surface.tsx), line 173. A synthetic check invoked the real hook with task A/feature A, returned a dirty-tree failure, then invoked its retry. It observed home-scoped stash/pop and an unscoped pull, exactly as above.
- **Smallest remedy:** Retain the complete failed operation identity, including project, task scope, branch and summary-update policy, and use it throughout retry. Do not reconstruct the target from the current selection or default checkout.
- **Validation needed:** Repeat the scoped-request assertion for task and explicit home-branch pulls; use isolated repositories to verify only the selected checkout is changed. Stash object identity during a concurrent stash push is a separate backend issue already recorded as M11-F04.

### M22-F02 — P2 · Conflict ownership: resolved paths and previews survive into another conflict scope

- **Anchor:** [use-conflict-resolution.ts](../../web-ui/src/hooks/git/use-conflict-resolution.ts), lines 53–55, 68–87 and 90–121.
- **Trigger:** Resolve `a.txt` in one rebase step, then advance to a later step that conflicts on `a.txt` again. The step-reset effect schedules a cleared resolved set, but the following load effect still reads the preceding render's `resolvedFilesRef`; it filters out the repeated path and returns. The next render updates the ref without changing the load effect's dependencies. Separately, switching directly between two conflicted tasks at the same step never resets the resolved set at all, because resets depend only on step or active/inactive state.
- **Impact:** The later step can display the prior step's ours/theirs content instead of the content the resolution action will actually select. A second task's unresolved file can be marked resolved and omitted from loading because the first task resolved the same pathname. This undermines the preview and resolution progress used to choose how to finish a merge/rebase.
- **Evidence:** Two synthetic checks used the real hook with controlled metadata and RPC results. After step 1 resolution, an empty conflict poll and step 2's repeated pathname, the resolved set became empty but the fetch count stayed at one and preview text remained `step-1 ours`. Switching task A to task B with the same step/path retained A's resolved flag and did not fetch B's content. [task-detail-repository-surface.tsx](../../web-ui/src/components/task/task-detail-repository-surface.tsx), line 108, renders the same unkeyed Git view across task changes. The panel consumes the cached content and resolved flags in [conflict-resolution-panel.tsx](../../web-ui/src/components/git/panels/conflict-resolution-panel.tsx), lines 74–88 and 148–164.
- **Smallest remedy:** Scope local conflict state to project, task and conflict operation/step. Reset its content, resolution sets and synchronous refs before deriving the next load, or use an explicit scope generation in loading and publication. A React state reset in a preceding effect is not a synchronous ref reset.
- **Validation needed:** Cover repeated paths across rebase steps, active-to-active task changes, and late resolution responses after a scope change. Verify the displayed content and resolved status match the currently actionable conflict. A later metadata dependency change may reload the step preview; the check establishes the missed transition, not a guarantee that every later poll leaves it stale.

### M22-F03 — P2 · Selection semantics: deselecting every file still stashes all changes

- **Anchor:** [use-commit-panel.ts](../../web-ui/src/hooks/git/use-commit-panel.ts), lines 297–309; [commit-panel.tsx](../../web-ui/src/components/git/panels/commit-panel.tsx), lines 302–306.
- **Trigger:** Uncheck all files in the commit panel, then click **Stash**. The button remains enabled whenever files exist; the callback has no empty-selection guard.
- **Impact:** The empty selected-path list is sent as `paths: []`, the backend sentinel for the entire working copy. All changes, including untracked files, are removed from the working copy into a stash even though none are selected. This is recoverable through the stash, but it performs the opposite of the selection shown by the UI.
- **Evidence:** The callback uses an empty list both for all-selected and none-selected. [git-stash.ts](../../src/workdir/git-stash.ts), lines 32–38, adds a path restriction only for a nonempty list and always includes untracked files. A synthetic real-hook check deselected both available files, verified `selectedPaths` was empty, and observed a successful call to `stashPush` with the unrestricted sentinel. Existing selection tests exercise the empty commit guard but do not cover this stash case.
- **Smallest remedy:** Disable Stash and return from its callback when no paths are selected. Keep the all-files sentinel only for an explicitly nonempty all-selected state, or send the selected paths consistently under a clearly typed scope contract.
- **Validation needed:** Assert no RPC for empty selection, restricted paths for a subset, and the intended all-file request when every file is selected. This is distinct from M11-F01's interpretation of nonempty filenames as pathspecs.

### M22-F04 — P2 · Draft ownership: late commit work overwrites a newer message draft

- **Anchor:** [use-commit-panel.ts](../../web-ui/src/hooks/git/use-commit-panel.ts), lines 179–205 and 331–351.
- **Trigger:** Start message generation and continue editing the textarea before the response arrives; or start a commit for task A, select task B and enter its next message before A completes. The textarea remains editable while work is pending, and message state has neither a scope generation nor an edit revision.
- **Impact:** Generated text overwrites the user's newer wording. A completed commit unconditionally clears the message even when it now belongs to another task or a newly edited draft. The browser loses work the operation never consumed.
- **Evidence:** The textarea at [commit-panel.tsx](../../web-ui/src/components/git/panels/commit-panel.tsx), lines 362–369, remains enabled. The task side panel renders an unkeyed `CommitPanel` at [task-detail-side-panel.tsx](../../web-ui/src/components/task/task-detail-side-panel.tsx), line 43. Two synthetic checks deferred real-hook RPC boundaries: a generated result replaced `new manual draft`, and a task A commit completion cleared `task B draft` after the same hook moved to task B. No model or Git process was involved.
- **Smallest remedy:** Capture the request's project/task scope and message edit revision. Publish generated text or clear a successfully committed draft only if that request still owns the current draft. Give drafts an explicit per-scope owner; disable-only treatment must also account for task changes.
- **Validation needed:** Resolve deferred generation/commit after a manual edit, task change and unmount, preserving newer drafts while still clearing an unchanged successfully committed message. Keep the existing commit/push failure behavior.

### M22-F05 — P2 · Dialog lifecycle: a second cherry-pick confirmation cannot be cancelled

- **Anchor:** [cherry-pick-confirmation-dialog.tsx](../../web-ui/src/components/git/history/cherry-pick-confirmation-dialog.tsx), lines 34–54.
- **Trigger:** Confirm one **Land commit on branch** dialog, let it close, then open another confirmation in the same history view. `confirmFiredRef` becomes true on the first confirmation and is never reset when the dialog closes or changes commit.
- **Impact:** The later dialog's Cancel button and `onOpenChange` dismissal both return without invoking `onClose`. The user cannot dismiss that confirmation normally, despite no cherry-pick being active. Leaving/remounting the history surface is required to reset it without confirming another mutation.
- **Evidence:** [git-history-view.tsx](../../web-ui/src/components/git/git-history-view.tsx), lines 155–189 and 413–418, closes dialog state after work but keeps the dialog component instance mounted; returning `null` is not an unmount of that instance. A synthetic DOM check rendered the real component and Radix controls, clicked the first confirmation, rendered closed then a different open commit, and clicked Cancel. `onClose` was never called and the dialog remained present.
- **Smallest remedy:** Reset the synchronous confirmation guard at the start/end of each dialog lifecycle, keyed to the confirmation identity. Retain protection against Radix's immediate close callback during the currently pending confirmation only.
- **Validation needed:** Exercise two successive open/confirm/close cycles and a second-open cancel, including first-operation failure. Preserve the original immediate-close protection and loading-state guard.

### M22-F06 — P2 · Request lifecycle: metadata refresh leaves history pagination permanently busy

- **Anchor:** [use-git-history-data.ts](../../web-ui/src/components/git/history/use-git-history-data.ts), lines 187–199 and 260–268.
- **Trigger:** A next-page request is pending when a working-copy metadata update refreshes history without changing its refs. The silent replacement request aborts the page request. The retired request's `finally` cannot clear its loading flag because it no longer owns the controller, while the replacement only clears the non-pagination loading flag.
- **Impact:** `isLoadingMoreCommits` remains true after all requests settle. Both subsequent explicit and automatic pagination are blocked, so older commits cannot be reached until the history scope is reset or reopened.
- **Evidence:** Metadata changes trigger silent refresh at lines 438–450; `loadMoreCommits` rejects while the stale flag is true at lines 298–300. A synthetic real-hook check loaded 150 of 400 commits, held the append request until its abort signal fired, and increased `stateVersion` with unchanged refs. The replacement completed with `isLogLoading` false but `isLoadingMoreCommits` true. Another load-more call produced no query; the count stayed at three (initial, aborted page, refresh). The main reset effect does not rerun when scope and refs remain stable.
- **Smallest remedy:** Transfer both loading flags to each new request when replacing the previous one, or derive the mode from a single owned request state. Preserve the current protection against a retired request clearing the new request's state.
- **Validation needed:** Interleave pagination with metadata refresh and manual refresh, for success, failure and cancellation; assert loading settles and the next page can subsequently load. Keep stale-response rejection and duplicate-commit suppression.

### M22-F07 — P3 · Maintainability: task-agent Git orchestration has no production caller

- **Anchor:** [use-git-actions.ts](../../web-ui/src/hooks/git/use-git-actions.ts), lines 153–302; [git-provider.tsx](../../web-ui/src/providers/git-provider.tsx), lines 203–225.
- **Trigger/impact:** Every mounted Git provider retains a substantial commit/PR-to-agent workflow, four derived loading maps, terminal input dependencies and a dedicated prompt builder, but none of its four action handlers can be invoked by the current application. Future changes must still understand and maintain this inactive workflow alongside the actual selected-file commit and task-input paths. The provider also exposes a loading map that no production consumer reads.
- **Evidence:** Repository-wide symbol search found the sole production `useGitActions(...)` caller in `GitProvider`; its destructuring omits `handleCommitTask`, `handleOpenPrTask`, `handleAgentCommitTask` and `handleAgentOpenPrTask`. Those names occur only in the hook's interface, definitions and return value. [build-task-git-action-prompt.ts](../../web-ui/src/git-actions/build-task-git-action-prompt.ts) has no production caller outside this unreachable subflow. The loading map occurs only in its producer/provider plumbing; one task-view test mock includes it. This is a source/call-graph finding, not a measured performance regression.
- **Smallest remedy:** Remove the unreachable handlers, their exclusive prompt-builder/loading helpers and corresponding unused provider inputs/fields, retaining any types or configuration used elsewhere. If restoring agent-driven actions is desired, treat that as an explicit feature with a real consumer and current session-identity contract rather than preserving dormant orchestration indefinitely.
- **Validation needed:** Re-run symbol/reference checks and frontend type checking after removal, plus the existing active Git-action and commit-panel tests. Do not remove shared prompt configuration solely because this browser helper is unused.

These were traced as UI consequences but are not repeated here. F01–F03 have separate frontend causes and remedies.
- M21/M19 own reachable terminal input ownership issues. The delayed terminal submission inside F07's unreachable code was not presented as a live input defect. M17's config/query ownership findings concern different stores and do not cover these local Git drafts or request flags.
- The active todo list requests Git/Files profiling and a Revert commit feature. Neither is evidence for a performance finding or one of the defects above. Graph construction, ref filtering and large-list behavior were reviewed, but no measured performance regression was established. The task history working-copy query's omitted mode is valid because its server default is `working_copy`.

## Validation and limits

- **59 existing tests passed** across six focused suites: `use-commit-panel`, `use-conflict-resolution`, `use-stash-list`, `git-actions`, `use-git-history-data`, and the `commit-panel` component. The other 13 primary test files were read, not executed.
- **Nine synthetic checks passed:** scoped pull retry; repeated-path rebase transition; active-to-active task conflict switch; empty stash selection; late generated text; late commit completion; two cherry-pick dialog cycles; refresh interrupting pagination; and the unscored cross-project stash-hook candidate. The first eight assert the current behavior underlying F01–F06. These checks are evidence of defects, not fixes.
- Checks used real hooks/components with React DOM and synthetic RPC/metadata boundaries. The dialog case used its real Radix controls. They did not run a provider, Git command or application runtime. The temporary synthetic test/config sources were removed; logs remain under ignored `.quarterdeck/review-validation/m22-candidates.log` and `m22-focused-tests.log`. Report links and all 67 inventory entries were checked.
- No browser session, Agent Lab, real provider, Git mutation fixture, broad suite, build or typecheck ran. No latency/memory measurement or visual claim is made. The checks establish local state/argument decisions and controlled interleavings; actual multi-worktree Git effects, full navigation timing and platform behavior remain validation work for fixes.
