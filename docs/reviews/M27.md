## Findings

### M27-F01 — P2 · Dependency isolation: Codex environment setup recreates dangerous shared dependency links

**Trigger and impact.** When the tracked Codex environment `[setup]` script runs in a checkout without root `node_modules`, it symlinks both root and web `node_modules` into the primary worktree. A subsequent `npm ci` from that checkout can remove packages in the primary checkout, including dependencies used by a live globally linked Quarterdeck runtime. This is dependency-directory corruption and runtime availability loss; the evidence does not show deletion of source files or task data. The guard checks only root `node_modules`, so it also fails to repair an independently missing web tree when root dependencies already exist.

**Evidence.** [`.codex/environments/environment.toml`](../../.codex/environments/environment.toml) lines 6–11 creates the links. [`AGENTS.md`](../../AGENTS.md) line 105 and [`DEVELOPMENT.md`](../../DEVELOPMENT.md) line 18 require task-local dependency trees. [`docs/implementation-log.md`](../implementation-log.md) lines 602–606 records the same earlier dependency-link incident. A fully isolated `/tmp` check on Node 22.22.2/npm 11.19.0 created a synthetic task-to-primary `node_modules` symlink with a sentinel in the primary directory; `npm ci --offline --ignore-scripts` from the task exited 0, removed the link and removed the primary sentinel. All synthetic paths were cleaned. Repository search found no Quarterdeck task-setup caller for this TOML: the trigger is **Codex environment provisioning executing its configured script**, not ordinary Quarterdeck task-worktree creation.

**Remedy and validation.** Replace the environment setup script with independent `npm ci` in each checkout, or leave installation to the documented task-local bootstrap. Check both dependency trees independently and reject legacy links before any installer follows them. Validate the exact Codex environment activation path and a fresh isolated checkout with its primary dependencies protected; retain the safe synthetic npm regression check.

### M27-F02 — P2 · Git staging: pre-commit hook silently adds unstaged hunks

**Trigger and impact.** A developer partially stages a file, then commits. After checks, the hook runs `git add` on every file with any staged content, which adds that file's remaining unstaged edits to the commit. This can commit unfinished work that was deliberately excluded from the staged patch.

**Evidence.** [`.husky/pre-commit`](../../.husky/pre-commit) lines 3 and 19–23 gather staged filenames and add their full working-tree contents. In an isolated temporary Git repository, a file containing staged `staged` and unstaged `unstaged` lines had only `staged` in the index before the hook's loop and both lines afterward. The synthetic repository was removed.

**Remedy and validation.** Remove the final re-add loop: `biome check --staged` is a read-only check and does not require restaging. If the hook later gains a formatter, stage only its intentional edits without changing unrelated hunks. Verify a partially staged file stays partially staged after a successful hook and a path containing spaces is handled correctly.

### M27-F03 — P2 · Shutdown ownership: dogfood instances with separate state homes share one cleanup lock

**Trigger and impact.** Start two dogfood wrappers concurrently with different `QUARTERDECK_STATE_HOME` values. The second observes the first wrapper's global temp lock and launches its independent runtime with `--skip-shutdown-cleanup`. On its shutdown, that runtime skips session interruption and explicit managed-process cleanup despite having no other owner for its state home. Persisted task sessions can remain stale; a managed child that survives runtime exit has no wrapper cleanup attempt. The wrapper's tree-kill fallback runs only when the runtime fails to exit before its timeout.

**Evidence.** [`scripts/dogfood.mjs`](../../scripts/dogfood.mjs) lines 15–20 uses one fixed lock path for all checkouts and state homes; lines 112–119 make any live lock PID the owner; lines 371–375 and 401–405 turn nonownership into the skip flag. The same script explicitly supports state-home overrides at lines 349–368. Its normal shutdown closes child stdin at lines 267–276, starts a timed tree-kill fallback at lines 277–285, and cancels that timer on child exit at lines 306–324. [`src/cli.ts`](../../src/cli.ts) lines 807–817 forwards the skip flag; [`src/execution/structured-shutdown-preparation.ts`](../../src/execution/structured-shutdown-preparation.ts) lines 16–21 skips stopping structured owners; [`src/server/shutdown-coordinator.ts`](../../src/server/shutdown-coordinator.ts) lines 126–131 immediately closes the server without session cleanup. [`src/server/runtime-state-hub.ts`](../../src/server/runtime-state-hub.ts) lines 409–425 closes browser resources, not terminal managers.

**Remedy and validation.** Scope cleanup ownership to the canonical state home (and the runtime group whose cleanup it protects), or let each independent runtime perform its own shutdown cleanup. Test two isolated state homes with concurrent wrappers and verify stopping either runtime retires only its own sessions and processes.

### M27-F04 — P2 · Concurrency: an incomplete dogfood lock can elect two cleanup owners

**Trigger and impact.** Wrapper A creates the exclusive lock file and has not yet written its JSON record. Wrapper B encounters `EEXIST`, reads an empty/partial record as invalid, unlinks A's live lock, and creates a new one. Both return `isCleanupOwner: true`. This violates the wrapper's single-owner cleanup policy: both runtimes then enter the full shutdown path and may write interrupted sessions in the same shared state home when either exits. The token written after opening A's now-unlinked inode cannot restore single ownership. Source inspection does not establish that either wrapper directly kills the other runtime's live processes.

**Evidence.** [`scripts/dogfood.mjs`](../../scripts/dogfood.mjs) lines 85–105 opens with `wx` and then writes the record asynchronously. Lines 52–70 convert an incomplete read into `null`; lines 112–127 treat that `null` as stale and unlink the file. There is no lock-initialization handshake or inode recheck. The same stale-unlink path can also race a replacement owner. [`src/server/shutdown-coordinator.ts`](../../src/server/shutdown-coordinator.ts) lines 177–192 gathers started tasks from the shared project index and lines 207–220 persists interrupted session summaries in normal cleanup; managed-process orphan cleanup checks exact ownership and does not by itself prove cross-runtime process termination. This is a source-proven lock interleaving, with a conditional shared-persistence consequence; no real dogfood process was launched for this review.

**Remedy and validation.** Publish a complete ownership record atomically and never classify a newly created unreadable file as stale until its creator's identity or an age bound has been checked. Fence stale-file removal against the exact file inspected. Use a focused multi-process temporary-directory test that pauses the first writer after exclusive creation and proves only one owner emerges, then test stale recovery.
