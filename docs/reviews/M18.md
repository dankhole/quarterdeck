# M18 — Application shell, navigation and layout

Baseline: `fb9a34fbc41fb8464dd5133db066120c24eb866c`. Review completed 2026-09-26. All 79 primary files in [module-inventory.json](./module-inventory.json) were read in full: 59 production files and 20 colocated test files. No application or existing test files changed.

The pass covered shell composition, project/task selection, URL synchronization, modal and hotkey behavior, single-tab ownership, startup setup, task-aware host actions, layout state, resize cleanup and maintainability. Repository instructions, the review-code-smells skill, and the web-ui, frontend-hooks, ui-layout, runtime-state, architecture and testing conventions informed the review. ## Findings

### M18-F01 — P2 · Scope preservation: task Open in IDE opens the project root

**Anchor:** [use-open-project.ts](../../web-ui/src/hooks/project/use-open-project.ts), lines 81–92; [connected-top-bar.tsx](../../web-ui/src/components/app/connected-top-bar.tsx), lines 97–103.

Select an isolated task whose worktree exists, then use its top-bar Open button. [use-navbar-state.ts](../../web-ui/src/hooks/app/use-navbar-state.ts), lines 72–80, deliberately resolves the assigned task checkout and refuses a missing worktree; its tests explicitly require the worktree as the open path. That path reaches `useOpenProject`, but is used only as a Boolean admission check. The request sends only `targetId`, so the server opens the project root. The user is placed in the shared checkout instead of the task checkout shown by the toolbar, which can direct subsequent IDE edits to the wrong working tree.

**Evidence:** the strict [request schema](../../src/core/api/shared.ts), lines 68–72, cannot carry task identity. The [server handler](../../src/trpc/handlers/open-project.ts), lines 12–15, always supplies `projectScope.projectPath` to the host boundary. A disposable composed test used the actual navbar hook, open hook, request parser and server handler; only the tRPC transport and final native host effect were replaced. With project `/repo-a` and existing task checkout `/worktrees/task-1/repo-a`, it asserted:

```text
navbar.openProjectPath = /worktrees/task-1/repo-a
canOpenProject = true
RPC input = { targetId: "vscode" }
host open path = /repo-a
```

**Remedy:** carry a typed optional task identity through the hook and RPC, then resolve that task's valid existing checkout on the server before calling `IRuntimeHostIntegrations`. Preserve root opening for home/shared-checkout tasks and the missing-worktree rejection. Do not restore arbitrary browser-supplied native commands or trust a browser path as the checkout authority.

**Validation:** compose the task toolbar with the actual request/handler boundary for home, shared checkout, existing isolated checkout and missing/deleted checkout. Assert the final host path, not just the navbar's derived path or invocation count. The check here did not launch an IDE or establish native-platform acceptance.

### M18-F02 — P2 · Optimistic state: failed project reorders never roll back

**Anchor:** [use-project-navigation-panel.ts](../../web-ui/src/hooks/project/use-project-navigation-panel.ts), lines 36–41 and 73–77; [use-project-navigation.ts](../../web-ui/src/hooks/project/use-project-navigation.ts), lines 318–329.

When the project-reorder mutation fails, the navigation hook shows an error but fulfills its `Promise<void>`. The panel has already installed `optimisticOrder` and neither observes completion nor receives a failure result. It clears the override only when the server's project-ID sequence changes. Since a failed write leaves that sequence unchanged, ordinary authoritative refreshes—including new counts/revisions—cannot restore the displayed order. The sidebar continues showing an order that was never saved until a remount or a later actual ordering/membership change.

**Evidence:** a disposable test composed the real navigation and panel hooks with a controlled stream and reorder transport. Starting with authoritative `[A,B,C]`, it moved A to the end, returned `{ok:false,error:"Synthetic reorder failure"}`, and verified the error notification. After supplying a fresh authoritative array with the same `[A,B,C]` order and newer board revisions, the displayed order remained `[B,C,A]`. Existing panel tests cover successful optimistic ordering and changed membership, but not mutation failure.

**Remedy:** return a typed success/failure result (or propagate the rejection) and roll back the matching optimistic reorder on failure. Track a request generation if multiple drags remain admissible so an older failure cannot erase a later user's order. Reconcile successful acknowledgment with the authoritative order rather than treating any unrelated list change as that acknowledgment.

**Validation:** cover rejected and thrown mutations, unchanged authoritative refreshes after rejection, successful acknowledgment and two overlapping reorders completing out of order. This finding establishes the failed-write display mismatch; it does not claim loss of task data.

### M18-F03 — P3 · Maintainability: layout persistence maintains state no production consumer reads

**Anchor:** [use-card-detail-layout.ts](../../web-ui/src/resize/use-card-detail-layout.ts), lines 24–85 and 106–128; sole production consumer [surface-navigation-provider.tsx](../../web-ui/src/providers/surface-navigation-provider.tsx), lines 56–67.

The layout explicitly starts with Home + Projects on every mount. Nevertheless, every main-view/sidebar change writes the old storage keys through `persistMainView`/`persistSidebar`; `loadMainView` and `loadSidebar` are used only by their tests. The hook also loads, updates, persists and returns `lastSidebarTab`, but its sole production caller discards that result. Task selection hard-codes `task_column`, and terminal restoration uses `sidebarBeforeAutoCollapseRef`, so neither path consumes the persisted last tab. The migration loaders, state and writes add no current within-session or reopen behavior.

**Evidence:** repository-wide symbol searches found no production reads of the main/sidebar loaders or storage keys outside this hook, and no production consumer of its returned `lastSidebarTab`. The [layout convention](../conventions/ui-layout.md), Persistence and Adding A Main View/Side Panel sections, still tells maintainers to update these loaders, while all 29 cases in the colocated layout test file exercise storage loaders rather than the active auto-coupling. This is redundant compatibility machinery, not a measured performance regression.

**Remedy:** remove the unused main/sidebar migration loaders and their write-only persistence wrappers, plus the unconsumed last-sidebar state/persistence. Keep React's current view/sidebar state, `sidebarBeforeAutoCollapseRef`, side-panel ratio persistence and layout-reset behavior. Update the convention and replace obsolete loader tests with the actual selection/collapse/restore rules. If restoring layout across reopen is desired later, first define that behavior; the current documentation explicitly specifies a fresh mount.

**Validation:** verify fresh mount, task select/deselect, Home navigation, Files/Git auto-collapse, Terminal restoration, Commit exemption and project switching. Confirm resize preferences still persist/reset. No storage or migration code was removed during this review.

## Uncertainty, overlap and limits

- **Discarded cancellation candidate:** comparing selection with `currentProjectId` initially appeared to block a return from pending B to A. The actual stream reducer installs the requested identity immediately in its request-generation effect; it does not retain A until B's server response. No ordinary delayed-response bug is claimed from an artificial stream mock that behaves differently.
- **Project-switch side effects:** asynchronous add/remove completion and cross-project browser-history restoration merit combined real-stream navigation coverage. No additional stale-completion defect was established here. M17 owns authoritative browser synchronization/cache ordering; M21 owns terminal pool/attachment identity. This report does not duplicate those issues from composition alone.
- **Single-tab ownership:** inspected and tested the release-before-remount implementation. The synthetic FIFO lock/broadcast model is not acceptance testing of browser freezing, multiple OS windows or native Web Locks implementations.
- **Layout policy:** persistent shell tabs/minimization and dirty editor scopes during destructive project/task cleanup are already tracked in [todo.md](../todo.md). F03 concerns values that cannot affect the existing transient-layout policy; it does not decide those backlog policies.
- **Host integration overlap:** M13 owns host capability and RPC admission boundaries. F01 is the lost task scope across the current task toolbar contract, not an authorization bypass or a failure of native capability enforcement. No IDE, picker, shell, provider, app runtime or external service was launched.
- No visual clipping/responsiveness, measured performance, accessibility certification or native-platform claim is made. Small wrappers with coherent presentation/domain ownership were retained; no general abstraction was proposed solely to reduce line count.
