## Findings

### M04-F01 — P2 · Resource lifecycle/concurrency: failed startup leaves the previous bootstrap alive during port retry

- **Anchor:** [runtime-server.ts](../../src/server/runtime-server.ts), lines 652–658; callers at [cli.ts](../../src/cli.ts), lines 708–717 and 730–741.
- **Trigger:** Server binding fails after bootstrap, notably an `EADDRINUSE` race with automatic port selection; a later readiness-registration failure also occurs after binding.
- **Consequence:** The rejection has no rollback owner. Registry reconciliation, persistence subscriptions, runtime hub, automatic-title listener and terminal bridge remain allocated; native startup recovery has already been queued before server creation. Auto-port retry creates a second bootstrap while the first can still prepare/launch tasks or persist summaries. The abandoned managers are absent from the eventual server's shutdown scope. Actual duplicate provider execution was not run in this review.
- **Evidence:** `createRuntimeBootstrapState` awaits indexed hydration and queues recovery before `createRuntimeServerHandle`. `startServer`'s catch resets diagnostic sinks and fails diagnostics only. The server's cleanup closure is returned only after `listen` and `markReady` succeed. A focused test invoking the actual server composition with an HTTP-server stub injected `EADDRINUSE`; the terminal-bridge close, persistence close, hub close and title unsubscribe were all uncalled. M01 explicitly deferred this bootstrap question to M04.
- **Smallest remedy:** Give the complete bootstrap attempt one disposal owner from its first allocation, including registry managers/recovery, streaming, persistence, listeners and any bound socket. On failure, cancel and drain that attempt before retrying; register recovery only when the startup attempt has ownership of its serving endpoint where practical.
- **Validation needed:** Inject failure at bind and after bind, then exercise one auto-port retry. Verify old managers cannot launch, publish or write, allocated resources close exactly once, and the successful attempt has one manager/process owner per task. Use fake agents for any process-level test.

### M04-F02 — P2 · Correctness/shutdown: cleanup errors or a hung pre-scan bypass server close

- **Anchor:** [shutdown-coordinator.ts](../../src/server/shutdown-coordinator.ts), lines 167 and 218–224; pre-deadline state reads at lines 152 and 173.
- **Trigger:** Index reading or interrupted-session saving rejects; alternatively, a project-state read hangs before the cleanup timeout is constructed.
- **Consequence:** `closeRuntimeServer` never runs despite the stated cleanup guarantee. The normal CLI shutdown consequently skips the server's persistence drain, transports and diagnostics cleanup, and relies on process-level exit. A hung early project read also prevents later managers from receiving their stop request and prevents exact-owned orphan cleanup from starting before the hard shutdown deadline.
- **Evidence:** The timeout covers only the final quiescence/save block. `Promise.race` propagates a rejected save instead of proceeding to close, and the index read is outside a catch/finally. An exact-source harness separately injected index rejection and save rejection: both rejected with zero close calls. With a never-resolving managed-project read, no timeout was even armed. Existing tests cover a hung save and hung quiescence, which occur after this uncovered pre-scan.
- **Smallest remedy:** Signal all managed sessions before awaiting project I/O, establish one deadline around the whole cleanup phase, and put server close in a guaranteed finalization path. Collect cleanup failures for reporting without skipping other owners, and clear the deadline timer when finished.
- **Validation needed:** Add index-error, save-error and hung-project-read cases. Assert every manager receives stop, close executes once within the cleanup budget, persistence errors remain reported, and no deadline timer survives successful shutdown.

### M04-F03 — P2 · Correctness/concurrency: overlapping selection installs another project's launch configuration

- **Anchor:** [project-registry.ts](../../src/server/project-registry.ts), lines 408–414; cached read at lines 386–390.
- **Trigger:** Project A starts loading its config, selection switches to B, B's load completes, then A's older load completes. Even one switch exposes the new active ID while its config is still loading.
- **Consequence:** The registry can report active project B while `loadScopedRuntimeConfig(B)` returns A's config indefinitely. Task preparation consumes that result, including the project-specific worktree setup script and system prompt; a task in B can run A's setup policy. This is distinct from M01's durable global-settings lost-update race.
- **Evidence:** Active ID/path are assigned before the await, but config is assigned unconditionally afterward, with no identity/generation guard. Runtime stream connections can select projects concurrently. An exact-source registry harness resolved B before A and observed active ID `b` with A's configuration returned for scope `b`. [task-session-start-service.ts](../../src/server/task-session-start-service.ts), lines 149 and 231, connects this cache directly to setup execution.
- **Smallest remedy:** Load configuration before atomically publishing the active project/config tuple, with a selection generation that discards stale completions. Keep scoped config resolution keyed by project, so launch correctness does not depend on a global presentation selection.
- **Validation needed:** Gate two selection loads and resolve them in both orders; also request B's config during its pending selection and clear/remove the active project during a load. No scoped consumer may receive another project's config.

### M04-F04 — P2 · Availability/input handling: malformed upgrade paths throw outside the request boundary

- **Anchor:** [runtime-server.ts](../../src/server/runtime-server.ts), lines 559–566; decoding at [assets.ts](../../src/server/assets.ts), lines 50–53.
- **Trigger:** An HTTP upgrade request passes the host/origin gate with a malformed encoded path such as `/%` or `/%E0%A4%A`.
- **Consequence:** `new URL` accepts the path, but `decodeURIComponent` throws `URIError` after the local try/catch ends. The synchronous HTTP upgrade listener propagates it out of the server event callback, terminating an ordinary Node process. No project or diagnostic token is required on this path; absent Origin is permitted by the middleware. This is not a claim that arbitrary cross-origin browser requests bypass its Origin gate.
- **Evidence:** A focused test used the actual runtime composition and middleware with a fake HTTP emitter, an allowed localhost Host and `/%`; emitting `upgrade` threw `URIError` and did not destroy the socket. Normal HTTP request decoding is inside its outer catch, whereas the upgrade decoder and terminal path predicates are not. No production uncaught-exception handler was found.
- **Smallest remedy:** Decode once inside the upgrade parsing boundary; on any malformed URL/path, reject/destroy the socket. Pass the validated pathname to route matching or make all path predicates fail closed.
- **Validation needed:** Send malformed percent encodings to runtime, terminal and unknown upgrade paths using a disposable HTTP-server test; each socket must close while a subsequent valid request succeeds. Preserve the existing host/origin restrictions.

### M04-F05 — P2 · Resource lifecycle/concurrency: project disposal does not retire pending or existing manager reconciliation

- **Anchor:** [project-registry.ts](../../src/server/project-registry.ts), lines 315–334 and 423–434.
- **Trigger:** A project is removed while `ensureTerminalManagerForProject` is awaiting persisted state. Ordinary removal of an already-created manager also leaves its reconciliation timer running.
- **Consequence:** Disposal sees no published manager and leaves its pending load intact; the later completion starts reconciliation, inserts the manager again and invokes the ready callback after the project path has been deleted. CLI callbacks can reattach persistence/stream listeners to this retired manager, and callers awaiting the original load receive an unstopped manager. For an already-published manager, deleting the map entry never calls `stopReconciliation`, so its interval retains the manager/store after removal.
- **Evidence:** An exact-source registry harness paused hydration, disposed the project, then released hydration. `getTerminalManagerForProject` again returned an unstopped, reconciling manager while `getProjectPathById` returned null. The load has no generation/tombstone check before publication; its `finally` unconditionally deletes the map entry. Both explicit API removal and unavailable-project reconciliation reach this disposal path. The execution-removal preparer only awaits managers for persisted ownership entries, so an empty ownership journal does not fence an independent pending hydration. Terminal `markInterruptedAndStopAll` does not stop the separate reconciliation timer.
- **Smallest remedy:** Fence manager loads with a per-project lifetime token and retire pending publication when disposing. Stop reconciliation on every discarded manager, including a late load, and only notify external owners for a current manager. Make pending-load cleanup conditional on the exact promise so a retired load cannot clear a newer one.
- **Validation needed:** Remove during a gated hydration and verify no manager or external listener is published; immediately re-add and ensure only the new lifetime survives. Verify ordinary removal clears the reconciliation timer. Exercise an in-flight task-start caller to ensure the retired manager cannot acquire a process afterward.

## Uncertain candidates and existing backlog

- [open-project.ts](../../src/server/open-project.ts), lines 177–180, uses the same SIGTERM-only timeout helper implicated by **M01-F05**. Its promise also waits for `close`, so a SIGTERM-ignoring POSIX launcher can leave Open Project pending past 60 seconds. This is an additional consumer of that existing termination defect, not a new M04 finding; native host launch was not executed.
- Merged main resolved **M03-F01/F03** through journaled transactions and locked snapshots; their original evidence remains in M03's reconciliation. **M03-F02** retains the still-present older-session-capture race, and **M03-F04** retains corrupt lifecycle-journal recovery ownership. These are separate from M04's startup, shutdown and registry findings.
- Startup lifecycle compensation and structured-owner recovery occur in server assembly after the CLI has queued native recovery. The precise interleaving for a valid pending lifecycle operation remains a question for M05/M09; this pass did not establish a distinct failure beyond F01.
- Startup launch spacing, frozen preparation, exact-session retry, live-unconfirmed handling and generation-based persistence have concrete contracts and focused tests. No justified simplification or measured performance regression was established. None of the five new findings appears in the active [todo list](../todo.md).
