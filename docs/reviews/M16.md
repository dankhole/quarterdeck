## Findings

### M16-F01 — P2 · Correctness/compatibility: the history reader rejects every currently supported native Codex version

- **Anchor:** [codex-history-parser.ts](../../src/conversation/codex-history-parser.ts), lines 17–21 and 49–55; rejection at 71–72.
- **Trigger:** A task launched with a supported native Codex release writes a transcript header declaring that release, then the user requests title regeneration. Native launch admission requires at least `0.157.0` in [agent-registry.ts](../../src/config/agent-registry.ts), line 72, while the history reader accepts only `0.142.5` through `0.149.1`, plus exactly `0.153.4`.
- **Impact:** The reader always returns `unsupported/format_unsupported` for such new transcripts, before projecting their messages. Explicit title regeneration silently falls back to stored assistant summaries/final text or the original task prompt, losing the recent user corrections it is meant to prioritize. With no completed summary yet, an evolved conversation is sent to initial-title generation using only its original request.
- **Evidence:** [runtime-server.ts](../../src/server/runtime-server.ts), lines 158–161, installs this reader for desktop use; this is not merely the independent structured-execution gate. [codex-conversation-adapter.ts](../../src/conversation/codex-conversation-adapter.ts), lines 66–77, rejects the header. [task-title-service.ts](../../src/server/task-title-service.ts), lines 36–62, consumes the empty entries and selects the fallback. Two synthetic checks used the real filesystem reader and title service, with identical paginated records differing only in `cli_version`: `0.153.4` returned the recent user direction and selected `followup`; `0.157.0` returned no messages and selected `initial`. The test stubbed generation and board publication, not parsing or context selection.
- **Qualification:** This demonstrates a supported-launch/history compatibility gap, not proof that all newer native schemas are safe to parse. Existing tests deliberately reject unvalidated releases, and the older allowlist remains useful for persisted histories. No current watchlist item explains the desktop gap; the structured exact-version limitation discussed in M09 is a different contract.
- **Smallest remedy:** Validate and admit the native release(s) the launcher supports, updating provider-record fixtures and the compatibility contract together. Until that validation is available, make the reduced-context result explicit to the regeneration caller; do not simply remove the defensive version gate.
- **Validation needed:** A synthetic transcript derived from an authorized compatibility run at the native minimum, covering user turns, injected context, commentary/final output, compaction and rollback; a reader-to-title-service assertion retaining recent user direction. Continue rejecting unvalidated schemas and reading older supported files.

### M16-F02 — P2 · Correctness/concurrency: summary polishing claims its single-flight slot after asynchronous setup

- **Anchor:** [display-summary-polish.ts](../../src/trpc/display-summary-polish.ts), lines 113–138.
- **Trigger:** Two polish requests for the same project/task arrive before the first finishes obtaining the terminal manager or loading project state. Both test `polishGenerationInFlight.has(...)` before either adds the key.
- **Impact:** Both requests launch model generation and publish their answers; completion order decides which wording remains. This spends duplicate generation work for one source. The first completion also removes the shared key while the other operation is still active, allowing further requests to bypass the intended coalescing policy.
- **Evidence:** The admission check is followed by awaits at lines 119 and 126; the claim is not made until line 138. Hook transitions/metadata and task-start completion both schedule this path in [hooks-api.ts](../../src/trpc/hooks-api.ts), lines 277–286, and [start-task-session.ts](../../src/trpc/handlers/start-task-session.ts), lines 97–104. A synthetic check gated manager acquisition for two calls and used the real polish function and `InMemorySessionSummaryStore`. Both reached the deferred generator, both called `setDisplaySummary`, and the second result replaced the first. The source fingerprint remained unchanged, so the existing stale-source check correctly did not prevent this admission race.
- **Smallest remedy:** Claim the key synchronously immediately after the admission check, then put all remaining setup, early returns and generation inside the existing `try/finally`. Preserve the latest pending request and ensure only the owning operation releases its claim.
- **Validation needed:** Overlap calls during manager lookup and board loading, asserting one generation and at most one queued follow-up. Exercise setup failure, empty source and disabled configuration so no claim leaks. Keep the existing test for newer source arriving during an already-claimed generation.

### M16-F03 — P2 · Resource usage/concurrency: separate title events bypass the three-request limit

- **Anchor:** [automatic-task-title-scheduler.ts](../../src/server/automatic-task-title-scheduler.ts), lines 113–118; intended request limit at line 9.
- **Trigger:** Multiple create-task commands or batches commit while automatic titles for previous non-Codex tasks are still being generated.
- **Impact:** Each event starts a separate detached batch loop. The limit of three applies inside one event only; total active generation grows with concurrent events. With the default saved-Codex helper policy this can start an unbounded number of helper processes/provider turns during a burst of task creation, despite the local limit.
- **Evidence:** The real post-commit publisher in [project-board-command-service.ts](../../src/state/project-board-command-service.ts), lines 264–275, does not wait for title work, and the title listener itself returns immediately. [automatic-title-generation-coordinator.ts](../../src/title/automatic-title-generation-coordinator.ts) deduplicates only the same project/task. A synthetic check delivered two events with three distinct Claude tasks each to the real listener/coordinator and blocked generation completion: **six generators were simultaneously active**. [generation-helper.ts](../../src/title/generation-helper.ts), lines 18–25, calls Codex before the gateway; only the gateway in [llm-client.ts](../../src/title/llm-client.ts) has a global rate/concurrency limiter. The lower-level Codex client has no equivalent admission owner. Tasks whose selected agent is Codex use a local placeholder and do not incur this cost.
- **Smallest remedy:** Put the concurrency budget in a shared scheduler/limiter used by all automatic-title events, alongside the existing per-task deduplication. Keep post-commit delivery nonblocking; queue generation under one runtime-owned budget rather than creating independent event budgets.
- **Validation needed:** Interleave several single-task and multi-task events, including different projects and duplicate deliveries, and assert peak active generation never exceeds the shared limit. Release/reject blocked calls and verify queued work advances without losing or duplicating titles.
- **Measurement limit:** The check measured six concurrent generator invocations against a configured batch size of three. It did not run providers or measure memory, latency, billed tokens or a host overload.

### M16-F04 — P2 · Privacy/logging: rejected model responses are printed to the default warning console

- **Anchor:** [llm-client.ts](../../src/title/llm-client.ts), lines 213–219; [codex-client.ts](../../src/title/codex-client.ts), lines 201–207.
- **Trigger:** A helper returns a question/refusal containing supplied task, conversation or change context, causing `sanitizeGenerationResponse` to reject it. A gateway error body that echoes request content also reaches the neighboring non-2xx path.
- **Impact:** The response text is sent to `log.warn`: the gateway includes the complete `rawContent`, and Codex includes up to 500 characters of stdout. The default runtime warning console therefore receives content even though the generated result is discarded. This violates the content-free warning/error policy in [diagnostics.md](../diagnostics.md), line 17; it can expose task or source text in terminal/service logs.
- **Evidence:** [runtime-logger.ts](../../src/core/runtime-logger.ts), lines 41 and 81–85, defaults to warning level and passes logger data unchanged to the console. Two synthetic checks invoked the real clients with a mocked HTTP response or injected executor returning a refusal containing a synthetic marker. Both returned `null`, and both printed that marker through the default `console.warn` path. No real task content, endpoint, credential or provider was used. The gateway's `bodySnippet` path at lines 175–189 similarly retains arbitrary response text by source inspection.
- **Qualification:** The canonical production diagnostic recorder reduces logger data to metadata; this finding does **not** claim these fields enter its journal or support bundles. Debug/info prompt and successful-result logging are not the basis of this default-warning finding. M15 owns a separate direct stderr leak on journal failure.
- **Smallest remedy:** Replace rejected-output/error-body text in production warning payloads with bounded classification and size metadata. Keep any rich synthetic output behind the Agent Lab evidence policy; preserve useful status, duration and validated error-class fields.
- **Validation needed:** Feed synthetic task-content markers through rejection and non-2xx responses for both providers, then assert their absence from default warning/error console output as well as canonical diagnostics. Include a long response to verify logging is bounded.

## Uncertain candidates and overlap

- The read service fixes provider roots from the runtime environment, whereas native ownership and the Codex title monitor retain launch-profile identity. A profile mismatch could make history unavailable after an internal handoff, but ordinary desktop start preparation supplies the same process environment; no independent normal-flow mismatch was established. Do not widen history-root access speculatively.
- The manual `generateDisplaySummary` RPC in [project-procedures.ts](../../src/trpc/project-procedures.ts), lines 330–400, has a separate task-ID-only in-flight set and no post-generation source comparison. M13 handed this adjacent concern to M16. There is no current browser call site for that RPC, and this review did not reproduce an external caller/replacement-session interleaving. It remains a candidate for consolidation with the guarded polish owner, not a counted desktop race.
- Claude reconstruction falls back to all records when the newest non-sidechain lineage record lacks `parentUuid`. That supports older formats, but a mixed-format trailing metadata record could weaken fork selection. No supported native record sequence demonstrating this was established; existing active-chain, broken-chain and cyclic-lineage tests remain meaningful.
- The helper's fixed 20-second Codex deadline differs from the smaller gateway options. Current provider-policy tests intentionally expect that override; it is not reported as a defect. The shared SIGTERM-only timeout issue is already owned by M01-F05; the helper settles its promise separately, so this report does not copy the availability-probe claim.
- M03 owns stale session snapshots persisted by unrelated board/title writes; M04 owns title-listener cleanup on failed bootstrap. Those are distinct from F02/F03 admission and capacity problems. M09's pinned structured protocol gate is distinct from F01's native desktop reader gap. M02 owns shared console dispatch; F04 concerns unsafe fields emitted by these specific producers.
- No finding above is an active item in [todo.md](../todo.md). No additional measured performance regression or actionable architectural cleanup was established. Bounded scanning, source validation and reconstruction are substantial domain logic, not complexity findings by themselves.
