## Findings

### M15-F01 — P2 · Correctness/admission: essential browser events are acknowledged and discarded

- **Anchor:** [browser-diagnostics.ts](../../web-ui/src/diagnostics/browser-diagnostics.ts), lines 315–326; [recorder.ts](../../src/diagnostics/recorder.ts), lines 251–263 and 364–382. The wire schema is [diagnostics.ts](../../src/core/api/diagnostics.ts), lines 69–78, and server admission is [recording-policy.ts](../../src/diagnostics/recording-policy.ts), lines 32–37.
- **Trigger:** With ordinary flight recording active, the browser emits an informational event marked `essential: true`, such as startup, connection, reconnect attempts or authoritative project hydration.
- **Consequence:** Client admission accepts the event, but the candidate omits the essential flag. Server ingestion treats only warning/error candidates as essential, drops the informational event, and still advances `highestAcceptedSequence`. The browser removes the acknowledged event from its pending queue. Always-on evidence therefore disappears permanently, and the doctor cannot detect a reconnect loop from those attempts unless deep recording was already enabled. This contradicts the requirement that useful flight evidence exist before asking a user to reproduce.
- **Evidence:** A synthetic test connected the actual browser queue and `flushBrowserDiagnostics()` to the actual `DiagnosticRecorder.ingestBrowserRecords()` through a fetch response shim. `initializeBrowserDiagnostics()` plus five calls to `noteBrowserRuntimeReconnect()` sent six candidates; the server retained zero and the browser queue became empty. Enabling server deep recording for the control retained the next five reconnect attempts and produced `RUNTIME_STREAM_RECONNECT_LOOP`. The doctor requires those named events at [doctor.ts](../../src/diagnostics/doctor.ts), lines 639–653. Other real producers include [use-project-sync.ts](../../web-ui/src/hooks/project/use-project-sync.ts), lines 220–224 and 292–301. Existing browser tests mock successful acknowledgement, while the existing server ingestion test enables deep recording before sending informational candidates; neither crosses this admission boundary.
- **Smallest remedy:** Preserve essential admission through a bounded typed browser contract, or derive it from a shared allowlist of essential browser event names on the server. Keep the client and server policy consistent without admitting every informational event. Continue acknowledging intentionally filtered records only after that policy decision is correct.
- **Validation needed:** Keep a browser-to-recorder flight test covering startup, connection/reconnect and hydration, assert retention after acknowledgement and capture, and assert reconnect-loop diagnosis without deep recording. Keep controls for nonessential informational events and scoped deep admission.

### M15-F02 — P2 · Privacy/error handling: journal failures print private paths to stderr

- **Anchor:** [recorder.ts](../../src/diagnostics/recorder.ts), lines 347–362, specifically the raw `error.message` at line 362. Production initialization routes real filesystem failures here in [runtime-diagnostics.ts](../../src/diagnostics/runtime-diagnostics.ts), lines 104–118.
- **Trigger:** The diagnostic state/journal directory cannot be created or appended, for example because the configured state-home path is a file, permissions deny access or storage fails.
- **Consequence:** The canonical health record contains a safe failure class, but its companion fallback warning writes the first 500 characters of the original filesystem error message directly to stderr. Real filesystem errors include the private absolute state path, so the degradation path bypasses path redaction and the content-free warning/error contract. Capturing ordinary process stderr can expose private directory names even though the journal and bundle remain sanitized.
- **Evidence:** A test supplied a real file as `stateHome`, with a synthetic private-name sentinel in its pathname, and called `createRuntimeDiagnostics()`. The actual `ENOTDIR` failure put that sentinel in the `diagnostic journal degraded` stderr warning. Canonical records contained only error classes and did not contain the sentinel. The neighboring descriptor persistence fallback already uses a validated error class. No actual secret or user data was used or observed.
- **Smallest remedy:** Use `getDiagnosticErrorClass(error)` in the fallback warning, as in the health record and descriptor fallback. Keep the rate limit and nonrecursive stderr fallback; do not introduce a second content-bearing diagnostic channel.
- **Validation needed:** Assert the absence of path/content sentinels from both stderr and canonical records for initialization and append failures, while retaining the error class and degraded-health signal. Preserve native Windows ACL failure behavior without printing raw command output.

### M15-F03 — P2 · Correctness/persistence: retrying a partial append corrupts the replay boundary

- **Anchor:** [journal.ts](../../src/diagnostics/journal.ts), lines 232–248 and 286–291. Invalid-line recovery is at lines 349–366.
- **Trigger:** An append writes a prefix ending inside a JSON record and then fails, such as an interrupted or exhausted-storage write. The journal requeues the entire batch and later retries successfully against the same segment.
- **Consequence:** The retry appends the first complete replayed record immediately after the unterminated fragment. Both become one malformed JSONL line, so the reader skips the first replayed record. The journal then reports healthy with an empty pending queue even though that evidence was not durably recovered. The in-memory tail can temporarily rescue a live capture, but offline capture or a later capture after eviction loses it. Deduplicating record IDs only helps complete duplicate lines; it cannot repair this framing error.
- **Evidence:** A controlled filesystem fault wrote the first 80 bytes of a real two-record append and then rejected it with synthetic `ENOSPC`. The first flush reported unhealthy with two pending records. After the fault was removed, the actual retry reported healthy with zero pending records; `readDiagnosticJournal()` returned only sequence 2 and warned that the line containing sequence 1 was skipped. The fixture used real segment files and the actual append/retry/reader implementation. This proves recovery behavior under the injected partial-write condition, not the incidence of partial writes on a particular filesystem. Existing tests cover a crash tail with no subsequent writer and recovery from a failure before any bytes were written.
- **Smallest remedy:** Before retrying a segment whose append failed, restore a known complete-line boundary or abandon that segment and replay into a fresh one. Keep segment byte/record accounting consistent with the recovered files and retain bounded rotation. Do not rely solely on whole-record ID deduplication.
- **Validation needed:** Inject failures before any bytes, inside the first record, after a complete record plus a fragment, and across segment rotation. After recovery and memory-tail removal, require every retained canonical ID exactly once from the journal, valid segment boundaries, bounded files and accurate health/accounting.

### M15-F04 — P2 · Correctness/runtime identity: a stale refresh restores another runtime's diagnostics

- **Anchor:** [browser-diagnostics.ts](../../web-ui/src/diagnostics/browser-diagnostics.ts), lines 420–425. Runtime replacement clears the old data at lines 355–365; the adjacent subscription request correctly fences capability/runtime identity at lines 428–445.
- **Trigger:** A panel refresh sent to runtime A remains unresolved while the browser processes a `diagnostics_state` message for replacement runtime B. A's already-issued response then resolves.
- **Consequence:** `refreshBrowserDiagnosticData()` unconditionally merges A's records into B's canonical timeline and installs A's descriptor, health, snapshots and findings as `remoteData`. The panel can display B's connection identity alongside A's health and doctor conclusions. Those old records persist until another runtime replacement or eviction; a normal refresh merges rather than replaces them. This undermines diagnostic attribution during the restart/reconnection incidents the panel is intended to explain.
- **Evidence:** A controlled fetch response held A's valid status result, delivered B's real stream-state handler first, then released A. The actual browser store ended with `runtimeInstanceId = runtime-B`, `remoteData.descriptor.runtimeInstanceId = runtime-A` and timeline ID `runtime-A:99`. [use-diagnostics.ts](../../web-ui/src/hooks/diagnostics/use-diagnostics.ts), lines 142–153 and 200–203, invokes this refresh path; [diagnostics-inspection.tsx](../../web-ui/src/components/diagnostics/diagnostics-inspection.tsx), lines 26–80, renders live identity and remote health/findings together. The controlled test establishes the exposed ordering; no real browser restart timing was measured.
- **Smallest remedy:** Capture runtime identity and capability before issuing the refresh and reject/ignore a response once either changes. Also require the returned descriptor/snapshot to belong to that captured runtime, following the adjacent subscription fence. Apply equivalent ownership checks to other asynchronous diagnostic state setters where appropriate.
- **Validation needed:** Cover A-request/B-state/A-response, capability replacement, disconnect before response, and concurrent refresh ordering. Assert that stale results change neither remote data nor canonical timeline while current responses still hydrate the panel.

## Uncertainty, overlap and existing backlog

- The accepted-socket error-handler failure already belongs to [M07-F02](./M07.md#m07-f02--p2--availabilitysocket-handling-malformed-terminal-frames-terminate-the-runtime). Diagnostic stream fanout uses that shared transport; this report adds no duplicate socket finding.
- Generic production `recordLog()` admission is content-safe even for arbitrary LLM data: it retains message length and a data summary. Producer-side raw console logging is being evaluated by M16, with the shared logger in M02; F02 is a separate direct stderr emission and does not claim that generic logger data enters production bundles.
- Snapshot responses can update the cached client snapshot independently of whether their nonce matches the current pending request. A separate stale-response consequence was not reproduced here and is not counted as a finding. Native filesystem/ACL behavior beyond the tested POSIX fixtures and mocked Windows ACL command boundary remains unverified.
- The active todo's first-open latency investigation and the Windows manual privacy/real-provider validation matrix are existing work, not evidence for additional findings. No measured performance regression, real-provider compatibility result or complete privacy certification is claimed.
