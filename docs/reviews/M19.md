## Findings

### M19-F01 — P2 · Correctness/ordering: same-column drops reorder the wrong stored indexes

**Anchor:** [board-state.ts](../../web-ui/src/state/board-state.ts), lines 252–259; display projection in [board-column.tsx](../../web-ui/src/components/board/board-column.tsx), lines 149–189.

The column assigns drag indexes after sorting started/pinned cards and excluding the inline editor. `applyDragResult` applies those indexes directly to the original stored array for same-column moves, ignoring `draggableId`. The cross-column path already locates the source by identity, but the same-column path does not. A valid user drag therefore moves another card or appears ineffective, and its resulting wrong order is eligible for the normal durable `reorder_column` command.

**Evidence:** a synthetic check rendered the actual `BoardColumn` with only DnD/render leaves substituted, then passed its indexes through the actual domain reducer. Stored `[A,B,C,S]`, where S is started and A/B/C are unstarted, renders `[S,A,B,C]`. Dragging A from index 1 below C at index 3 produced stored `[A,C,S,B]` and displayed `[S,A,C,B]`, rather than `[S,B,C,A]`. A second check edited B inline in `[A,B,C,D]`: C receives draggable index 1; dropping it at 2 instead moves B and leaves the visible draggable order `[A,C,D]` unchanged. The [sort policy](../../web-ui/src/state/sort-column-cards.ts) and [command diff](../../web-ui/src/hooks/project/project-board-command-sync.ts), lines 164–174, preserve the causal mismatch. Canonical runtime dependency normalization does not sort it away.

**Remedy:** derive moves by task identity and translate the destination through the exact draggable projection, including non-draggable editors and fixed started/pinned groups. Define which groups permit manual ordering and keep the renderer and command construction consistent. Merely replacing the source index with `findIndex` leaves the destination mismatch.

**Validation needed:** actual column projection plus reducer/command tests for mixed started/unstarted cards, pinning, inline editing and unchanged-order drops. No browser drag animation or visual layout was tested here.

### M19-F02 — P2 · Correctness/intent: a pending lifecycle command absorbs a different action

**Anchor:** [use-task-lifecycle-operations.ts](../../web-ui/src/hooks/board/use-task-lifecycle-operations.ts), lines 159–164; [task-lifecycle-operations.ts](../../web-ui/src/hooks/board/task-lifecycle-operations.ts), lines 21–23.

Single-flight admission keys only on project and task. Any second command for that task receives the first promise, regardless of operation kind, creation identity or parameters. During a slow Start/Restart, a user can confirm Trash through the card action: that action is disabled only by its own Trash loading flag, not the pending lifecycle operation. No Trash command reaches the server, yet its caller receives `ok: true` from Start and treats it as a successful Trash outcome. The task can remain running despite the accepted user gesture.

**Evidence:** a mounted real lifecycle hook sent Start through a deferred transport, then received Trash for the same task. Releasing a successful Start produced one RPC total, and the Trash caller received an `ok: true` result with `operation.kind = start`, with no error notification. [board-card-actions.tsx](../../web-ui/src/components/board/board-card-actions.tsx), lines 124–142, admits the running-task action; [use-linked-backlog-task-actions.ts](../../web-ui/src/hooks/board/use-linked-backlog-task-actions.ts), lines 130–136, tests only `result.ok`. Existing tests validate identical duplicate gestures, not incompatible intents.

**Remedy:** coalesce only identical intent identities. Return an explicit busy result or serialize a distinct command with fresh authoritative revision/identity after the first completes. Surface pending-state admission consistently, and never report success for a different requested action. Preserve same-operation retries and server lifecycle ownership.

**Validation needed:** overlapping Start/Trash, Restart/Trash and Restore/Delete, plus identical retries and replacement creation identity. Assert both the sent commands and the operation kind returned to each caller.

### M19-F03 — P2 · Correctness/project ownership: resetting animations releases queued Trash work into the new project

**Anchor:** [use-programmatic-card-moves.ts](../../web-ui/src/hooks/board/use-programmatic-card-moves.ts), lines 173–184 and 223–231; caller reset at [use-board-interactions.ts](../../web-ui/src/hooks/board/use-board-interactions.ts), lines 244–249.

A confirmed Trash animation blocked by another animation awaits availability, then recursively retries. Project reset resolves that availability promise as though the slot became available; it does not cancel or generation-fence the waiting intent. The recursive call reads the replacement Trash handler. If the newly selected project contains the same task ID, it can issue Trash for that project's task using its current creation identity and the old project's already-confirmed `skipWorkingChangeWarning` flag. The old user's confirmation is thereby transferred to another task scope.

**Evidence:** a controlled React test composed the real programmatic-move hook and real linked-task actions, including the parent's handler-registration-before-reset effect order. A blocked request for `shared-task` in A was followed by B with a same-ID card created at 99. Reset resumed the old request, and the resulting lifecycle draft was `{kind: trash, taskId: shared-task, taskCreatedAt: 99, sourceColumnId: review}` through B's executor. No A command was sent. The animation sensor and final lifecycle transport were controlled; no real worktree or process was affected. The initial smaller handler-swap reproduction was replaced by this composed check.

**Qualification:** cross-project damage requires the same task ID in both projects and navigation while waiting. Task IDs are scoped by project elsewhere; uniqueness is not guaranteed globally. With no matching B task, the linked action returns without a command. The confirmed skip flag is a real path from [use-trash-workflow.ts](../../web-ui/src/hooks/board/use-trash-workflow.ts), lines 292–302. This is distinct from server-side lifecycle compensation findings in M05 and global worktree path collisions in M10.

**Remedy:** distinguish cancellation/reset from availability, capture project/task creation identity for each pending intent, and revalidate after every wait. Cancel queued starts/trash moves on project change/unmount rather than resolving them into retry loops. Keep successful animation completion separate from command success.

**Validation needed:** project change and unmount while blocked, matching/nonmatching task IDs, already-confirmed warnings, replacement creation identities and ordinary same-project animation completion.

### M19-F04 — P2 · Correctness/input ownership: a delayed shortcut submits a replacement project's terminal

**Anchor:** [use-prompt-shortcuts.ts](../../web-ui/src/hooks/board/use-prompt-shortcuts.ts), lines 63–85; [use-task-sessions.ts](../../web-ui/src/hooks/board/use-task-sessions.ts), lines 80–95.

Prompt shortcuts paste text, wait 200 milliseconds, then submit through a retained callback. Each send resolves the current terminal controller by task ID, without checking the hook's active-project fence or preserving the original session/controller identity. If a project switch replaces that controller with a same-ID task's controller during the delay, the carriage return goes to the new terminal even though the prompt was pasted into the old one. It can submit unrelated pending text or a prompt there.

**Evidence:** a composed test used the actual shortcut hook, task-session hook and [controller registry](../../web-ui/src/terminal/terminal-controller-registry.ts). It pasted `/commit` into A, unregistered A normally, rerendered the hooks for B and registered B's same-ID controller. Advancing the timer sent exactly one carriage return to B, with no paste to B and no submit to A. Controller I/O was synthetic; the RPC fallback was configured to fail if used and was not used. Thus normal old-controller cleanup does not prevent this race. Existing input tests fence late summary updates, not the target of a later retained send. The review-comment Send action has the same paste/wait/submit sequence in [use-card-detail-view.ts](../../web-ui/src/hooks/board/use-card-detail-view.ts), lines 208–238; that additional caller was source-traced by M20, not separately reproduced.

**Remedy:** bind paste-and-submit to project, task and launch/controller identity. Revalidate that ownership after the delay and before all input delivery; cancel rather than resolve a different controller. Apply the same identity check to the terminal fast path and RPC fallback, preserving the provider-neutral submit intent.

**Validation needed:** navigation to same-ID and different-ID tasks, controller replacement/restart, unmount and terminal-to-RPC fallback between paste and submit. The same-project replacement-session variant follows from the lookup policy but was not separately executed.

## Uncertainty and overlap

- Creation draft preservation belongs to M20. M17 owns authoritative queue/cache/config races; this report owns the interaction-side intent/projection errors preceding those boundaries. M21 owns pool/transport cleanup; F04 is the higher-level delayed shortcut delivery across otherwise normal controller replacement.
- Dependency layout repeatedly measures all task elements during motion and receives broad subtree mutation notifications. No representative profile or measured bottleneck was obtained; this is not counted as a performance finding. Pointer-driven SVG controls were not given an accessibility or visual acceptance pass.
- Optimistic presentation on a lifecycle preflight failure merits a composed synchronization check; a standalone mocked flush failure is insufficient because real command recovery may already replace presentation. No additional finding is counted.
- Existing todo items around dirty draft cleanup, first-open latency and terminal/task interaction policy remain their own work. No general hook-size complaint, unnecessary wrapper extraction or naming-only cleanup was justified. The legacy “backlog” names reflect the recently merged Review migration and are not bugs by themselves.

Controlled React/jsdom schedules demonstrate the stated ownership decisions; they do not measure real-world incidence or certify all UI behavior.
