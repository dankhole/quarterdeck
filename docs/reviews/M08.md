## Findings

### M08-F01 — P2 · Correctness/replay: outbox replay discards persistent Codex session navigation

- **Anchor:** [hook-transition-outbox.ts](../../src/hook-transition-outbox.ts), lines 49–65 and 95–98. The affected consumer is [hook-event-order.ts](../../src/terminal/hook-event-order.ts), lines 530–542.
- **Trigger:** An established native Codex session navigates to a different persistent conversation, and its reliable `SessionStart` must be delivered from the outbox because the direct attempts did not apply it.
- **Consequence:** `minimalReplayMetadata` removes `transcriptPath` without retaining its presence. The ordering guard distinguishes persistent navigation from ephemeral side threads using that presence, so it rejects the replay as `non_foreground_session`. Ingest acknowledges the rejection as successful delivery, allowing the outbox to remove it. The old `resumeSessionId` remains authoritative and subsequent work/completion hooks from the new foreground conversation are also rejected. The runtime can remain stuck at the old task meaning and retain the wrong recovery target.
- **Evidence:** A synthetic check used the real `createHooksApi` and `TerminalSessionManager`, with only launch preparation and PTY creation stubbed. After accepting session `main`, a newer `SessionStart` for `new-main` with a synthetic transcript path passed ordering. The exact request returned by `createPersistedHookTransition` failed ordering, its ingest returned `{ok:true}`, the stored resume ID remained `main`, and the next `UserPromptSubmit` from `new-main` failed with `non_foreground_session`. Existing outbox tests check that SessionStart is queued, but do not replay a changed foreground identity. Durable ordering receipts already preserve the content-free `sessionStartHasTranscript` boolean; the outbox does not.
- **Smallest remedy:** Preserve explicit content-free persistent-session evidence in the outbox schema and reconstruct the same input semantics for ordering and the transition reducer. Keep actual transcript paths out of durable replay content. Do not weaken the side-thread fence.
- **Validation needed:** Replay persistent `/clear`/`/resume` navigation after failed direct delivery; verify identity transfer, retirement of the old interaction and subsequent work acceptance. Include an ephemeral SessionStart without a transcript, stale navigation and duplicate replay as negative cases.

### M08-F02 — P2 · Input authorization: transcript text can trigger Codex trust confirmation

- **Anchor:** [session-workspace-trust.ts](../../src/terminal/session-workspace-trust.ts), lines 52–78 and 85–93; [codex-workspace-trust.ts](../../src/terminal/codex-workspace-trust.ts), lines 58–76.
- **Trigger:** Any later terminal output contains the ordered words of the Codex trust question—for example, documentation quoting “Do you trust the contents of this directory?” or a command containing that string. Detection remains enabled after native work begins and after earlier trust confirmations.
- **Consequence:** The rolling raw-output buffer treats the text as a trust dialog and schedules an unconditional carriage return 100 ms later. There is no rendered dialog, selected-choice or current-screen recheck. This sends input to the provider without a user action; depending on the TUI at delivery time, it can submit composer text or confirm an unrelated selection. Actual approval acceptance was not exercised against Codex, so that consequence remains conditional on the provider's current UI.
- **Evidence:** A synthetic manager check established real current-launch native work through `hooks.ingest`, then delivered a plain narrative quotation through the real output pipeline. The fake PTY recorded exactly one `write("\r")` after 101 ms, despite there being no trust dialog. [session-output-pipeline.ts](../../src/terminal/session-output-pipeline.ts), lines 105–118, runs this detector for ordinary task output; transition handling only clears its buffer, rather than retiring it. The five-confirmation cap bounds repetition but does not authorize any individual key.
- **Smallest remedy:** Drive Codex trust from the rendered actionable trust dialog and its selected affirmative choice, bound it to the launch trust phase, and recheck the exact active process and current dialog before writing. Retire the trust driver once ordinary native work establishes that startup has finished.
- **Validation needed:** Narrative quotations, split historical output and commands containing the trust text must never write input. Preserve genuine trust confirmation, and cover a dialog disappearing or its selection changing during the delay, a replacement PTY and output during an unrelated approval wait. Validate the final dialog recognition against the supported Codex TUI only in an authorized provider lane.

### M08-F03 — P2 · Correctness/ordering: a parallel tool completion suppresses the awaited tool's completion

- **Anchor:** [hook-event-order.ts](../../src/terminal/hook-event-order.ts), lines 584–601 and 808–812.
- **Trigger:** Codex tool A has an exactly correlated permission wait. Tool B in the same turn has the same tool name. B's later `PostToolUse` is delivered before A's earlier completion—for example, A completed at time 40 and B at time 50, but A's hook delivery was delayed.
- **Consequence:** Ingest correctly refuses to let B resolve A's interaction, but retains B as ordering evidence. That commit stores its completion under `(turnId, toolName)`. A's exact `toolUseId` then loses to this name-level timestamp check before identity comparison: it is rejected as `completed_tool`. The provider has completed A, while Quarterdeck retains A's waiting or response-pending permission until another superseding event happens.
- **Evidence:** A synthetic check ran the actual ingest API, manager, correlation and reducer. It accepted `PreToolUse(A)` and a permission request correlated to A, followed by same-name B activity. B's completion at 50 was classified `unrelated_tool_completion` and retained by ingest. A's completion at 40 was then rejected as `completed_tool`; after both ingests, the stored interaction still had `toolUseId: "A"` and `status: "waiting"`. Existing tests cover an unrelated completion and reordered differently named tools separately, but not this same-name combination. The behavior also matters when ordered observations are rebuilt, since the durable receipt reuses the same reducer.
- **Smallest remedy:** Track identity-bearing completion deduplication by the exact tool-use ID within its turn. Keep conservative name-only ordering for payloads that lack identity, but do not let a different known tool's completion invalidate an exact match for the outstanding interaction.
- **Validation needed:** Exercise same-name parallel completions in both delivery orders through ingest and receipt restoration. Prove A's exact completion resolves A, B's completion cannot resolve A, duplicates stay rejected, and genuinely ambiguous permission requests remain fail-closed.

### M08-F04 — P3 · Correctness/display: a discharging Mac battery is shown as charging

- **Anchor:** [statusline.ts](../../src/commands/statusline.ts), line 260.
- **Trigger:** `pmset -g batt` reports `Battery Power` with a `discharging` battery status.
- **Consequence:** `result.includes("charging")` also matches `discharging`. The statusline renders the charging icon and green coloring, including at low charge, rather than the battery-level icon and warning color.
- **Evidence:** Executed the exact `getMacBattery` helper after Node TypeScript stripping, substituting synthetic `pmset` output containing `20%; discharging`. It returned `{percent:20, charging:true}`. `formatBattery` takes its charging branch before considering the percentage. Existing statusline tests validate the input schema but not battery parsing.
- **Smallest remedy:** Parse the battery status token or require a complete `charging` word instead of matching a substring. Preserve the intended treatment of AC power.
- **Validation needed:** Parser cases for discharging, charging and charged/AC output, plus the low-battery display selection. This does not require a provider or runtime test.
