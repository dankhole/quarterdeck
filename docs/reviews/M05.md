## Findings

### M05-F01 — P2 · Correctness/compensation: failed Trash permanently removes task dependencies

- **Anchor:** [project-task-lifecycle-service.ts](../../src/server/project-task-lifecycle-service.ts), lines 550–586 and 1062–1109. Related canonical mutation: [task-board-mutations.ts](../../src/core/task-board-mutations.ts), lines 188–213, 242–292 and 564–577.
- **Trigger:** A started Review task has a linked unstarted task. Trash commits its board move, then stopping the task or detail shell fails or times out.
- **Consequence:** Compensation returns the parent to Review, but the failed action has permanently removed its dependency links. A later successful Trash cannot rediscover those children for automatic start. The original `workingDirectory` is also cleared by the forward move and is not restored by compensation; subsequent session projection may repair that path, but does not restore dependency edges.
- **Evidence:** A focused test used the real board command service, lifecycle service, operation journal and filesystem state, with only process stopping stubbed to time out. Before Trash the board had one dependency. The result correctly reported `stop_timed_out` and returned the parent to Review, but both the returned and durable board had no dependencies. Canonical dependency normalization deliberately drops edges touching Trash; `compensateMove` only emits another `move_task`. The journal retains child IDs, not the removed dependency records or original workspace metadata. This reproduces on the post-merge explicit-unstarted model.
- **Smallest remedy:** Journal the board metadata that this transition destroys, then restore still-valid dependency identities and workspace metadata through the board command owner as part of guarded compensation. Preserve concurrent edits and the existing identity/revision checks; do not replace the entire board from the pre-operation snapshot.
- **Validation needed:** Extend the stop-timeout case to assert the original dependency IDs and workspace identity survive compensation, then retry Trash and verify the linked child starts once. Cover a detail-shell stop failure and a concurrent edit that must not be overwritten. The analogous failed Start path also warrants a dependency-preservation assertion.

### M05-F02 — P2 · Correctness/recovery: recovery archives a task after its Trash move was already compensated

- **Anchor:** [project-task-lifecycle-service.ts](../../src/server/project-task-lifecycle-service.ts), lines 525–599, particularly the phase overwrite at 546 and unconditional effects after receipt replay at 570–599.
- **Trigger:** Trash cannot stop its process, commits its compensation back to Review, and the runtime exits before the lifecycle operation is finalized. The durable lifecycle operation remains `pending`/`compensating`; its original Trash move and compensation both have board-command receipts.
- **Consequence:** Startup recovery restarts `executeTrash` from its first step. The original move receipt returns `acceptedChange: true` with the current board, which already has the card back in Review. Recovery stops the task/detail shell, archives the worktree, and records successful Trash even though the card remains in Review. A recovered process can therefore be stopped and its launch folder removed after the earlier failed Trash was visibly reversed.
- **Evidence:** A focused persistence-backed test seeded the precise two committed board commands and pending compensation phase, then invoked the real `recover`. It observed two stop calls, one archive call, a successful terminal operation, and a card still in Review. Worktree deletion itself was stubbed; the test proves the erroneous effect admission. `executeTrash` validates task identity before replay, but never checks that the replayed receipt's current board still places that identity in Trash. It overwrites `compensating` with `board_transition`, losing the opportunity to reconcile the completed compensation first. The new state transaction makes the receipts durable but does not fix this lifecycle decision.
- **Smallest remedy:** Reconcile an interrupted compensation before re-entering forward effects. Recognize its stable compensation receipt/current state, finish the original operation without archive or child-start effects, and require the authoritative target-column/identity precondition before any replayed destructive effect.
- **Validation needed:** Inject a crash immediately after compensation commits and before the final journal update; recovery must leave the card and worktree in their compensated state and run no stop/archive/child-start effect. Retain the existing test proving that an uncompensated committed Trash move can still finish its intended cleanup.

### M05-F03 — P2 · Correctness/idempotency: retrying a successful native Restart repeats the process effects

- **Anchor:** [project-task-lifecycle-service.ts](../../src/server/project-task-lifecycle-service.ts), lines 780–831; compare matching-launch reconciliation in Start at 484–486 and Restore at 676–678.
- **Trigger:** A native Restart successfully replaces its process, but the final lifecycle-journal writes fail. The caller retries the same operation ID after journal access recovers. This does not require a runtime crash.
- **Consequence:** Native Restart ignores the already-successful summary with its own `launchOperationId` and attempts to stop again. With the original session-instance fence, it rejects its own replacement as stale and persists `stop_failed`, despite having performed the requested restart. Without that optional fence, it stops the replacement and launches another copy, interrupting work that may have begun. The current browser supplies the original session-instance ID when available.
- **Evidence:** Two focused tests used the real lifecycle journal and injected failure into both finalization attempts after a successful stubbed start. The journal remained pending and the live summary identified the successful Restart. Retrying the same command produced a second stop call in both cases: the fenced case finished `stop_failed` with one launch; the unfenced case launched a second time. Terminal stop's actual stale-instance rejection was traced in [session-lifecycle-controller.ts](../../src/terminal/session-lifecycle-controller.ts), lines 334–348. The structured restart owner already checks its own operation identity; the missing check is in the native branch.
- **Smallest remedy:** Reconcile an existing successful launch for this operation before native stop/relaunch, using the same authoritative matching-launch contract as Start and Restore. Preserve rejection of unrelated newer launches and the original requested session fence when the restart has not happened yet.
- **Validation needed:** Keep both injected-finalization-failure cases and require retries to complete from the existing launch without another stop/start. Add a different-operation/current-instance control. Cold-start coordination needs the separate ordering check below because generic startup recovery can replace the old launch marker.

## Uncertain candidates and cross-module follow-up

- **Startup recovery ordering (M04/M06/M09):** CLI initialization queues native startup recovery before runtime-server assembly invokes lifecycle recovery. Registry candidate selection checks execution ownership and board/session meaning, but does not consult pending lifecycle operations. Generic recovery requests omit the lifecycle `launchOperationId`. A pending Restart/Restore therefore has potentially competing owners, and a generic replacement can erase the launch marker used by lifecycle replay. This source ordering is established; no complete coordinator/PTY interleaving was reproduced in this pass, so it is not a fourth finding. The smallest deciding check gates native preparation/launch while recovering a pending lifecycle operation and asserts one authorized process owner and a correct terminal result.
- **Resource serialization (M10/M13/M21):** Runtime wiring wraps lifecycle stop and start in `TaskResourceOperationCoordinator`, while lifecycle ensure/archive/purge call worktree functions directly. The worktree operation/setup locks serialize filesystem setup/removal, but do not own PTY launch. The compatibility native-start route can omit `launchOperationId`, and the shell-start handler has neither the task-resource runner nor lifecycle-column admission. A concurrent client launch between stop and archive needs a caller-path test. This is an unresolved cross-boundary race, not a claim that ordinary single-client Trash always deletes a live checkout.
- **Periodic Git lock cleanup (M12):** Orphan maintenance correctly deduplicates paths and prevents overlapping sweeps. Its callee [lock-cleanup.ts](../../src/fs/lock-cleanup.ts) removes `index.lock` after a ten-second mtime threshold without identifying an owner. Age alone does not demonstrate that a long-running Git process exited. Carry the callee's safety contract into M12; this pass did not run a process holding an actual Git index lock.
- **Large lifecycle journals:** Every phase update rewrites the bounded operation journal, including retained create/start command content. Clear Trash bounds concurrent workers but not total requests or journal bytes. No representative image-heavy/large-board benchmark ran, so this remains a profiling candidate rather than a measured performance finding.
