## Findings

### M03-F02 — P2 · Correctness/concurrency: older board work can overwrite a newer persisted session snapshot

- **Anchor:** [project-board-command-service.ts](../../src/state/project-board-command-service.ts), lines 188–189 and 283–292; persistence at [project-state.ts](../../src/state/project-state.ts), lines 466–472.
- **Trigger:** A title or metadata operation captures session snapshot S0, then waits during context resolution or lock acquisition. Session reconciliation captures and persists S1 first. The older operation subsequently acquires the lock.
- **Consequence:** Even a rejected/no-op generated-title update rewrites `sessions.json` with S0 because every internal mutation sets `persistSessionsOnNoop: true`. The disk can regress after `RuntimeSessionPersistence` has acknowledged S1 and marked its generation persisted. It stays stale until a subsequent session reconciliation; its generation accounting cannot detect a later unrelated writer's regression.
- **Evidence:** CLI composition obtains cloned summaries from the terminal store before entering `applyProjectBoardMutation`; that function parses the supplied snapshot before awaiting context and the project lock. A dependency-free execution of the actual command-service class, with a gated persistence seam, persisted S1 through reconciliation and then S0 through an older title no-op. The real seam unconditionally writes the captured input. `RuntimeSessionPersistence` only retries while dirty generation exceeds persisted generation. This establishes stale durable state, not a demonstrated provider-restart failure.
- **Smallest remedy:** Stop persisting session snapshots as a side effect of unrelated title/metadata work, and give session persistence an ordered owner. If board commands must include sessions, obtain/version-check their authoritative snapshot inside the serialization boundary so an older capture cannot replace a newer committed generation. Preserve board-linked pruning.
- **Validation needed:** Delay a title/metadata operation before lock entry, persist a newer session generation and acknowledge its barrier, then release the older operation. Reload disk and assert the newer summary survives, including a title no-op and shutdown with no later session change.

### M03-F04 — P2 · Correctness/recovery: corrupt lifecycle journal handling forgets the durable operation history

- **Anchor:** [project-task-lifecycle-operation-store.ts](../../src/state/project-task-lifecycle-operation-store.ts), lines 100–105 and 135–153.
- **Trigger:** A lifecycle journal is malformed and its first reader successfully renames it to the corruption backup.
- **Consequence:** Only the first read fails. Every later read treats the now-missing journal as an empty history. Startup recovery logs the first failure and continues; a later restart sees no pending work to compensate. Subsequent `begin` calls can accept operation IDs whose prior content/outcome can no longer be checked, and pending linked-task plans are silently unavailable.
- **Evidence:** An exact-source check read malformed JSON twice: the first call threw; the second returned `{version:1, operations:[]}`. Runtime startup calls `taskLifecycle.recover`, which obtains pending operations through `listActive`, and catches failed project recovery at the composition boundary. The execution-ownership store deliberately copies corruption while preserving the source and has a repeated-read fail-closed test; lifecycle storage lacks that safeguard. The report does not assume every lost receipt necessarily relaunches a process: board and session guards still protect some paths.
- **Smallest remedy:** Preserve the invalid journal in place, copy it to a bounded/content-addressed backup, and keep reads and admissions blocked until explicit repair. Reuse the execution journal's established policy.
- **Validation needed:** Repeated `get`, `listActive` and `begin` calls, including a new store instance, must reject after corruption without replacing history. Verify valid pending-operation recovery still works and backups do not grow on every read.

### M03-F05 — P2 · Architecture/correctness: omitting a move's source bypasses lifecycle command admission

- **Anchor:** [project-board-command.ts](../../src/core/api/project-board-command.ts), lines 108–116; [project-board-command-service.ts](../../src/state/project-board-command-service.ts), lines 140–145.
- **Trigger:** A generic `applyBoardCommands` caller sends a `move_task` to Review without the optional `sourceColumnId`, for a started card actually in Trash.
- **Consequence:** The classifier accepts the command and the reducer moves the card without the managed restore workflow, bypassing its journal, worktree preparation and session launch. This violates the published command-service ownership boundary.
- **Evidence:** The schema makes `sourceColumnId` optional. Merged main now rejects every move to In Progress, closing the original start variant. Restore rejection still depends on the caller declaring `sourceColumnId: "trash"`; the reducer checks that source precondition only when it is present. The RPC handler invokes `executeClientBatch` directly. The initial exact-source check demonstrated the omitted-source start on the earlier baseline; post-merge source inspection confirms the remaining omitted-source restore bypass. No post-merge RPC execution is claimed. Existing boundary coverage supplies the source and therefore misses this case. This is an API contract defect, not a claim that current ordinary browser gestures omit the field or an authentication exploit.
- **Smallest remedy:** Require source preconditions on client moves and validate lifecycle policy against the actual locked board, including sequential moves within a batch. Retain internal projection commands' explicit runtime authority.
- **Validation needed:** RPC/service cases for omitted and misleading sources, and a multi-command batch changing the source column before the next move. No forbidden transition may persist or run effects; allowed reordering/ordinary edits must remain supported.

### M03-F06 — P2 · Correctness/backup coverage: project configuration is absent from backups

- **Anchor:** [state-backup.ts](../../src/state/state-backup.ts), lines 44–51 and 185–205; fingerprint selection at lines 339–345.
- **Trigger:** Create a backup after setting project-specific configuration, then restore following loss of the state directory, or restore over newer project settings.
- **Consequence:** Project `config.json` is never copied or restored. Settings such as the worktree setup script, default base ref and project shortcuts are lost after a state-home wipe, or retain their newer value during restore. A project-config-only edit also does not trigger a periodic backup.
- **Evidence:** `getRuntimeProjectConfigPath` stores these settings in `projects/<id>/config.json`; backups copy only the global config and six other project files. An exact-source backup/restore check on disposable synthetic state confirmed that project config was missing from both backup and restored project, and that changing only that file left the fingerprint unchanged. No documented exclusion was found in the inspected backup CLI or current setup/architecture documentation. This is separate from M01's concurrent global-settings save defect.
- **Smallest remedy:** Add project config to one shared backup/restore/fingerprint file inventory, with an explicit compatibility policy for older snapshots. Include pinned-branches in change detection as well: it is copied but currently omitted from the fingerprint.
- **Validation needed:** Round-trip project settings through a clean state-home restore; verify project-config-only and pinned-branches-only changes trigger detection, and define missing-file behavior for older backups.
