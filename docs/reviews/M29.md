## Findings

### M29-F01 — P2 · Lifecycle documentation: developer guide assigns state transitions to Codex compaction

- **Anchor:** [DEVELOPMENT.md](../../DEVELOPMENT.md), lines 312–315.
- **Trigger and impact:** A developer follows the “Current agent mappings” section while modifying Codex hooks or investigating a card that changes state around `/compact`. It says manual compaction start emits `to_in_progress` and completion emits `to_review`. Implementing or debugging to that guide would reintroduce a false Running/Review transition for TUI maintenance, contrary to the current provider-evidence rule.
- **Evidence:** [codex-hooks.ts](../../src/codex-hooks.ts), lines 106–118, maps both manual `PreCompact` and `PostCompact` to `activity`; automatic compaction is not matched. The authoritative [session-lifecycle.md](../conventions/session-lifecycle.md), line 153, and [CHANGELOG.md](../../CHANGELOG.md), line 487, explicitly say compaction is activity-only. The developer guide retained the older paired-transition model after that change.
- **Smallest remedy:** Correct the Codex bullets in `DEVELOPMENT.md` so only prompt submission and qualifying tool completion are working transitions, root Stop/permission/Interrupt are review or interruption evidence as applicable, and manual compaction appears under activity. Keep the more detailed provider caveats in the routed lifecycle document.
- **Validation needed:** Compare the revised summary with `createCodexHooksConfig` and the focused Codex hook/lifecycle tests; run only documentation link/format checks for the edit.

### M29-F02 — P3 · Release documentation: packaged manual advertises an older version

- **Anchor:** [quarterdeck.1](../../man/quarterdeck.1), line 1; [RELEASE_WORKFLOW.md](../../RELEASE_WORKFLOW.md), lines 31–40.
- **Trigger and impact:** A user opens the npm package’s man page for release 0.12.7. Its title/header says `quarterdeck 0.12.3` and “August 2026,” so the shipped command reference appears to describe an older CLI. The release runbook’s version step does not mention the man-page header, allowing the mismatch to recur. The same step says “both package manifests,” although the publishable root package is 0.12.7 and the private `web-ui` package deliberately remains 0.1.0; the command shown operates on the root package and lockfile.
- **Evidence:** [package.json](../../package.json), lines 2–4 and 27–30, declares version 0.12.7 and includes `man/quarterdeck.1` in the npm artifact. [web-ui/package.json](../../web-ui/package.json), lines 2–5, declares a private 0.1.0 package. [CHANGELOG.md](../../CHANGELOG.md), line 45, has the 0.12.7 release section. The [publish workflow](../../.github/workflows/publish.yml), lines 97–110, validates the root package version, with no man-page version gate.
- **Smallest remedy:** Update the man header with each CLI release and make that an explicit release-prep check, preferably generated or checked against the root package version. Clarify that `npm version --no-git-tag-version` updates the root manifest/lockfile, while the private web package has an independent version.
- **Validation needed:** Inspect the packed man page or check its header against `package.json` during the package smoke/release gate; verify the release instructions describe the actual version targets. No current CLI behavior is claimed to be wrong.

### M29-F03 — P3 · Backlog documentation: upstream idea is gated on a release that already happened

- **Anchor:** [upstream-sync.md](../upstream-sync.md), lines 96–100.
- **Trigger and impact:** Someone triages the upstream update-available modal idea using this living tracker. It says Quarterdeck is not published to npm, that `docs/todo.md` still tracks first publish, and to revisit only after publishing. That gate has already passed, so the item is incorrectly deferred and points to a nonexistent todo entry.
- **Evidence:** [README.md](../../README.md), lines 24–25 and 158–179, describes the public npm package and install/upgrade paths; [CHANGELOG.md](../../CHANGELOG.md), lines 45 and 114–120, records subsequent releases and first npm distribution. The current [todo.md](../todo.md) contains no first-publish item. The code already has a background npm update notice, so the tracker should decide whether a modal adds enough value under the present product contract rather than waiting for distribution.
- **Smallest remedy:** Replace the stale “current state” and “revisit after npm publishing” text with the current CLI update-notice behavior and a concrete adoption/defer decision for a modal. Keep the upstream commit as historical provenance.
- **Validation needed:** Check the edited tracker against the current README, todo list, and update-notifier entry point; link/format validation is sufficient.
