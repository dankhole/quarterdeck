## Findings

### M06-F01 — P2 · Correctness/concurrency: task launch can publish an unstopped process after shutdown

- **Anchor:** [session-lifecycle.ts](../../src/terminal/session-lifecycle.ts), lines 235–237 and 280–286. The last cancellation check is at lines 159–168; shutdown changes the generation in [session-lifecycle-controller.ts](../../src/terminal/session-lifecycle-controller.ts), lines 397–419.
- **Trigger:** Shutdown starts after `PtySession.spawn()` but while `registerManagedProcessOwnership()` is pending. Windows registration has real asynchronous PID/ownership work, so this is more than an artificially inserted pause; the reproduction gates that boundary without launching a real PTY.
- **Consequence:** Shutdown sees a pending start with no `entry.active`, marks the summary interrupted and cancels its launch monitor, but cannot stop the provisional PTY. When registration resolves, `spawnTaskSession` publishes the PTY and a live summary without rechecking the generation. `waitForShutdownQuiescence()` waits for that start to finish, then returns with the new process still owned and unstopped. Shutdown persistence can consequently capture live state after its terminal boundary.
- **Evidence:** The actual manager/controller/store with a gated fake PTY returned an interrupted summary with `pid: null` at shutdown, then returned from quiescence with `state: running`, a non-null PID and `startupRecoveryRequired: false`. The PTY's `stop` method had never been called. Existing shutdown tests pass, but do not pause ownership registration after the physical spawn.
- **Smallest remedy:** Fence publication after the ownership await using the existing lifecycle generation/cancellation predicate. If invalidated, stop the exact provisional PTY, dispose its mirror and complete launch cleanup before releasing the tracked start. Keep that cleanup inside shutdown quiescence.
- **Validation needed:** A gated ownership-registration regression should assert cancellation, exact-process cleanup and no post-shutdown live summary; a Windows/ConPTY check is still needed to validate the real process boundary.

### M06-F02 — P2 · Resource lifecycle/concurrency: shell starts lack pending ownership and can orphan a concurrent PTY

- **Anchor:** [session-lifecycle-controller.ts](../../src/terminal/session-lifecycle-controller.ts), lines 220–239; [session-lifecycle.ts](../../src/terminal/session-lifecycle.ts), lines 660–661 and 694–703. Shutdown quiescence collects only task-start and auto-restart promises at controller lines 443–453.
- **Trigger:** Two `startShellSession` requests for the same terminal overlap before the first ownership registration finishes. [start-shell-session.ts](../../src/trpc/handlers/start-shell-session.ts), lines 29–36, forwards directly to this path. A single shell start can also overlap shutdown at the same await.
- **Consequence:** Both starts pass the `entry.active` check and spawn. Their completions overwrite the same active-process/mirror slots, leaving the earlier PTY without a lifecycle owner; its callbacks are rejected by the exact-active-session guards. Shutdown stops only the retained PTY. Pending shell starts are also absent from `hasTaskSessionLifecycleActivity` and shutdown quiescence, so shutdown can finish before a shell publishes itself.
- **Evidence:** Two concurrent calls through the real shell RPC handler, using a gated fake ownership-registration method, created two PTYs and both returned success. Lifecycle activity was false while both were pending. After completion and shutdown, only the second PTY received `stop`. A separate single-start check showed quiescence returning before registration was released, followed by a live shell summary after shutdown.
- **Smallest remedy:** Give shell starts a tracked in-flight operation with per-terminal coalescing/admission and the same cancellation fence used by task starts. Include that operation in lifecycle-activity and shutdown accounting. Dispose any superseded provisional mirror/process rather than replacing its owner silently.
- **Validation needed:** Exercise concurrent identical shell requests and shutdown during registration; assert one retained launch, no orphan, pending activity visibility and completed cancellation before quiescence. This is independent of the backlog's product decision about whether shell panels should persist.

### M06-F03 — P2 · Correctness/identity: pre-handoff hooks can be acknowledged before the launch can enforce their meaning

- **Anchor:** [session-manager.ts](../../src/terminal/session-manager.ts), lines 298–311 and 430–445; [session-lifecycle-controller.ts](../../src/terminal/session-lifecycle-controller.ts), lines 258–260. [hooks-api.ts](../../src/trpc/hooks-api.ts), lines 242–252, observes launch readiness before honoring handoff deferral.
- **Trigger:** A native hook for the current launch arrives while process-ownership registration is pending. In particular, an explicit exact-target resume emits `SessionStart` with the wrong provider session ID before `entry.active` exists. The startup-recovery coordinator has separate handling; the demonstrated path is an ordinary explicit resume.
- **Consequence:** Readiness permanently settles to `identity_mismatch`, but `failTargetedResumeIdentity` returns without stopping or marking failure because there is no active process yet. The hook is acknowledged. After the spawn publishes, subsequent mismatches skip the failure action because the previous outcome is already `identity_mismatch`. The wrong-conversation PTY remains writable, with the requested resume identity still stored and no failure warning.
- **Related loss at the same boundary:** The handoff deferral explicitly exempts all `activity` events, although `PreToolUse` can carry native work evidence. An early current-launch `PreToolUse` is applied without a live process, acknowledged and recorded as delivered. Its retry after handoff is rejected as a duplicate, leaving an otherwise idle resumed launch in Review/Unconfirmed until another qualifying hook arrives. Moving only the activity exemption does not by itself fix mismatch handling, because readiness observation currently runs before the deferral return.
- **Evidence:** Two checks use the real hook-ingest API and manager with gated registration. The mismatch case returned `ok: true`, retained `identity_mismatch`, never stopped the fake PTY, left `warningMessage: null`/the expected resume ID, and accepted subsequent terminal input. The activity case returned `ok: true`, then rejected the identical post-handoff delivery as `duplicate_delivery`; the summary remained unconfirmed with no native work evidence.
- **Smallest remedy:** Make pre-handoff hook admission and launch publication one explicit boundary. Preserve/retry state-bearing activity until the exact launch is active, and enforce a settled mismatch against the provisional or newly published exact PTY before it can become writable. Do not depend on receiving a second mismatch to finish that work.
- **Validation needed:** Deliver SessionStart mismatch and PreToolUse before ownership registration resolves, through reliable hook ingestion; assert exact-process stop/error for mismatch and exactly-once native work application after handoff. Include explicit resume separately from coordinator-owned startup recovery.

### M06-F04 — P2 · Correctness/recovery: viewer reconnect bypasses terminal failure and restart admission

- **Anchor:** [session-lifecycle.ts](../../src/terminal/session-lifecycle.ts), lines 769–784; compare the admission checks in [session-auto-restart.ts](../../src/terminal/session-auto-restart.ts), lines 39–68, and the exact-target fallback at lines 103–106.
- **Trigger:** A viewer reconnects after a failed exact-target Claude/Pi resume, or after normal crash recovery exhausts its three-restarts-in-five-seconds budget. The IO and control connection paths invoke stale recovery through [ws-server.ts](../../src/terminal/ws-server.ts), lines 61–69, 157 and 225.
- **Consequence:** `recoverStaleSession` calls `scheduleAutoRestart` directly for Error summaries, bypassing `shouldAutoRestart`. Its failure guard is specifically `isCodexResumeFailureSummary`, so it does not retain the equivalent Claude/Pi failure as terminal. Although exit handling cleared the failed summary's resume ID, `scheduleAutoRestart` falls back to the retained request's rejected ID. Each later reconnect can launch the same failed target again. Reconnect also starts a fifth process after three automatic crash replacements have consumed the configured budget, without updating that budget.
- **Evidence:** Parameterized manager checks for Claude and Pi exited an unconfirmed exact-target launch with code 78. The summary's resume ID became null, but two subsequent stale-recovery calls each spawned another process using the same `bad-target`. A separate clock-controlled crash check reached four total processes/three recorded automatic restarts; stale recovery created a fifth while the count remained three. No fresh prompt replay was observed or claimed.
- **Smallest remedy:** Share recovery admission and failure disposition between exit-driven and reconnect-driven replacement. Retain a provider-independent terminal exact-resume failure, honor the shared restart budget, and require explicit lifecycle intent to replace that failed request. A transport attachment should not reset those decisions.
- **Validation needed:** Cover all supported providers' failed target paths and reconnect after budget exhaustion, including separate IO/control attachments. Assert that explicit user restart can still establish an authorized new attempt. This is a concrete split-policy defect, not a request for a general recovery refactor.

### M06-F05 — P2 · Correctness/state ownership: rejected starts replace the active launch's policy

- **Anchor:** [session-lifecycle-controller.ts](../../src/terminal/session-lifecycle-controller.ts), lines 142–150 precede active-session rejection/reuse at lines 170–199. The policy is later consumed by [session-manager.ts](../../src/terminal/session-manager.ts), lines 331–334.
- **Trigger:** While a task session is active, another start requests different launch settings and is rejected for a different `launchOperationId`, or merely reuses the current session. For example, Codex approvals change from `user` to `auto_review` between requests. The direct native-start route can reach this manager boundary; native execution ownership does not reject an already-native owner before it.
- **Consequence:** The second request did not create the running process, but its cloned configuration has already replaced `entry.restartRequest`. Native permission interpretation now follows settings the active process never received. In the demonstrated case, a genuine user-review PermissionRequest is ignored as automatic review and the task remains Running. Later automatic restart would also use the rejected request's retained launch configuration.
- **Evidence:** Started launch A with the user approvals reviewer, confirmed native work, then submitted launch B with automatic review. Launch B rejected with “A different task session is already active.” The next launch-A PermissionRequest left the actual summary Running with no outstanding interaction and `launchOperationId: launch-a`. The rendered approval fallback was not exercised; it may independently surface an overlay, but does not make mutation of the active native policy correct.
- **Smallest remedy:** Check rejection/reuse conditions before publishing restart configuration or cancelling current launch readiness. Keep active-launch policy immutable for its process identity, and install replacement configuration only when a new launch is admitted.
- **Validation needed:** For both rejected and reused starts with changed settings, assert unchanged active policy, readiness and restart configuration. Verify the next current-launch permission is interpreted under the actual process's settings.

### M06-F06 — P2 · Correctness/event ordering: delayed Claude tools make ambiguous permission ownership depend on arrival order

- **Anchor:** [session-state-machine.ts](../../src/terminal/session-state-machine.ts), lines 515–535 and 745–758. Compare [hook-event-order.ts](../../src/terminal/hook-event-order.ts), lines 346–365, which deliberately declines ambiguous correlation for already-observed tools.
- **Trigger:** A Claude PermissionRequest lacks a tool-use ID and arrives before two delayed PreToolUse events for different parallel tools with the same prompt/tool name. Both tools occurred before the permission. A later PostToolUse completes one of them.
- **Consequence:** The reducer immediately binds the permission to whichever delayed predecessor arrives first. Once set, another matching predecessor cannot invalidate that inferred identity. Completion of the first-arriving tool therefore clears the permission and claims Running, even though the missing native identity cannot establish that it was the requested tool. Reversing only the predecessors' delivery order changes the final state. The parallel tool may still be waiting for the user.
- **Evidence:** Two real hook-ingest checks used permission at time 300, PreToolUse(A) at 100, PreToolUse(B) at 200 and PostToolUse(A) at 400. Delivering A then B after the permission produced Running with no interaction; delivering B then A produced Review with a waiting interaction bound to B. The existing hook-order test explicitly expects parallel matching candidates to remain uncorrelated, but does not cover this delayed reducer path.
- **Smallest remedy:** Apply the same fail-closed ambiguity rule to delayed correlation. Preserve whether an ID was inferred, and invalidate that inference when another matching predecessor makes it ambiguous; do not clear the interaction on the guessed tool's completion. Avoid treating network arrival order as provider ownership evidence.
- **Validation needed:** Add both delivery permutations through manager/ingest, including persistence/replay of the unresolved interaction. Neither permutation should resolve an ambiguous permission solely from one parallel completion; an explicit matching resolution must still work.
