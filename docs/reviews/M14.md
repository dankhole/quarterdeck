## Findings

### M14-F01 — P2 · Correctness/concurrency: an older full refresh overwrites newer home Git metadata

- **Anchor:** [project-metadata-refresher.ts](../../src/server/project-metadata-refresher.ts), lines 122–135 and 252–258.
- **Trigger:** A full project refresh is awaiting its home Git probe while an explicit home refresh or post-fetch invalidation finishes with newer data. Full and home refreshes have separate queues and share no freshness guard for the home result.
- **Consequence:** The old full-refresh completion replaces the newer home cache and broadcasts its older state version/branch/change counts. The source comment explicitly chooses last-completion-wins because this is one project-wide value, but having one value does not remove the overlapping-read race. The display can regress until a later successful poll. This is a metadata defect, not a claim that Git itself is modified.
- **Evidence:** A real monitor/controller/refresher check gated only the loader. Explicit refresh published branch `newer`, version 3; releasing the earlier full probe returned and published branch `older`, version 2. The existing task freshness tests pass because they protect task metadata, not this home path.
- **Smallest remedy:** Put all home refreshes through one shared serialization/freshness owner, or reject a captured result after a newer home generation has committed. Preserve explicit invalidation through coalescing.
- **Validation needed:** Gate full versus manual, poll and post-fetch refreshes in both orders and assert the latest admitted home result cannot regress.

### M14-F02 — P2 · Resource ownership: disposed metadata controllers still publish after replacement

- **Anchor:** [project-metadata-controller.ts](../../src/server/project-metadata-controller.ts), lines 194–200; [project-metadata-monitor.ts](../../src/server/project-metadata-monitor.ts), lines 121–137; publication at [project-metadata-refresher.ts](../../src/server/project-metadata-refresher.ts), lines 285–293 and 369–373.
- **Trigger:** The final client disconnects, a project is disposed or the monitor closes while a refresh/fetch is queued or running. A later connection can create a new controller for the same project before that old work completes.
- **Consequence:** Disposal stops timers but neither retires the refresher nor fences its callbacks. The old controller still commits and calls the shared project callbacks after its replacement publishes. These callbacks are not display-only: the hub also forwards task metadata and inferred base refs to the durable board command service. Pending old fetch success can additionally initiate refresh work after stop.
- **Evidence:** A synthetic check blocked the initial home loader, disposed its actual controller, connected a replacement and observed `new-controller` publication. Releasing the old loader then published `disposed-controller` for the same project. No network fetch occurred: both clients were hidden. Durable task mutation after disposal is a source-traced consequence of the common callback, not an executed full lifecycle test.
- **Smallest remedy:** Retire a controller generation on disposal and reject every post-await commit/callback from that generation. Stop queued follow-up work; cancellation of an already-running Git subprocess is optional if completion is safely fenced. Scope limiter lifetime consistently with the retiring controller.
- **Validation needed:** Dispose/disconnect/close during queued and running probes, reconnect the same project, and assert no late metadata/base-ref persistence or refresh scheduling. Include remote-fetch completion after stop.

### M14-F03 — P2 · Ownership/correctness: metadata trusts a Git registration rejected by launch and removal

- **Anchor:** [project-metadata-paths.ts](../../src/server/project-metadata-paths.ts), lines 81–91; [project-metadata-path-loader.ts](../../src/server/project-metadata-path-loader.ts), lines 79–108. Persistence wiring is [runtime-state-hub.ts](../../src/server/runtime-state-hub.ts), lines 156–181.
- **Trigger:** An isolated task's stale `.git` file resolves to an administrative directory whose backlink now belongs to another worktree. Metadata checks path existence and probes Git, without applying the registration identity check required by ordinary task operations.
- **Consequence:** A successful Git probe is projected as valid task branch/HEAD metadata even though it belongs to another task. The hub feeds the result to `reconcileRuntimeMetadata`; the board projection can persist the wrong branch. A detected branch change can also infer and persist a wrong base ref. Launch/removal fail closed for the same directory, so metadata can corrupt task identity while reporting a usable checkout.
- **Evidence:** A real disposable repository had two registered task worktrees. After pointing A's gitfile at B's admin entry, `assertTaskWorktreeRegistration(A)` rejected it. The actual metadata loader nevertheless returned `exists:true`, B's HEAD and B's branch for A. Both branches and the changed HEAD were real Git objects. [runtime-board-projection.ts](../../src/core/runtime-board-projection.ts), lines 86–112, persists nonempty changed branch names from this projection; that downstream write was inspected, not run in the fixture.
- **Smallest remedy:** Verify isolated checkout registration before probing/projecting authoritative identity. Preserve the shared-project-checkout exemption. Treat failed registration as unavailable/unknown metadata and never persist a branch/base-ref derived from it.
- **Validation needed:** Reuse the broken/backlink-reassigned fixture through the monitor and board command boundary; verify no foreign branch or base ref is applied. Keep valid persisted worktrees and shared-checkout tasks working. M10 owns cross-project task-ID collisions; this is a separate missing registration check in the metadata caller.

### M14-F04 — P2 · Project scoping: background base-ref inference uses the globally selected project's configuration

- **Anchor:** [runtime-state-hub.ts](../../src/server/runtime-state-hub.ts), lines 219–221; consumer at [project-metadata-refresher.ts](../../src/server/project-metadata-refresher.ts), lines 341–351.
- **Trigger:** Multiple projects remain connected and a task branch changes in project B while project A is globally selected. The monitor supplies B's ID to `getProjectDefaultBaseRef`, but the hub callback ignores it and returns `getActiveRuntimeConfig().defaultBaseRef`.
- **Consequence:** B's inference uses A's project-specific preferred integration branch. Where candidate distances tie, the supplied default is first and wins; where B's custom default is not in the built-in candidates, it is omitted entirely. The inferred result is submitted to B's durable board unless the task base ref is pinned. Which project another client selects can therefore alter B's task comparison base.
- **Evidence:** Source trace: [runtime-config.ts](../../src/config/runtime-config.ts), lines 255–257, stores `defaultBaseRef` in per-project configuration; the monitor is explicitly a multi-project map; the refresher passes its own project ID; [git-utils.ts](../../src/workdir/git-utils.ts), lines 511–589, puts the supplied default first and sorts valid candidates by distance; hub lines 180–190 persist and publish the result. This finding is source-verified; no multi-browser or actual default-selection reproduction ran.
- **Smallest remedy:** Resolve the configuration for the monitor's project ID, retaining it within that project's controller or exposing an explicitly project-scoped lookup. Do not use the active selection as a fallback for another project.
- **Validation needed:** Two projects with different custom defaults and tied candidate ancestry; change selection while B's probe is pending and verify B's base-ref result remains B-scoped. Include a pinned base ref as a negative control.

## Uncertain candidates and overlap

- Accepted state-stream sockets also register no `error` handler, matching [M07-F02](./M07.md). The terminal transport reproduction established the WebSocket failure mechanism; this additional source path is recorded here without another finding or a claim that the state endpoint itself was attacked in testing.
- Ordinary state messages lack the diagnostic stream's buffered-byte drop policy. A slow client can accumulate sends, but no state-stream memory/load benchmark ran. Any remedy needs an authoritative resnapshot policy rather than arbitrarily dropping durable state messages.
- Hidden mode deliberately disables focused polling while continuing background tasks; current tests explicitly assert that behavior. This review does not label the intended hidden focus pause a bug merely because the selected task is excluded from background polling.
- Equality omits some nested conflict details and timestamps use `Date.now()`; current tokens/version changes usually trigger publication. No independently reproduced stale-equality failure was established.
- Task deletion/recreation and overlapping full/background refreshes deserve further freshness tests, but this pass did not establish another distinct defect beyond the demonstrated ownership failures.
- M03 owns captured-session persistence races, M04 registry/bootstrap disposal, M07 terminal transport and M15 diagnostics internals. No current todo item specifically covers F01–F04.
