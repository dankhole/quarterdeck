## Findings

### M26-F01 — P2 · Modal lifecycle: stacked confirmation guards make the next Escape close fail

- **Anchor:** [confirmation-dialog.tsx](../../web-ui/src/components/ui/confirmation-dialog.tsx), lines 51–72 and 78–91; actual caller [use-trash-workflow.ts](../../web-ui/src/hooks/board/use-trash-workflow.ts), lines 223–240 and 269–304. The wrappers are [hard-delete-task-dialog.tsx](../../web-ui/src/components/task/hard-delete-task-dialog.tsx), lines 17–35, and [task-trash-warning-dialog.tsx](../../web-ui/src/components/task/task-trash-warning-dialog.tsx), lines 34–41.
- **Trigger and impact:** Confirm either dialog, then open it again and press Escape. The shared `ConfirmationDialog` sets its `confirmFiredRef` and consumes Radix's post-action `onOpenChange(false)` without calling the parent's cancel handler. `useTrashWorkflow` also sets its own `hardDeleteConfirmedRef` or `trashWarningConfirmedRef` on confirm; because the parent cancel handler was skipped, that second ref remains true. On the next opening, Escape calls the parent cancel handler once; it only clears the stale ref and returns, leaving the dialog open. A second Escape closes it. The visible Cancel button invokes the shared cancel handler twice (its own click plus Radix close), masking the stale parent guard in that path.
- **Evidence:** The actual shared component, installed Radix `DialogClose` click composition and both production caller guards were traced. A disposable controlled React/Vitest mount matching the caller guard confirmed: confirm closes, reopen succeeds, first Escape leaves `[role=alertdialog]` mounted, second Escape removes it. A separate disposable DOM check counted two `onCancel` calls for one Cancel click. Both temporary test files were removed. No live browser or user runtime was launched.
- **Smallest remedy:** Make `ConfirmationDialog` the single owner of post-confirm suppression; remove the redundant caller confirmation refs/branches, and invoke `onCancel` only from `onOpenChange(false)` for a cancel click. Preserve the caller's optimistic Trash rollback on a true cancellation.
- **Validation needed:** Add a component/caller-path test covering confirm → reopen → Escape for both Trash warning and hard delete, one Cancel click, and optimistic rollback exactly once. Check pointer and keyboard paths in an isolated browser if visual/focus behavior changes.

### M26-F02 — P2 · Storage availability: blocked localStorage access escapes the fallback

- **Anchor:** [local-storage-store.ts](../../web-ui/src/storage/local-storage-store.ts), lines 48–52 and 55–89. Render-time reads include [use-card-detail-layout.ts](../../web-ui/src/resize/use-card-detail-layout.ts), lines 71–77 and 106–111, through [resize-persistence.ts](../../web-ui/src/resize/resize-persistence.ts), lines 27–44.
- **Trigger and impact:** If a browser denies access to the `window.localStorage` getter (for example, a restricted browsing context), `getLocalStorage()` throws before the read/write/remove functions enter their `try` blocks. The helpers explicitly intend to return null or ignore storage failures, but a layout initialization read can instead throw during rendering and prevent the application from opening. Other consumers lose the same fallback.
- **Evidence:** A disposable web Vitest check replaced the getter with a `SecurityError`; both `readLocalStorageItem` and `writeLocalStorageItem` threw rather than using their documented failure path. The temporary test was removed. Existing M26 tests do not exercise the storage getter exception.
- **Smallest remedy:** Catch the getter itself inside `getLocalStorage()` and return null; keep operation-level catches for access failures after obtaining a storage object.
- **Validation needed:** Add focused getter-throw and operation-throw tests for read/write/remove, and one layout initializer assertion that defaults remain usable when storage is denied.

### M26-F03 — P2 · Keyboard visibility: shared hover-only actions take invisible focus

- **Anchor:** [components.css](../../web-ui/src/styles/components.css), lines 3–22, with the actual focusable menu in [project-navigation-row.tsx](../../web-ui/src/components/app/project-navigation-row.tsx), lines 85–95 and 181–195. The second path is [branch-select-dropdown.tsx](../../web-ui/src/components/git/branch-select-dropdown.tsx), lines 70–89, composed by [search-select-dropdown.tsx](../../web-ui/src/components/search-select-dropdown.tsx), lines 264–305; live selectors are in [task-create-dialog.tsx](../../web-ui/src/components/task/task-create-dialog.tsx), line 235, and [task-inline-create-card.tsx](../../web-ui/src/components/task/task-inline-create-card.tsx), line 180.
- **Trigger and impact:** Keyboard users tab to a project's ellipsis menu or a nondefault branch's Pin action without moving the pointer over the row. The project actions container is `opacity: 0` and becomes visible only on `.kb-project-row:hover`; the branch Pin button likewise has `opacity-0 group-hover/option:opacity-100`. Neither has a focus/focus-within reveal. Both remain tabbable, so focus can land on an invisible action. In the branch selector, the Pin `<button>` is also nested inside the option `<button>`, giving two interactive controls an invalid parent/child relationship.
- **Evidence:** The CSS and actual production markup establish the focus/visibility condition. A disposable DOM mount confirmed the branch action is inside an option button; its source visibility classes and the project-row CSS lack a keyboard-focus override. The DOM check does **not** establish a specific assistive-technology failure or measured pixel result; native browser/AT behavior remains to be checked.
- **Smallest remedy:** Reveal project actions on row `:focus-within` and Pin on its own focus/option focus-within. Render the option selection and Pin as sibling buttons in a row, retaining distinct click and keyboard actions.
- **Validation needed:** Keyboard-tab through the project list and both task-create branch selectors in an isolated browser; assert a visible focused action, separate accessible controls, and that Pin does not select the branch.

### M26-F04 — P3 · Path fidelity: any user's home-shaped path is displayed as this user's home

- **Anchor:** [path-display.ts](../../web-ui/src/utils/path-display.ts), lines 17–44. Direct formatted-path displays include [project-navigation-row.tsx](../../web-ui/src/components/app/project-navigation-row.tsx), lines 46 and 154–160, and [task-trash-warning-dialog.tsx](../../web-ui/src/components/task/task-trash-warning-dialog.tsx), lines 52–67.
- **Trigger and impact:** Open a project under another account's `/Users/<name>`, `/home/<name>` or `C:/Users/<name>` directory. The formatter detects the path shape but has no current-user home input, and rewrites it as `~`. For example, `/Users/alice/project` is displayed as `~/project` even when the running user is Bob, so the project list labels its location incorrectly. A Trash warning can likewise mislabel a worktree path, but only when it has uncommitted changes and that worktree lies under another account's home; the normal worktree root is derived from the running user's state home. The top bar uses only the final path segment and retains the raw path in its tooltip, so a nested project's top-bar label is normally unaffected. The function only changes display; no filesystem operation is redirected.
- **Evidence:** The regex accepts any nonempty username at lines 19–25; the current-user home is never compared. Existing [path-display.test.ts](../../web-ui/src/utils/path-display.test.ts), lines 5–32, confirms the unconditional shorthand as current behavior but does not check identity. This is a source-backed incorrect-label path, not a production-data observation.
- **Smallest remedy:** Shorten only against an actual normalized home path supplied by a trusted runtime/browser context. Until available, display the full normalized path rather than infer identity from its shape.
- **Validation needed:** Test own-home, another user's home, a sibling with a shared prefix, Unix and Windows path variants, plus the Trash warning's rendered label.

## Uncertainty, overlap and existing backlog

- The nested branch buttons are proven DOM structure and a maintainability/accessibility concern grouped with F03's concrete invisible-focus issue. A specific screen-reader failure was not observed and is not claimed.
- F01 is distinct from [M22-F05](./M22.md#m22-f05--p2--dialog-lifecycle-a-second-cherry-pick-confirmation-cannot-be-cancelled): the cherry-pick dialog's own guard blocks cancellation until remount, whereas the shared dialog's guard resets and the Trash caller's stale guard consumes only the first Escape after reopen. Their remedies have separate owners.
- The service worker's navigation fetch/fallback and the icon/manifest wiring were reviewed without a live offline PWA install. No offline failure was established. CSS focus conclusions come from selector/markup contracts, not screenshots.
- Diagnostic log sanitization and runtime admission remain M15-owned. Notification audio mechanics in M26 were inspected and its 12 tests passed; M25 owns the scheduling/visibility hook and should retain any notification timing finding. No measured performance regression or other supported code-smell finding emerged from the remaining utilities.
