## Findings

### M13-F01 — P2 · Resource ownership: detail-shell starts can run inside a worktree that Trash is deleting

**Anchor:** [start-shell-session.ts](../../src/trpc/handlers/start-shell-session.ts), lines 17–36; destructive counterpart [project-task-lifecycle-service.ts](../../src/server/project-task-lifecycle-service.ts), lines 571–600 and 873–895.

The shell RPC resolves/ensures the parent task's checkout and launches a shell without the shared task-resource coordinator or a pending-lifecycle/Trash admission check. Managed Trash stops the task and detail shell through individually coordinated stop calls, then releases those locks before archiving the worktree. A second browser's detail-shell request can therefore launch after the stop checks and before archive removal. The worktree resolver accepts the durable Trash card, and the archive operation does not check for a newly admitted process. Trash succeeds while the newly launched shell retains a deleted working directory. Commands writing during archive can also race its patch snapshot/removal, although the executable check established directory removal beneath a live process, not lost command output.

**Reachability and evidence:** the desktop detail-shell caller sends `projectTaskId` and the derived detail-terminal ID in [use-terminal-panels.ts](../../web-ui/src/hooks/terminal/use-terminal-panels.ts), lines 396–424. Its pending-stop coordination is local to that browser hook. The router exposes this handler through `runtime.startShellSession`; the runtime's managed stop wiring at [runtime-server.ts](../../src/server/runtime-server.ts), lines 371–375, only holds the per-ID coordinator during the stop. [task-worktree-resolve.ts](../../src/workdir/task-worktree-resolve.ts), lines 51–78, does not reject a Trash card or an active lifecycle operation.

A disposable check used the actual `ProjectTaskLifecycleService`, board command service, durable operation journal, task-resource coordinator, worktree creation/resolver and archive implementation. The archive dependency was gated immediately after both stop calls; the actual shell handler then started a plain Node fixture child in the resolved task checkout. Releasing archive produced:

```json
{"stoppedIds":["m13-task","__detail_terminal__:m13-task"],"shellStartAccepted":true,"trashSucceeded":true,"worktreeExists":false,"syntheticChildStillAlive":true}
```

The shell manager/stop result were controlled dependencies; this was not a real PTY or provider test. The child was explicitly terminated and awaited, and the synthetic Git repository, worktree and state were removed. The durable lifecycle journal correctly rejects a second *managed* operation for the same task identity; that is why this finding is about shell/low-level admission rather than competing managed Restore commands.

**Remedy:** make parent-task checkout admission and shell creation share the task-resource boundary with the full stop-and-remove phase. Reject or defer starts when that task has an active destructive lifecycle operation, then recheck the durable task under that boundary. Use the parent task identity for detail-shell checkout ownership; locking only the shell's derived ID would not serialize archive. Preserve the existing process-activity deletion guard as defense in depth and avoid recursively taking the same non-reentrant coordinator from already coordinated stop helpers.

**Validation:** gate immediately before archive and purge, issue a detail-shell start from another client, and prove that either admission is rejected/deferred or removal waits and stops the admitted shell. Cover an already queued start and a request arriving after the card moves to Trash. Keep the distinct M06 concurrent-shell-start test, which addresses pending PTY ownership rather than checkout deletion.

### M13-F02 — P2 · Scope validation: unknown project configuration requests fall back to active/global configuration

**Anchor:** [app-router.ts](../../src/trpc/app-router.ts), lines 48–56; [save-config.ts](../../src/trpc/handlers/save-config.ts), lines 27–43.

`getConfig` and `saveConfig` use the unrestricted procedure and pass only `ctx.projectScope`, discarding the distinction between an intentionally unscoped request and an explicitly requested project that no longer exists. The request resolver deliberately represents the latter as `{ requestedProjectId, projectScope: null }`. Consequently a stale tab or delayed settings request after project removal reads the active project's configuration; saving project-specific settings returns success through `updateGlobalRuntimeConfig`, where those settings are ignored. The caller never receives the `NOT_FOUND` used by ordinary project procedures.

**Evidence:** [runtime-server.ts](../../src/server/runtime-server.ts), lines 175–205, preserves the requested-but-unresolved ID; [load-config.ts](../../src/trpc/handlers/load-config.ts), lines 12–24, then selects the active configuration when scope is null. In [runtime-config.ts](../../src/config/runtime-config.ts), lines 119–126 and 286–306, the global update has no project path/ID, so project shortcuts, pinned branches, base ref and setup script retain their prior values.

A focused check invoked the actual tRPC router and load/save handlers with `requestedProjectId: "deleted-project"`, null resolved scope and a different active project. Only `buildRuntimeConfigResponse` was replaced to avoid agent discovery. `getConfig` returned the active project's config path; saving `{ defaultBaseRef: "feature/expected", worktreeSetupScript: "echo setup" }` fulfilled successfully with the old `main` base ref and empty setup script. No scoped config load occurred. The real config update/locking path ran within a disposable state directory.

**Remedy:** introduce an optional-project procedure or equivalent context check: allow a null scope only when no project ID was requested; reject an explicitly unknown project before calling handlers. Apply the same distinction to other optional-project reads whose result depends on project configuration, such as the Codex model catalog. Keep intentional global settings access supported.

**Validation:** test absent scope, a valid requested scope, and an unknown/removed requested scope through the router. The last case must fail before config reads/writes; a valid project save must persist its base ref/setup script, and an intentionally global save must retain its documented behavior.

## Uncertain candidates and overlap

- **Managed lifecycle concurrency narrowed:** another same-identity managed operation is blocked by `ProjectTaskLifecycleOperationStore.begin`. No finding asserts that ordinary managed Restore races pending Trash. F01 establishes a separate reachable shell admission path.
- **Other checkout consumers:** low-level `deleteWorktree` checks only the task's terminal-manager activity; detail shells and internal structured owners have different ownership. Direct low-level task starts and compatibility worktree routes also do not consume the lifecycle journal's pending reservation. These are adjacent coverage cases for the F01 remedy, not separately counted or presented as current desktop structured execution exposure.
- **Project removal:** asynchronous worktree cleanup after project removal deserves a gated remove/re-add test before claiming it deletes a newly admitted replacement checkout. No such claim is established here. M04 already owns manager disposal/reconciliation leakage.
- **Generated summaries:** `project-procedures.ts` keeps an in-flight set keyed only by task ID and publishes generated text after an asynchronous call without rechecking the source session. Reachability, meaningful cross-project ID reuse and overlap with the dedicated polish pipeline should be assessed in M16; no duplicate finding here.
- **Security boundary:** Host and Origin rejection run before ordinary HTTP and upgrade routing; no-Origin access is an intentional local/CLI contract. Host-event routes require a ledger and runtime composition rejects that ledger unless integrations are simulated. No origin/authentication bypass was demonstrated. Native and simulation capability checks precede launcher calls. Open-file's broad path contract and native protocol handling were not treated as an exploit without an unauthorized caller/contract violation.
- **Existing findings:** M01 config lost updates; M02 stop-ID normalization and IPv6 origin formatting; M04 malformed upgrade decoding/disposal; M06 duplicate shell PTY ownership; M08 hook/provider ordering; M09 internal structured ownership; M10 cross-project worktree identity and failed patch preservation; M11 checkpoint ordering, Git argument handling and diff symlinks; M12 editor containment and search false-empty results remain with their primary reports. Hooks' unguarded late checkpoint publication was explicitly handed to M11.
- **Existing backlog:** shell persistence/minimization policy and unsaved editor state during deleted-scope cleanup are tracked in `docs/todo.md`. Neither supplies a safety policy allowing a new process during an active destructive operation. No measured performance claim or new speculative abstraction is proposed.
