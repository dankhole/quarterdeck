## Findings

### M01-F01 — P1 · Correctness/concurrency: squash landing can silently discard a concurrent target change

- **Anchor:** [prompt-templates.ts](../../src/prompts/prompt-templates.ts), lines 204–219; compare the earlier synchronization and tree verification in steps 3–4.
- **Trigger:** Another worktree advances the target after the agent synchronizes/reviews its tree, but before step 6 captures `OLD_TARGET`.
- **Consequence:** The prompt instructs the agent to create a commit with the old worktree tree and the newly advanced target as parent. `update-ref` succeeds because its expected value was captured after the concurrent change. The new target commit remains in history, but its file changes disappear from the target's final tree without a conflict or rejected compare-and-swap.
- **Evidence:** Let validated target be A, prepared worktree tree be W, and a concurrent target update be B. Step 6 reads B, constructs `commit-tree W -p B`, and successfully swaps B to that commit. Nothing between reading B and updating the ref checks that W includes B. Existing prompt-shortcut tests check portability and legacy text migration, not this invariant. This is static command-sequence evidence; the prompt was not executed.
- **Smallest remedy:** Capture the target object ID before synchronization, use that immutable object ID for synchronization, validation and the new commit's parent, and use the same ID as `update-ref`'s expected old value. If the target advances, reject the land and repeat synchronization/review against the new snapshot.
- **Validation needed:** A disposable Git integration case that advances the target between validation and landing and verifies rejection, plus the unchanged-target success case. Never execute the prompt's destructive worktree reset as part of that test.

### M01-F02 — P2 · Correctness/CLI: disabling update notices also exits the runtime

- **Anchor:** [cli.ts](../../src/cli.ts), line 88, with registration at line 881 and exit at lines 919–924.
- **Trigger:** Launch `quarterdeck --no-update-notifier`, including in combination with `--no-open` or a port option.
- **Consequence:** The recognized root option is absent from `shouldAutoOpenBrowserTabForInvocation`'s allowlist. After the root action finishes startup, `run()` treats this as a command invocation and calls `process.exit(0)`. The runtime does not stay running, and that exit does not call the installed graceful-shutdown controller.
- **Evidence:** Executing the exact extracted classifier returned `true` for `[]` and `["--no-open"]`, but `false` for `["--no-update-notifier"]` and `["--no-open", "--no-update-notifier"]`. The root action awaits `runMainCommand`; that function installs shutdown handlers and then returns. No runtime was launched to establish additional process/state consequences.
- **Smallest remedy:** Add the missing flag immediately; also separate “root runtime action executed” from browser-opening policy so another optional launch flag cannot determine process lifetime.
- **Validation needed:** An isolated CLI launch with this flag must remain alive and then complete graceful shutdown. Cover every registered root launch option in the classifier/lifetime test.

### M01-F03 — P2 · Correctness/concurrency: global settings saves can overwrite unrelated completed updates

- **Anchor:** [runtime-config.ts](../../src/config/runtime-config.ts), lines 286–302; caller [save-config.ts](../../src/trpc/handlers/save-config.ts), lines 29–37.
- **Trigger:** Two unscoped settings requests capture the same `activeRuntimeConfig` before either save completes, then update different fields. A global request racing a project-scoped save of global fields has the same problem.
- **Consequence:** The global file lock serializes writes but not the read/merge transaction. The second request merges into its stale caller snapshot and writes all resolved global fields, undoing the first request's unrelated setting. This includes permission modes and notification preferences, not just presentation settings.
- **Evidence:** `updateGlobalRuntimeConfig` passes `current` directly into `applyConfigUpdates` inside the lock without rereading disk. `applyConfigUpdates` writes a complete merged field set. For example, concurrent changes from `{statuslineEnabled:false, showSummaryOnCards:false}` to each individual field leave only the later change persisted. In contrast, `updateRuntimeConfig` calls `loadRuntimeConfigLocked` after taking its lock. The existing concurrency test exercises that safe function, not `updateGlobalRuntimeConfig` or the unscoped RPC path.
- **Smallest remedy:** Read and merge authoritative global settings under the same lock, preserving project-only context separately for the returned state. Reuse the existing locked update owner where possible.
- **Validation needed:** Two concurrent unscoped RPC saves of distinct fields must both survive reload; add one global-versus-project-scoped save case. This finding is source-traced, not a completed concurrency integration test.

### M01-F04 — P2 · Correctness/configuration: malformed hidden-shortcut settings prevent configuration loading

- **Anchor:** [runtime-config-normalizers.ts](../../src/config/runtime-config-normalizers.ts), line 273 and lines 344–347.
- **Trigger:** Persisted JSON contains a non-array `hiddenDefaultPromptShortcuts`, or an array containing non-string entries, for example `"commit"`, `[null]`, or `[4]`.
- **Consequence:** Configuration loading throws instead of falling back/filtering invalid entries. The project registry loads global settings during startup, so this otherwise recoverable malformed field can block startup and therefore prevent repair through Settings.
- **Evidence:** `toRuntimeConfigState` normalizes the field for its returned property, but passes the raw JSON value into `normalizePromptShortcuts`, which immediately calls `.map` and `.trim`. Exact extracted-source execution produced `TypeError` for all three examples. `normalizeHiddenDefaultPromptShortcuts` already implements the needed filtering; the raw parallel path bypasses it. JSON reads are cast to TypeScript shapes and do not validate those shapes at runtime.
- **Smallest remedy:** Normalize hidden defaults once and pass the normalized value to both fields, or make `normalizePromptShortcuts` itself accept unknown input and use the existing normalizer.
- **Validation needed:** Load malformed persisted JSON through `loadGlobalRuntimeConfig`; assert the surviving valid entries and default shortcuts, and that startup configuration assembly completes.

### M01-F05 — P2 · Availability/resource lifecycle: the probe timeout does not bound a SIGTERM-ignoring probe

- **Anchor:** [agent-registry.ts](../../src/config/agent-registry.ts), lines 267–274; [process-termination.ts](../../src/core/process-termination.ts), POSIX branch of `terminateProcessForTimeout`.
- **Trigger:** On POSIX, an agent's version/features process ignores SIGTERM or remains stuck in its shutdown handler.
- **Consequence:** The nominal three-second timeout sends SIGTERM but neither rejects the promise nor schedules escalation. Settlement still depends on the `execFile` callback. The availability promise remains in the shared in-flight map, so later Settings and launch requests join that same unresolved probe; initial agent selection can also wait indefinitely.
- **Evidence:** A dependency-free harness executed the exact extracted `runProbeCommand` against a synthetic Node process with a SIGTERM handler and an active timer. At 3,300 ms the timeout signal had been sent once and the promise was still pending. The harness then sent SIGKILL and awaited callback completion, leaving no child process behind. The existing timeout unit test manually invokes the callback after asserting the signal, so it does not cover this failure. The model-catalog transport already has a separate grace/escalation/reap path, but availability discovery does not use it.
- **Smallest remedy:** Give probes a bounded termination owner with graceful signal, short escalation deadline and confirmed cleanup; settle with the typed timeout result and release in-flight ownership. Preserve platform-specific process-tree handling and content-safe diagnostics.
- **Validation needed:** Synthetic process integration coverage for SIGTERM resistance and inherited stdio, plus retry after the failed probe. Validate Windows behavior separately; this reproduction establishes only POSIX behavior.
