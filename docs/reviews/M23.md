# M23 — Diff loading and rendering

Baseline: `fb9a34fbc41fb8464dd5133db066120c24eb866c`. Reviewed 2026-09-26. This is a current-application review, not a branch diff. No application or permanent test source was changed.

## Findings

### M23-F01 — P2 · Fetch failure: a failed priority diff becomes a cached empty file

- **Anchor:** [use-all-file-diff-content.ts](../../web-ui/src/runtime/use-all-file-diff-content.ts#L233), lines 233–263 and 296–303; [all-file-diff-content.ts](../../web-ui/src/runtime/all-file-diff-content.ts#L29), lines 29–39.
- **Trigger and impact:** The selected or visible priority file's `getFileDiff` request fails once. The hook substitutes `{ oldText: null, newText: null }`, caches it, removes the force-fetch marker and marks the path loaded. The [viewer](../../web-ui/src/components/git/panels/diff-viewer-panel.tsx#L183) then suppresses its loading skeleton and renders an empty diff with no fetch error. Re-selecting the file or receiving another list poll with unchanged per-file `contentRevision` cannot retry it. A failed refresh with prior cached text likewise marks the old data as successfully refreshed.
- **Evidence:** A disposable test mounted the real hook, rejected its first priority query, then recovered the mocked transport and advanced `filesRevision` while holding `contentRevision` constant. The path remained in `loaded`, text stayed null and the query count stayed at one. The existing test for an *uncached background* failure at [use-all-file-diff-content.test.tsx](../../web-ui/src/runtime/use-all-file-diff-content.test.tsx#L435) follows a different catch branch and does retry when promoted to priority.
- **Smallest remedy:** Keep failure separate from a successful empty response. Preserve any stale text for display, but retain retry eligibility and an error/pending state for the failed path; only update the cache and clear the force-fetch marker after a successful response. Keep background prefetch bounded.
- **Validation needed:** Reject priority initial load and priority refresh, then recover on reselection and on a later poll. Assert the viewer communicates failure or retry state, and verify a successful genuinely empty diff is still considered loaded.

### M23-F02 — P2 · Selection ownership: a pending file response replaces a newer cached selection

- **Anchor:** [use-file-diff-content.ts](../../web-ui/src/runtime/use-file-diff-content.ts#L70), lines 70–83 and 104–110; [git-history-view.tsx](../../web-ui/src/components/git/git-history-view.tsx#L286), lines 286–318.
- **Trigger and impact:** Load file A, select uncached B while its request is pending, then reselect cached A before B resolves. The cache-hit return publishes A without incrementing `requestIdRef`. B still passes the ownership guard and publishes B's text while A remains selected. The history view enriches the currently selected A entry with that hook result, so it can show B's content under A's pathname.
- **Evidence:** A disposable real-hook test used stable file objects and the exact A → B → cached A sequence. It observed A after reselection, then B's `newText` after the deferred B response settled. The production caller is a one-shot working-copy history view and deliberately omits `changesGeneratedAt`; this race does not require polling.
- **Smallest remedy:** Invalidate pending publication whenever selection or context changes, including cache hits and null selections. Associate each result with its request's file/context identity; a cached result may display immediately while the old request is discarded.
- **Validation needed:** Cover A → B → cached A, selection to null, and a context switch with late success and failure. Assert the displayed content always belongs to the selected path.

### M23-F03 — P2 · Draft preservation: review comments clear before terminal paste succeeds

- **Anchor:** [use-diff-comments.ts](../../web-ui/src/hooks/git/use-diff-comments.ts#L106), lines 106–122; [use-card-detail-view.ts](../../web-ui/src/hooks/board/use-card-detail-view.ts#L190), lines 190–205 and 208–222.
- **Trigger and impact:** With typed inline comments, choose **Add** or **Send** while the first terminal paste fails. Both actions invoke a callback typed to return `void` and immediately clear the comment map. The actual task-detail handlers await `sendTaskSessionInput`; on a rejected paste result they show a toast and return. Since no paste was accepted and no comment restoration occurs, the user's draft is lost. A later submit failure is distinct: paste may already have put the text in the terminal.
- **Evidence:** A disposable test mounted the real comments hook with React-owned comment state and a deferred asynchronous callback. The draft disappeared while delivery was pending and remained absent after the callback completed without delivery. The real handler's failed-first-paste behavior was checked in source; the test stubbed transport completion and did not exercise a live terminal or prove server receipt. The existing panel shortcut test at [diff-viewer-panel.test.tsx](../../web-ui/src/components/git/panels/diff-viewer-panel.test.tsx#L399) checks callback invocation and immediate clearing with synchronous mocks, not acknowledgement.
- **Smallest remedy:** Make the paste callback return a typed delivery outcome or awaited promise. Clear the submitted snapshot only after the first paste is accepted; keep it on failure, and avoid clearing edits made while the operation is pending. Treat paste success and later submit success as separate outcomes.
- **Validation needed:** Exercise Add and Send on failed first paste, successful paste, and failed later submit through the task-detail caller. Preserve comments edited during pending delivery and avoid duplicate insertion on retry.

### M23-F04 — P2 · Line coordinates: split context gutters show the new-file number on the old side

- **Anchor:** [diff-parser.ts](../../web-ui/src/components/shared/diff-parser.ts#L157), lines 157–159 and 198–200; [diff-split.tsx](../../web-ui/src/components/git/panels/diff-split.tsx#L80), lines 80–84 and 125–168.
- **Trigger and impact:** Insert or delete lines before unchanged context, then open the split diff. Context rows carry only the new-file `lineNumber` and are reused for both sides, so the old gutter reports the wrong source line. Users checking the original file against the diff can navigate to the wrong line; the error grows with preceding insertions/deletions. Comments on context remain right-side only, so this is a gutter-coordinate defect rather than an established comment-identity defect.
- **Evidence:** `buildUnifiedDiffRows("a\nb\n", "insert\na\nb\n")` gives context `a` old/new coordinates 1/2. A disposable rendered `SplitDiff` check found the first context pair's gutter texts were `[2, 2]`, where `[1, 2]` is required. The existing split tests at [diff-viewer-panel.test.tsx](../../web-ui/src/components/git/panels/diff-viewer-panel.test.tsx#L223) cover replacement alignment and placeholders but do not assert context line numbers.
- **Smallest remedy:** Retain separate old and new coordinates for context rows in the parsed row model. Have the split renderer use the old coordinate on the left and the new coordinate on the right, while preserving the unified renderer's new-side comment identity.
- **Validation needed:** Assert split gutters after leading and middle insertions/deletions, including patch-parsed rows and collapsed context expansion. Verify the unified display and comment keys retain their current semantics.
