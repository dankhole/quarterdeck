# M20 — Task creation, editing and detail surfaces

Baseline: `fb9a34fbc41fb8464dd5133db066120c24eb866c`. Review completed 2026-09-26. All 45 primary files in [module-inventory.json](./module-inventory.json) were read in full: 31 production files and 14 colocated test files. No application or existing test files changed.

The review covered draft ownership, create/edit submission, prompt/image input, asynchronous completions, keyboard and pointer handling, agent options, onboarding, and task-detail composition. Repository instructions, the review-code-smells skill, and the web-ui, frontend-hooks, ui-layout, runtime-state, session-lifecycle, architecture and testing conventions informed the pass. Six P2 findings are supported.

## Findings

### M20-F01 — P2 · Draft ownership: a create request that never persists loses its draft

**Anchor:** [use-task-editor.ts](../../web-ui/src/hooks/board/use-task-editor.ts), lines 437–455 and 472–488; reset implementation at lines 350–363.

Start a newly composed task, then have both request deliveries fail before acceptance. Once authoritative recovery confirms that no task exists, its prompt, images and creation options are already cleared and the dialog is closed. Preparing a lifecycle command calls `resetCreateEditorAfterSubmit` synchronously, before any durable acceptance. The [start actions](../../web-ui/src/hooks/board/use-task-start-actions.ts), lines 152–198, return the prospective IDs immediately and ignore the outcome for draft recovery. The [lifecycle hook](../../web-ui/src/hooks/board/use-task-lifecycle-operations.ts), lines 49–74 and 235–250, correctly retries and refreshes the board, but cannot restore the discarded editor state.

**Evidence:** two disposable tests composed the actual editor, start-action and lifecycle hooks. One supplied a rejected result with an authoritative empty board; the other rejected both delivery attempts and supplied an empty board during recovery. Both ended with no board card, an empty prompt/images and a closed editor after the request had carried the original prompt. Only transport, geometry and authoritative-state delivery were substituted. A server rejection before the create commit can likewise return a no-card state: [project-task-lifecycle-service.ts](../../src/server/project-task-lifecycle-service.ts), lines 325–344 and 370–376. Ordinary unrelated revision changes are semantically retried, so a single revision bump is not claimed to cause this rejection. Failures after the create commit may preserve a Review card and are outside this loss claim.

**Remedy:** retain the prepared draft under its operation identity until authoritative acceptance is known. On confirmed non-creation, restore it or expose an explicit recoverable draft; protect a newer draft from an older failure. Give dialog callers an asynchronous acceptance result. For batches, retain each unsuccessful draft separately; the current bulk loop continues after returned failures rather than breaking.

**Validation:** cover failure before delivery, server rejection before create, accepted creation followed by launch failure, ambiguous accepted delivery, partial batch success and Create more with a newer draft already being edited.

### M20-F02 — P2 · Async state: concurrent image imports overwrite attachments

**Anchor:** [task-prompt-composer.tsx](../../web-ui/src/components/task/task-prompt-composer.tsx), lines 257–301.

Paste or drop a second image while the first image is still being read. Each handler captures `appendImages`, whose closure contains the image array from that render. After decoding, each publishes that old array plus only its own new images. The later completion replaces the attachment added by the earlier one. The same stale snapshot can restore an image removed during a pending read. Both live composer callers support paste/drop, so this does not depend on the hidden file-picker path.

**Evidence:** a disposable DOM test used the real composer, image extraction utility and React state, with a controlled `FileReader`. It dispatched two paste events before either read completed. Completing `one.png` produced `[one.png]`; completing `two.png` then produced `[two.png]`. The first successfully imported attachment disappeared without an error. The utility captures browser transfer files synchronously, so expiration of clipboard data is not the cause.

**Remedy:** append through the current draft owner using a functional state update or an explicit append operation. Preserve draft identity across asynchronous reads so a canceled/replaced draft cannot receive old imports; avoid making a latest-value ref silently attach old input to a new draft.

**Validation:** complete overlapping paste/drop reads in both orders, remove an attachment during a read, and cancel or replace the draft before completion. Assert final attachment identities, not only decoder calls.

### M20-F03 — P2 · Pointer ownership: selecting a file completion closes the inline editor first

**Anchor:** [task-inline-create-card.tsx](../../web-ui/src/components/task/task-inline-create-card.tsx), lines 119–135; [inline-completion-picker.tsx](../../web-ui/src/components/app/inline-completion-picker.tsx), lines 76–86 and 103–106.

While editing an unstarted task, type an `@file` mention and click a suggested file. Inline editing autosaves on document `pointerdown` outside its container. The completion picker portals its menu to `document.body`, and applies the selection on the later `mousedown`. The capture listener therefore treats the suggestion as an outside click, saves the unfinished mention and closes the editor before selection can run. Only the branch popover has an exemption.

**Evidence:** a disposable test rendered the actual inline card, composer and Radix completion portal with a controlled file-search result. The suggested `src/example.ts` button was outside the card DOM. Dispatching its `pointerdown` saved `@src` and unmounted the editor; the following `mousedown` could no longer update the prompt. The actual [App binding](../../web-ui/src/App.tsx), lines 338–354, supplies `handleSaveEditedTask`, which clears the edit state.

**Remedy:** treat the completion portal as part of the editor's interaction boundary, for example through a local portal container or an explicit owned-overlay ref. Preserve ordinary outside-click save and branch-menu handling. Merely moving selection to a bubbling pointer handler still leaves the document capture listener first.

**Validation:** compose the real portal with edit-state teardown; verify pointer selection inserts the mention and keeps editing, keyboard completion works, and a true outside click still saves. This is an event-order finding, not a screenshot-based visual claim.

### M20-F04 — P2 · Keyboard contract: the inline Save shortcut starts the agent

**Anchor:** [task-inline-create-card.tsx](../../web-ui/src/components/task/task-inline-create-card.tsx), lines 224–245; [task-prompt-composer.tsx](../../web-ui/src/components/task/task-prompt-composer.tsx), lines 188–206.

The inline editor displays Command+Enter beside Save and Command+Shift+Enter beside Start. Its shared composer always interprets unmodified Command/Ctrl+Enter as `onSubmitAndStart`, and lets Shift+Enter bubble for the create dialog's Start and open handler. An inline editor has no such parent handler. Following the displayed Save shortcut therefore saves and queues an agent launch; the displayed Start shortcut does nothing in this editor. This can launch unfinished work the user intended only to save.

**Evidence:** the [App binding](../../web-ui/src/App.tsx), lines 339–345, supplies both save and save-and-start. The latter calls `queueTaskStartAfterEdit` at [use-task-editor.ts](../../web-ui/src/hooks/board/use-task-editor.ts), lines 342–348. A disposable test with the real inline card and composer dispatched Command+Enter and observed Start once, Save zero times; Command+Shift+Enter then invoked neither callback. No provider was launched in the test.

**Remedy:** make the composer's submit-key policy explicit per host, or have the inline host own its hotkeys, and derive the shortcut labels from that same policy. Retain the intended create-dialog Start/Start and open mapping separately.

**Validation:** test Save and Start for both inline editing and the create dialog, including platform modifier keys, Shift/Alt combinations and open completion menus. Assert the lifecycle intent as well as default prevention.

### M20-F05 — P2 · Result ownership: an old branch-name response overwrites a newer draft

**Anchor:** [use-task-editor.ts](../../web-ui/src/hooks/board/use-task-editor.ts), lines 232–257 and 272–283.

Request a generated branch name, cancel that draft, open a new task and enter its branch manually before the original request finishes. The result always calls `setBranchName`; neither cancel/open nor manual edits invalidate the request. The old name replaces the newer choice and can subsequently be sent as the new task's requested branch. The single-flight Boolean prevents concurrent generation calls but does not establish which draft still owns the response.

**Evidence:** a disposable test exercised the actual hook with a deferred generation transport. It started generation for `Old draft`, canceled/reopened, set `New draft` and `manual-new-branch`, then resolved the first request. The prompt remained `New draft`, but the branch became `quarterdeck/generated-old-branch`. The branch input remains editable while generation is pending; [task-create-dialog.tsx](../../web-ui/src/components/task/task-create-dialog.tsx), lines 291–315, disables only the generation button.

**Remedy:** bind generation to project, draft generation and input/edit revision. Discard results after cancel, replacement, project change or a later manual branch edit; clear pending presentation without letting an old completion clear a newer request. Cancellation alone is insufficient if the transport may already have completed.

**Validation:** cover manual edits during generation, cancel/reopen, project switching, successful unchanged-draft completion and an older rejection after a newer request begins.

### M20-F06 — P2 · Option propagation: split tasks silently ignore Create feature branch

**Anchor:** [task-create-dialog.tsx](../../web-ui/src/components/task/task-create-dialog.tsx), lines 260–315; [task-editor-drafts.ts](../../web-ui/src/hooks/board/task-editor-drafts.ts), lines 138–174.

Enable Create feature branch and enter a name, then split a list into multiple tasks and use Create all or Start all. The dialog continues showing the checked option and editable name, but both bulk paths call `createTasksOnBoard`, which accepts neither `createFeatureBranch` nor `branchName` and supplies no branch to any created task. The single-task path does pass the option at lines 120–128. With no requested branch, the worktree path defaults to detached creation rather than the selected named-branch behavior.

**Evidence:** one disposable test rendered the actual dialog, split a two-item list and verified the checked feature-branch control and enabled `desired-feature` name remained. A second exercised the actual editor's bulk preparation from that selected state; both resulting tasks had `branch === undefined`. Ordinary Create all uses the same builder at [use-task-editor.ts](../../web-ui/src/hooks/board/use-task-editor.ts), lines 405–419. The server worktree's named-branch versus detached decision is at [task-worktree-lifecycle.ts](../../src/workdir/task-worktree-lifecycle.ts), lines 190–262; no worktree was launched by these checks.

**Remedy:** define a bulk branch policy. The smallest safe UI correction is to hide/disable this single-name option in multi-task mode and clearly show the actual detached behavior. If named branches are supported for split tasks, collect or derive a distinct validated name per task and preserve it through creation; forwarding the same name to every parallel worktree is not sufficient.

**Validation:** compare the visible options with the final task payload for single create/start, split Create all/Start all, and returning from split to single mode.
