## Findings

### M07-F01 — P1 · Correctness/process ownership: Unix orphan cleanup can terminate unrelated agents

- **Anchor:** [orphan-cleanup.ts](../../src/terminal/orphan-cleanup.ts), lines 111–117 and 147–170; automatic consumers at [cli.ts](../../src/cli.ts), lines 422–441, and [shutdown-coordinator.ts](../../src/server/shutdown-coordinator.ts), lines 197–201.
- **Trigger:** On macOS/Linux, an independently launched `codex`, `claude`, or `pi` process has parent PID 1, for example after its launching shell exits. Start or shut down Quarterdeck while that process is still doing work.
- **Impact:** Cleanup selects that process without establishing any Quarterdeck ownership and sends SIGTERM, followed by SIGKILL if it stays alive. It also signals a process group with the same ID when one exists. A process the current user can signal can lose active work even though Quarterdeck never launched it. Parent PID 1 establishes reparenting, not the former parent's identity.
- **Evidence:** The default Unix path obtains the global `ps -eo pid=,ppid=,comm=` list and checks only parent PID, current-runtime exclusion, and the executable basename. There is no project, state-home, launch-record, or creation-identity check. A temporary test supplied a synthetic unrelated `/opt/user-independent/codex` at parent 1 and confirmed both selection and delivery to the injected kill function; the parent-42 control was excluded. No real external process was signalled. Windows uses the separate exact-record path and is not subject to this name-based finding.
- **Smallest remedy:** Remove name-only termination authority on Unix. Persist/revalidate exact owned roots using an appropriate Unix process identity, or fail closed and report unverifiable orphans until that ownership exists. Retain process-group cleanup only for a verified managed launch.
- **Validation needed:** Verify that an independently detached matching-name process is never selected, a previously managed abandoned process is selected, a live owning runtime is respected, and PID reuse cannot authorize a kill. Use synthetic executables and disposable process groups.

### M07-F02 — P2 · Availability/socket handling: malformed terminal frames terminate the runtime

- **Anchor:** [ws-server.ts](../../src/terminal/ws-server.ts), lines 148–216 and 218–375, especially the message/close registration at lines 189–215. Neither accepted socket gets an `error` listener.
- **Trigger:** A client that completes the permitted terminal upgrade sends an invalid WebSocket frame. The IO and control paths both use the same unhandled socket lifecycle.
- **Impact:** The `ws` receiver emits an `error` on the accepted WebSocket. Node treats the unhandled EventEmitter error as a process exception, terminating the runtime and disconnecting unrelated tasks/viewers. The upgrade handler's try/catch cannot catch this later asynchronous event.
- **Evidence:** An isolated child used the actual bridge, middleware, installed `ws`, a fake terminal service, and a disposable loopback listener. After a successful IO handshake, sending the two-byte unmasked text frame `81 00` exited the child with code 1 and `Unhandled 'error' event`, `WS_ERR_EXPECTED_MASK`. This exercised a malformed frame, not merely an injected application exception. The request had an allowed localhost Host and no Origin; no claim is made that a disallowed browser Origin bypasses the middleware. The existing 12 WebSocket tests pass but cover valid frames and malformed JSON, which does not exercise the receiver-error path.
- **Smallest remedy:** Install bounded, content-safe error handling on every accepted socket before using it. Terminate the failed connection and let its existing close/disposal owner release its writer, restore state and backpressure. Keep the Host/Origin gates intact.
- **Validation needed:** Invalid masking, invalid UTF-8 and payload-limit failures on both socket roles must close the offending viewer without terminating the server; a sibling viewer and subsequent valid connection must remain functional.

### M07-F03 — P2 · Correctness/restore ordering: initial restore replays bytes already present in its snapshot

- **Anchor:** [terminal-ws-restore-coordinator.ts](../../src/terminal/terminal-ws-restore-coordinator.ts), lines 87–94, 123–126 and 140–156; snapshot drain at [terminal-state-mirror.ts](../../src/terminal/terminal-state-mirror.ts), lines 159–181.
- **Trigger:** PTY output arrives after restore begins but before its deferred/resize-triggered snapshot is captured, or while already-queued mirror work is being drained.
- **Impact:** The serialized terminal already contains that output, but `restore_complete` subsequently replays the same queued bytes through IO. Normal shell text duplicates; relative cursor movement and non-idempotent terminal operations can leave the browser different from the authoritative mirror.
- **Evidence:** Restore sets `restoreComplete=false` and queues every live chunk while `getRestoreSnapshot()` drains the mirror. There is no sequence boundary distinguishing bytes included in the snapshot from bytes after it. A temporary test used the actual coordinator and actual xterm-backed mirror: `unique-line\r\n` written before the first resize appeared once in the snapshot and once again in the live queue. Applying snapshot plus queue to a second real mirror yielded two occurrences. The existing buffering test emits only after the snapshot has been sent, so it misses the overlapping interval.
- **Smallest remedy:** Establish one ordered snapshot/output boundary at the mirror or stream owner, and replay only chunks strictly after that boundary. Capture the boundary with the snapshot; clearing the buffer after an arbitrary await would instead lose newer bytes.
- **Validation needed:** Exercise output before capture, during a gated mirror drain, and after capture, including relative cursor/scroll sequences and an existing IO batch during explicit re-restore. Snapshot plus subsequent stream must reproduce the mirror exactly once.

### M07-F04 — P2 · Resource lifecycle/backpressure: a missing restore acknowledgement retains unlimited output

- **Anchor:** [terminal-ws-restore-coordinator.ts](../../src/terminal/terminal-ws-restore-coordinator.ts), lines 76–94; [terminal-ws-connection-registry.ts](../../src/terminal/terminal-ws-connection-registry.ts), lines 105–114 and 153–159.
- **Trigger:** IO stays connected while control never connects, closes during restore, or the browser never sends `restore_complete` after a failed/stalled restore.
- **Impact:** Each subsequent output chunk is retained in `pendingOutputChunks` indefinitely. These bytes bypass `createTerminalWsIoOutputState`, so its high-water marks and PTY pause policy never run. One abandoned viewer can retain all future output for an active task and eventually exhaust runtime memory. The 100 ms timer initiates a snapshot; it does not bound handshake completion or retained bytes.
- **Evidence:** `handleLiveOutput` appends whenever an IO socket exists and restore is incomplete. Control disconnect leaves the IO viewer alive; unused-viewer cleanup runs only when both sockets are gone. A temporary check retained 32 MiB across 32 chunks while the IO enqueue/backpressure entry point was called zero times. This demonstrates growth and the absent bound, not a measured production memory incident. Browser control close also leaves the separate IO connection present.
- **Smallest remedy:** Give the restore phase a byte budget and a completion deadline. On failure, retire that viewer's paired sockets/queue or require a fresh bounded snapshot; preserve other viewers and avoid pausing a shared PTY forever for an abandoned client.
- **Validation needed:** Keep IO open with no control, close control during capture/application, and withhold the acknowledgement under continuous output. Verify bounded retained bytes, timer cleanup, prompt disposal, and continued output to a healthy sibling.

### M07-F05 — P2 · Correctness/concurrency: orphan discovery can delete an ownership record during publication

- **Anchor:** [managed-process-ownership.ts](../../src/terminal/managed-process-ownership.ts), lines 208–221 and 274–288.
- **Trigger:** Two runtimes share the state home. One registers a Windows PTY while the other's startup/shutdown discovery reads the newly created `.json` file before its write completes.
- **Impact:** Discovery treats the empty/partial file as malformed and unlinks it. The writer can finish writing and syncing its open descriptor and return a successful ownership handle although the directory no longer contains the record. The handed-off process then lacks the durable evidence needed for later crash cleanup.
- **Evidence:** Registration opens the final discoverable filename with `wx`, then awaits `writeFile` and `sync`; discovery has no shared lock and immediately removes every unreadable/malformed `.json` entry. A temporary test called the actual register/discover functions with a gated first write, real temporary filesystem operations and synthetic Windows identities. Discovery deleted the open empty record; registration subsequently succeeded, but `stat(handle.path)` returned `ENOENT`. It ran on macOS with the Windows policy option, not native Windows. The cross-runtime publication race is separate from M06's post-spawn cancellation/handoff races.
- **Smallest remedy:** Write and sync a uniquely named non-discoverable temporary record, atomically publish the complete file while preserving exclusive record identity, and only then return the handle; alternatively coordinate record reads/writes with one cross-process lock. Do not interpret an in-progress publication as corrupt durable evidence.
- **Validation needed:** Run the gated publication/discovery interleaving on Windows, including crash before publication, concurrent registration/discovery and genuine malformed records. Every successful registration must retain a readable exact-identity record until its explicit retirement.

### M07-F06 — P2 · Correctness/resource bounds: incomplete terminal escapes swallow and repeatedly copy subsequent output

- **Anchor:** [terminal-protocol-filter.ts](../../src/terminal/terminal-protocol-filter.ts), lines 59–62 and 83–111; analogous pending CSI handling at lines 128–147.
- **Trigger:** A shell command or provider emits an unterminated OSC, such as an incomplete title sequence, then continues emitting ordinary output. A cancelled OSC also triggers this because the filter does not recognize cancellation bytes.
- **Impact:** The filter suppresses all following output until BEL or ESC-backslash, retaining it without a size bound. Every incoming chunk concatenates and rescans the entire accumulated sequence, causing unbounded memory and quadratic cumulative copy/scan work for a continuing unterminated sequence. This happens before mirror processing and WebSocket backpressure, including with no viewer attached.
- **Evidence:** The filter only checks OSC terminators before storing the remaining suffix as `pendingChunk`, even when interception is disabled. A temporary test sent an incomplete OSC containing CAN (`0x18`), then eight 256 KiB printable chunks: every call returned no output and pending state exceeded 2 MiB. Existing tests validate split short queries, but not cancellation, oversized sequences or recovery from malformed output. No latency/CPU regression is claimed as measured.
- **Smallest remedy:** Keep only the bounded prefix needed to recognize the short queries this filter owns; stream or safely discard non-target sequences according to a bounded parser state, honoring cancellation/reset semantics. Avoid rebuilding the whole pending sequence per chunk. Preserve valid chunk-split color and device-attribute queries.
- **Validation needed:** Unterminated, cancelled and very long OSC/CSI streams must keep bounded state and allow subsequent valid output to recover. Retain split-terminator, UTF-8, ordinary OSC and query-interception cases.

### M07-F07 — P2 · Correctness/output ordering: inspection state changes reorder live terminal bytes

- **Anchor:** [session-output-pipeline.ts](../../src/terminal/session-output-pipeline.ts), lines 57–64, 95–98 and 120–125; Codex's conditional inspection predicate at [agent-session-adapters.ts](../../src/terminal/agent-session-adapters.ts), lines 483–487.
- **Trigger:** Chunk A arrives while Codex requires rendered-screen inspection and is queued in the asynchronous mirror. Before it applies, a native hook completes/interrupts the turn into an ordinary Review state. Chunk B then arrives with inspection disabled.
- **Impact:** B broadcasts synchronously while A still awaits the mirror callback; A broadcasts later. The server mirror preserves A/B order while viewers receive B/A. ANSI cursor changes, screen clears and text can therefore render a different terminal state. Inspection policy currently changes transport ordering, violating the otherwise useful separation between semantic observation and output delivery.
- **Evidence:** A temporary test used the actual output pipeline, active-entry factory, real headless mirror and the production-equivalent Codex inspection predicate. With the summary moving from Running to Review between writes, the mirror serialized `AB` while the listener received `BA`. No provider was launched; the hook's resulting summary was injected at the existing store boundary. Existing approval tests check transition-before-output but do not change inspection mode with an earlier write still queued.
- **Smallest remedy:** Keep one ordered delivery path for all chunks of an exact PTY. Inspection may delay a chunk and establish its semantic event before publication, but later uninspected chunks must wait behind it. Retain current-session/listener fencing.
- **Validation needed:** Gate mirror application, change state by a real manager hook between A and B, then verify byte-for-byte listener order with inspection turning both on and off. Include ANSI sequences and listener detach/replacement; semantic transitions must still precede the corresponding visible overlay.

## Uncertain candidates and existing overlap

- Snapshot requests on the same control socket have no server-side restore generation. The normal browser serializes its requests, so this pass does not elevate a malicious/alternate-client overlapping request into a separate finding. F03 owns the demonstrated ordinary initial-restore failure.
- A control-only disconnect after a completed restore can also strand future IO acknowledgements and shared backpressure. F04 owns paired-viewer teardown/handshake lifetime; a separate finding would duplicate much of that remedy. The demonstrated F04 memory case is the pre-completion interval.
- Deferred inspected output is also fenced away after `entry.active` changes; whether natural exit can omit its final bytes warrants a focused exit/drain test. This report makes no extra finding for that unexecuted ordering case.
- The active [todo list](../todo.md) already asks for profiling the per-write Codex rendered approval shim and eventual removal when native hooks cover it. F07 is an independently reproduced ordering defect, not another request for that profiling. No measured hot-path performance claim or justified general rewrite of the backpressure/mirror policy was established.
- M01-F05 owns SIGTERM-only timeout behavior. The managed Windows identity snapshot calls the shared termination helper, but this pass found no new Windows timeout defect. M02-F01/F02 retain dropped stop identity and IPv6-origin ownership. M04-F04 owns malformed upgrade-path decoding before the terminal bridge; F02 occurs after a successful upgrade. M04-F05 owns manager reconciliation after project disposal. M06 owns task/shell spawn admission, post-await handoff and stale-recovery restart policy; those are not repeated here.
- None of the seven new findings is already an active todo item. Broad PTY retention policy for hidden shell surfaces remains the separate existing backlog decision.
