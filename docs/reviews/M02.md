## Findings

### M02-F01 — P2 · Correctness/concurrency: stop-request normalization removes the requested process identity

- **Anchor:** [api-validation.ts](../../src/core/api-validation.ts), lines 154–163, especially the returned object at 160–163.
- **Trigger:** A client calls `runtime.stopTaskSession` with `sessionInstanceId: A`, but the task now owns replacement session B when the queued stop executes.
- **Impact:** The intended stale-session guard is lost. The handler stops the current owner instead of rejecting the stale request, potentially interrupting replacement work.
- **Evidence:** The request schema in [task-session.ts](../../src/core/api/task-session.ts) accepts and trims `sessionInstanceId`. The router validates that schema, then `parseTaskSessionStopRequest` reconstructs an object with only `taskId` and `waitForExit`. [stop-task-session.ts](../../src/trpc/handlers/stop-task-session.ts), line 42, forwards the now-undefined ID. The production delegate in [runtime-server.ts](../../src/server/runtime-server.ts), lines 467–468, calls `executionOwnership.stopCurrentOwner`; its native path chooses the current process identity when the requested identity is absent. The terminal controller otherwise rejects mismatches before signalling. An extracted-source check of the post-schema normalization reproduced the missing property.
- **Scope qualification:** Current browser shell-stop callers omit the ID, and managed lifecycle gestures use a separate path that preserves it. This finding establishes a broken published RPC contract; it does not claim that ordinary board Stop currently uses this failing path.
- **Smallest remedy:** Preserve the parsed request fields while replacing only normalized `taskId` (or explicitly retain `sessionInstanceId`). Preserve the ID through every stop implementation, including any non-wait fallback that may be used.
- **Validation needed:** Parser assertion retaining the ID, plus a handler/delegate test where A is replaced by B before execution and no stop signal reaches B. Cover matching-ID and omitted-ID behavior separately. The existing parser test checks only `waitForExit`.

### M02-F02 — P2 · Correctness/availability: IPv6 hosts produce invalid runtime origins

- **Anchor:** [runtime-endpoint.ts](../../src/core/runtime-endpoint.ts), lines 38–43.
- **Trigger:** Launch with the supported host option/environment override set to an IPv6 literal, for example `--host ::1`.
- **Impact:** URL helpers return `http://::1:3500` and `ws://::1:3500`, which are invalid authorities. Browser-opening and hook URLs fail; runtime WebSocket upgrades are rejected even if the user manually visits the bracketed HTTP address.
- **Evidence:** CLI passes the host unchanged to both the host setter and `server.listen`. Exact-source execution returned `http://::1:3500`; Node's `URL.canParse` returned false. [runtime-server.ts](../../src/server/runtime-server.ts), lines 558–564, constructs the upgrade URL with this origin and destroys the socket on parse failure. [ws-server.ts](../../src/terminal/ws-server.ts), line 115, uses the same invalid base. Existing endpoint tests cover IPv4 only; middleware already recognizes bracketed IPv6 loopback origins, so IPv6 is not consistently excluded by the surrounding contract.
- **Smallest remedy:** Keep the unbracketed bind host separate from its URL-authority representation; bracket IPv6 literals in the shared origin builders. Apply the same representation to configured-host allowlists so non-loopback IPv6 hosts also work.
- **Validation needed:** HTTP/WS origin tests for IPv4, DNS names and IPv6; an isolated IPv6-loopback runtime test proving stream upgrade and hook URL parsing. The source/harness evidence does not constitute that runtime test.

### M02-F03 — P3 · Correctness/input validation: port parsing silently accepts malformed integers

- **Anchor:** [runtime-endpoint.ts](../../src/core/runtime-endpoint.ts), lines 15–23.
- **Trigger:** A CLI/environment port contains trailing characters, a fraction, or exponent notation.
- **Impact:** Quarterdeck binds or probes a different port from the supplied value instead of reporting the promised integer-validation error. For example, `3500junk` and `3500.9` become 3500, while `3e3` becomes 3.
- **Evidence:** Exact-source execution reproduced all three results. `parseCliPortValue` directly uses this helper, and `setQuarterdeckRuntimePort` also converts its numeric argument through the same permissive parser. Existing tests reject zero, out-of-range values and wholly nonnumeric text but omit partially numeric input.
- **Smallest remedy:** Validate the complete trimmed decimal representation before conversion and require an integer in range. Retain the documented absent-value default and the CLI's separate `auto` handling.
- **Validation needed:** Table-driven parser/CLI tests for valid bounds, surrounding whitespace, fractional values, suffixes, exponent notation and the absent-value default.
