### M24-F01 — P2 · Editor correctness: a late reload discards edits made after it began

**Anchor:** [use-file-editor-workspace.ts](../../web-ui/src/hooks/git/use-file-editor-workspace.ts), lines 320–355 and 361–374; [file-editor-workspace.ts](../../web-ui/src/hooks/git/file-editor-workspace.ts), lines 86–115.

**Trigger and impact:** Open a clean editable file, click Reload, then type before the read returns. The reload started without a discard prompt, but `reloadTab` unconditionally applies the response with `force: true`. The newly typed content disappears. The same exposure exists after confirming a dirty-tab reload if the user types again while that read is pending. A second reload can also complete out of order. The [editor panel](../../web-ui/src/components/git/panels/file-editor-panel.tsx), lines 353–360 and 447–458, leaves editing available while reload runs.

**Evidence:** A disposable test used the real workspace hook and cache with a deferred `reloadFileContent`. It observed `new local edit` before the response and `disk` afterward. A normal content refresh uses `upsertLoadedFileEditorTab` without force and preserves a dirty tab; the explicit reload bypasses that protection.

**Remedy:** Bind a reload to the tab revision/value at request or confirmation time. Apply its forced replacement only if no later edit or newer reload superseded that authorization; otherwise preserve the edit and request another discard decision if needed. Test clean and confirmed-dirty starts, typing during the request, repeated reload ordering, and selection changes.

### M24-F02 — P2 · Cache lifecycle: a save finishing after Files unmounts leaves the tab stuck saving

**Anchor:** [use-file-editor-workspace.ts](../../web-ui/src/hooks/git/use-file-editor-workspace.ts), lines 99–122 and 206–236; [file-editor-workspace.ts](../../web-ui/src/hooks/git/file-editor-workspace.ts), lines 33–45 and 121–166.

**Trigger and impact:** Save a dirty file, navigate away from Files while the mutation is pending, and return after it succeeds. The module-level cache receives `isSaving: true` before the request. Both success and failure completion update that cache only as a side effect inside a React `setTabsState` updater. Once the hook is unmounted, React drops that update. The remounted tab remains `isSaving: true`; [FileEditorPanel](../../web-ui/src/components/git/panels/file-editor-panel.tsx), lines 186–190 and 263–270, disables save, close, and reload, and the hook's save guard refuses another attempt. Re-fetching the dirty tab preserves its cached saving flag.

**Evidence:** A disposable real-hook test deferred `saveFileContent`, confirmed the cached saving state, unmounted Files, completed the save, and remounted with loaded content. The cached and active tab both remained saving. The failure branch has the same cache-write placement, though only success was executed in this check. Home and task Files surfaces mount conditionally at [home-view.tsx](../../web-ui/src/components/app/home-view.tsx), line 133, and [task-detail-repository-surface.tsx](../../web-ui/src/components/task/task-detail-repository-surface.tsx), line 139.

**Remedy:** Keep the cache and in-flight save lifecycle independent of the mounted hook's state updater. On completion, settle the scoped cached tab first, then publish to a still-mounted matching view. Preserve edits typed during save and prevent an old completion from changing a replacement tab. Test success, rejection, unmount/remount, and scope switches. This is distinct from the existing [todo item](../todo.md) about cleaning caches when a project/task/worktree is deleted.

### M24-F03 — P2 · Search intent: edited queries can navigate or publish old results

**Anchor:** [use-text-search.ts](../../web-ui/src/hooks/search/use-text-search.ts), lines 40–50, 65–98 and 124–150; [use-file-finder.ts](../../web-ui/src/hooks/search/use-file-finder.ts), lines 29–45 and 79–105.

**Trigger and impact:** Search text for `old`, select a result, replace the input with `new`, then press Enter. `setQuery` neither clears the selected result nor invalidates it. Enter opens the old file/line instead of searching `new`. A pending `old` response can also publish after the query changes because the request ID advances only when another search starts. File Finder has the same intent gap during its 150 ms debounce: old results remain actionable until the delayed callback advances the ID. These are same-scope query edits; no project-crossing claim is needed.

**Evidence:** Two disposable tests exercised the real text-search hook. The first saw `onSelect("old.ts", 1)` and no `new` request after the query edit and Enter. The second changed the query while an old request was pending and observed its old result published beneath the new query. The [App caller](../../web-ui/src/App.tsx), lines 216–223 and 565–581, turns selection into Files navigation and does not validate the query that produced the result.

**Remedy:** Give results and selection an explicit query/scope identity. Invalidate or hide them as soon as the intent changes, and require a matching identity before Enter, mouse selection, or response publication. Preserve the intentional debounce while preventing stale navigation. Test both overlays with query edits before and after request dispatch.

### M24-F04 — P2 · Mutation result: a failed list refresh masks a committed file operation

**Anchor:** [use-file-browser-data.ts](../../web-ui/src/hooks/git/use-file-browser-data.ts), lines 111–124, 129–153 and 165–185; [files-view.tsx](../../web-ui/src/components/git/files-view.tsx), lines 172–227.

**Trigger and impact:** Rename a file successfully, then have the follow-up `listFiles` refresh reject. `renameEntry` rejects before updating the selected path, and FilesView never remaps the open editor tab. The [tree dialog](../../web-ui/src/components/git/panels/file-browser-tree-panel.tsx), lines 315–350, shows an error and keeps the old rename input open, although the file has moved. Retrying targets a now-missing old path. Create and delete have the same await-before-return structure; their local selection/tab reconciliation can likewise be skipped after a committed mutation.

**Evidence:** A disposable test used the real `useFileBrowserData` hook. The mocked mutation returned `{path: "new.ts", kind: "file"}`; only the next list query rejected. The caller received that refresh error and retained `selectedPath === "old.ts"`. The server mutation and read are separate RPCs; a failed read does not roll back the completed mutation.

**Remedy:** Return and reconcile the committed mutation result before treating list refresh as best-effort view synchronization. Surface a separate refresh warning/retry without labeling the mutation failed. Test all three mutations with a successful mutation followed by a rejected list read, including open tabs and selected paths.

### M24-F05 — P2 · Search errors: transport failures are displayed as no matches

**Anchor:** [use-text-search.ts](../../web-ui/src/hooks/search/use-text-search.ts), lines 65–97; [text-search-overlay.tsx](../../web-ui/src/components/search/text-search-overlay.tsx), lines 111–122; [use-file-finder.ts](../../web-ui/src/hooks/search/use-file-finder.ts), lines 48–72; [file-finder-overlay.tsx](../../web-ui/src/components/search/file-finder-overlay.tsx), lines 37 and 74–76.

**Trigger and impact:** If either search RPC rejects because the runtime is unavailable, times out, or returns an explicit error, the hook clears results and sets no error state. Text search marks the query searched and renders “No results found”; File Finder renders “No files found.” Users receive a false absence result and cannot tell whether retry is needed.

**Evidence:** A disposable real-hook test rejected the text-search RPC and observed `hasSearched: true`, `isLoading: false`, and empty results. The overlay's empty-result branch then applies. File Finder's catch and presentation use the same empty-on-error policy. [M12-F04](./M12.md#m12-f04--p2--correctnesssearch-errors-failed-text-searches-are-reported-as-successful-empty-results) separately covers server-side failures that are converted into successful empty responses; this finding concerns explicit client-visible RPC rejections and needs a browser error state even after the server fix.

**Remedy:** Retain a typed search error state, show a retryable failure, and reserve the empty message for a successful search with no matches. Test rejected requests and ordinary empty results for both overlays.

### M24-F06 — P2 · Editor history: changing word wrap erases undo for unsaved edits

**Anchor:** [source-editor.tsx](../../web-ui/src/components/editor/source-editor.tsx), lines 231–236, 313–346; [file-editor-panel.tsx](../../web-ui/src/components/git/panels/file-editor-panel.tsx), lines 400–413 and 447–458.

**Trigger and impact:** Edit a file, then toggle Enable/Disable word wrap. `wordWrap` changes `extensions`, causing the effect to destroy the current CodeMirror `EditorView` and create a new `EditorState` from the current text. The unsaved text survives, but its undo stack, selection, and editor view state do not. The next Undo cannot reverse the earlier edit.

**Evidence:** The installed CodeMirror API stores history in an extension on `EditorState`; a focused state check showed undo depth one after an edit and zero after creating a fresh state with the same document. The production component recreates exactly that state on the wrap toggle. A disposable full-component attempt was inconclusive because the out-of-tree fixture loaded duplicate CodeMirror module instances; it is not counted as a passing render test.

**Remedy:** Reconfigure the existing CodeMirror view for presentation changes, using a compartment or equivalent state-preserving effect. Preserve undo and selection across wrap toggles; use a distinct editor identity when the file itself changes. Add a component test with one resolved CodeMirror module graph.

### M24-F07 — P3 · Search rendering: capture groups duplicate text in result snippets

**Anchor:** [text-search-overlay.tsx](../../web-ui/src/components/search/text-search-overlay.tsx), lines 20–38 and 190–194.

**Trigger and impact:** Search with a regular expression containing a capturing group, such as `(foo)`. JavaScript `split` includes captured substrings in `parts`, while `match` also includes the complete match. The renderer interleaves both and displays `foofoo` for a single `foo` in a result line. Multiple groups can scramble longer snippets. Navigation still uses the result's original file and line.

**Evidence:** A direct check of the exact split/match/reduce algorithm on `abc foo xyz` produced `abc foofoo xyz`. This is a display defect; no browser pixel claim or timing claim is made.

**Remedy:** Iterate match indices and slice the original string between them, or use a single replacement/tokenization pass that never inserts capture groups as separate source text. Test plain, grouped, repeated, and zero-width regex matches.
