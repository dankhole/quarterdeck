## Findings

### M17-F01 — P2 · Save queue: an edit accepted during conflict recovery is left unsent

**Anchor:** [use-project-sync.ts](../../web-ui/src/hooks/project/use-project-sync.ts), lines 173–214 and 424–439.

When a board command conflicts or ultimately fails, recovery clears the old pending batches, reapplies the last authoritative state and awaits a refresh. Reapplying that state restores a usable revision, so another edit can be accepted during this await. Its batch joins the queue while `running` is true. After refresh, the catch block breaks out of the pump and sets `running` false without scheduling the newly queued batch.

**Impact:** the second edit remains visible as an optimistic overlay but is not sent. It waits for a later edit or explicit flush. Closing/reloading before that action loses the new edit; the earlier failure toast does not identify this later accepted change as unsaved.

**Evidence:** a real React `useProjectSync` harness deferred only the query/command transport. Command A conflicted; while its refresh was pending, edit B was accepted. Resolving the refresh kept B visible, but the mutation call count remained one. An explicit later flush sent B with the refreshed revision, proving that the batch had been stranded in the queue rather than rejected. No server persistence or browser UI was simulated as having succeeded.

**Remedy:** make recovery an explicit queue state. Either reject/defer admission until recovery settles, or continue pumping batches accepted after the failed batch was cleared. Preserve the distinction between the failed flush and later commands. Avoid silently dropping later edits as a shortcut.

**Validation:** enqueue during successful and failed recovery, then allow no subsequent user action. Assert every accepted edit reaches a terminal saved/failed state and flush waiters resolve for the commands they cover.

### M17-F02 — P2 · Project ownership: late recovery from project A disables project B edits

**Anchor:** [use-project-sync.ts](../../web-ui/src/hooks/project/use-project-sync.ts), lines 195–207; request ownership checks at lines 352–375; edit admission at lines 390–394.

Recovery checks the active project before awaiting its refresh, but does not repeat that check afterward. If the user switches from A to B during A's pending refresh, the refresh correctly ignores its stale response. The recovery caller interprets the unchanged success counter as a failed refresh and unconditionally assigns `{ projectId: A, revision: null }` to the shared authoritative version, even though B has already hydrated.

**Impact:** B's board still renders, but `getAuthoritativeRevision()` returns null and ordinary `setBoard` calls silently return. Editing stays unavailable until another authoritative B apply repairs the version. This is independent of F01's stranded pending batch.

**Evidence:** a second actual-hook check made A's command conflict, held its refresh, switched and hydrated B at revision 7, then released A. B retained its board ownership while its authoritative revision became null. A subsequent B edit made no mutation call and did not alter the board. Only transport results were controlled.

**Remedy:** capture recovery project/generation and recheck them after every await before mutating shared authority. Keep the queue's per-project recovery result separate from the active browser project's version. A refresh should return an explicit applied/obsolete/failed outcome rather than making callers infer it from a shared success counter.

**Validation:** A→B and A→B→A switches during recovery, including B stream hydration without a B HTTP refresh. Obsolete recovery must not change B's revision or edit admission.

### M17-F03 — P2 · Config ownership: a late save response replaces a different project's config

**Anchor:** [use-runtime-config.ts](../../web-ui/src/runtime/use-runtime-config.ts), lines 70–83; persistent consumer [app-dialogs.tsx](../../web-ui/src/components/app/app-dialogs.tsx), lines 64–76.

Config reads have request ordering, but the save callback publishes its result through the stable `setConfigData` without checking the current project or dialog generation. A save started for A can resolve after the mounted hook has changed to B and loaded B's config. The A result then becomes B's displayed config; its `finally` also changes shared saving state without mutation ownership.

**Evidence:** mounted the production hook, loaded A, started a deferred A save, rerendered for B and loaded B, then resolved A. The hook's config changed from B's path/base ref to A's saved path/base ref. The settings dialog is unkeyed and remains mounted across visibility/project changes. Closing a dialog does not cancel its outstanding save. This reproduction is at the real-hook boundary; it does not claim a subsequent wrong-project server write was executed.

**Impact:** settings can show another project's values after a close/switch or other scope change. The form consumes this config, so treating it as B's editable baseline is unsafe. Server-side unknown-project fallback is a separate M13-F02 defect.

**Remedy:** fence mutation publication and saving state by project plus request/generation identity, including unmount/close policy. A stale save may finish durably for A, but must not publish into B's active hook state. Apply the same ownership to completion callbacks in the dialog.

**Validation:** A save finishing after B loads, close/reopen while saving, and overlapping saves. Verify the actual form's scope and callbacks as well as the shared hook.

### M17-F04 — P2 · Read/write ordering: an older config read overwrites a successful save response

**Anchor:** [use-trpc-query.ts](../../web-ui/src/runtime/use-trpc-query.ts), lines 41–44 and 60–74; [use-runtime-config.ts](../../web-ui/src/runtime/use-runtime-config.ts), lines 74–75.

`setData` publishes mutation results without advancing or otherwise invalidating the query request fence. A `getConfig` started before a save can therefore finish afterward with its earlier snapshot and replace the just-saved config. The hook allows saving with `initialConfig` while its refresh is pending: its loading result is false when that initial config exists.

**Evidence:** the real config hook opened with initial config and a deferred old read. A save returned the new base ref and was visible in hook state. Releasing the old read restored the previous base ref. The test used the production `useTrpcQuery` and controlled only query/mutation responses.

**Impact:** the displayed saved baseline regresses even though persistence succeeded. The dialog/form derives its values from that baseline. This is read-versus-write ordering within one project, distinct from F03's cross-project mutation completion and M01's server-side concurrent config writes.

**Remedy:** give authoritative mutation publication an ordering barrier against older queries, or refetch under a new request generation after save. Do not blindly change every `setData` into query cancellation: initialization/clearing also uses that method and needs explicit semantics.

**Validation:** old reads completing both successfully and with an error after save, repeated saves and refreshes, and opening from initial config. A pre-save result must not replace or clear an acknowledged newer value.

## Uncertain candidates and overlap

- Existing Codex options are not compared by command derivation, but the current editor only edits prompt/images/base ref for an existing card. No reachable options-edit loss was established, so this is not scored.
- Notification preload seeding merges even when versioned memory exists. A stale preload after a tombstone could briefly revive a notification; a realistic stream/preload interleaving is needed before adding a finding. Snapshot replacement and current tests intentionally preserve newer session evidence.
- Board-cache updates do not independently reject lower revisions, and project path/Git fields are assigned before the board revision gate. Their user-visible consequences under a realistic out-of-order response were not reproduced here.
- Transport parses trusted runtime JSON without schema validation and build checking acquires `sessionStorage` outside the helper's internal try/catch. No malformed-production-message or storage-access failure was reproduced; neither is called an exploit or a proven browser outage.
- Per-project client/queue maps and duplicate config consumers deserve profiling for long sessions. No memory/performance benchmark ran, so this review makes no measured performance claim or recommendation to add a cache.
- M15 owns browser diagnostics admission/status response races; M14 owns server metadata/fanout races. M18 owns navigation intent; M25 will assess form resets and setting-specific workflows. Those are separate from the demonstrated shared-hook publication failures here.
