## Findings

### M25-F01 — P2 · Draft ownership: a changed config response erases unsaved settings

- **Anchor:** [use-settings-form.ts](../../web-ui/src/hooks/settings/use-settings-form.ts), lines 40–55; caller at [runtime-settings-dialog.tsx](../../web-ui/src/components/settings/runtime-settings-dialog.tsx), lines 53–66.
- **Trigger:** Open Settings with cached `initialConfig`, edit a field before the fresh `runtime.getConfig` response arrives, then receive a response with any different mapped value. The form fingerprints all initial values and unconditionally replaces `fields` whenever that fingerprint changes.
- **Impact:** A draft in an unrelated field disappears, and the Save button can revert to disabled. For example, a worktree setup script being typed is replaced when an audible setting changes in the fresh config. This is local form reset behavior independent of M17's stale-response ordering.
- **Evidence:** [use-runtime-config.ts](../../web-ui/src/runtime/use-runtime-config.ts), lines 24–28 and 90–95, permits initial config to be edited while its query runs. A disposable test mounted the real form hook, changed the script to `unsaved draft`, then supplied a config differing only in `audibleNotificationsEnabled`; the textarea reverted to `original`. Existing settings tests cover mapping/equality and initial hydration, not dirty edits across a changed response.
- **Smallest remedy:** Establish the editable baseline on open, then merge fresh server values only into fields the user has not changed, or retain the draft and surface a conflict/reload decision. Preserve an explicit project/open generation so a new dialog scope can still reset intentionally.
- **Validation needed:** Defer an actual config query after an edit, test a same-value refresh, a changed unrelated field, a changed same field, close/reopen and project switch. Verify Save sends the user's retained intent.

### M25-F02 — P2 · Draft ownership: a prompt shortcut refresh discards in-progress edits

- **Anchor:** [prompt-shortcut-editor-dialog.tsx](../../web-ui/src/components/settings/prompt-shortcut-editor-dialog.tsx), lines 63–69; parent at [app-dialogs.tsx](../../web-ui/src/components/app/app-dialogs.tsx), lines 78–83.
- **Trigger:** With a task and active prompt shortcut selected, save Settings, then open the top-bar **Manage shortcuts...** control and edit a prompt shortcut before the Settings-triggered project-config refetch completes. Settings calls `onSaved` before closing; [app-dialogs.tsx](../../web-ui/src/components/app/app-dialogs.tsx), lines 64–83, starts `refreshRuntimeProjectConfig()` and independently keeps the prompt editor mounted. The [top-bar control](../../web-ui/src/components/app/top-bar-prompt-shortcut-control.tsx), lines 24–28 and 81–90, invokes the [connected top-bar callback](../../web-ui/src/components/app/connected-top-bar.tsx), line 183, to open that editor. When the pending response arrives, the editor's reset effect runs on the new array identities.
- **Impact:** The unsaved label or prompt is silently restored from the fetched config. Even a response with equivalent shortcut values can lose the draft.
- **Evidence:** [runtime-settings-dialog.tsx](../../web-ui/src/components/settings/runtime-settings-dialog.tsx), lines 126–139, calls `onSaved?.()` and immediately closes after a successful save. [use-runtime-project-config.ts](../../web-ui/src/runtime/use-runtime-project-config.ts), lines 13–37, refetches asynchronously; its [query hook](../../web-ui/src/runtime/use-trpc-query.ts), lines 65–75, replaces data without a semantic equality predicate. A disposable DOM test edited `Custom`'s prompt, rerendered the real editor with newly allocated but semantically equal arrays, and observed the textarea revert from `unsaved draft` to `original`. Existing editor tests cover edit/save but do not rerender new prop arrays during an edit.
- **Smallest remedy:** Reset the local editor on a new opening or explicit project/editor identity. Treat server refresh while dirty as a distinct update, preserving local edits or asking how to reconcile them.
- **Validation needed:** Rerender through `AppDialogs` after a real project config refresh, including equivalent and changed values; verify close/reopen and project switch still initialize from the correct server state.

### M25-F03 — P2 · Save ownership: shortcut edits remain active after their save snapshot is submitted

- **Anchor:** [shortcuts-section.tsx](../../web-ui/src/components/settings/shortcuts-section.tsx), lines 181–231; [prompt-shortcut-editor-dialog.tsx](../../web-ui/src/components/settings/prompt-shortcut-editor-dialog.tsx), lines 153–164 and 209–283.
- **Trigger:** Click Save, then edit, delete, add or reorder a shortcut while the request is pending. The settings dialog sets `controlsDisabled` during `isSaving`, but its shortcut row controls do not use it. The prompt editor disables only its Save button; its inputs, drag handles, Add, Delete and Cancel remain active.
- **Impact:** The user sees a change that the already captured save payload does not contain. When the earlier request succeeds, each dialog closes and the later edit is lost.
- **Evidence:** The settings save passes the render's `fields` snapshot at [runtime-settings-dialog.tsx](../../web-ui/src/components/settings/runtime-settings-dialog.tsx), lines 126–138. A disposable DOM test deferred `onSave` in the real prompt editor, clicked Save, edited its textarea to `later draft`, and observed the visible new value while `onSave` still held `original` and then completed. Settings row markup has no `disabled` propagation despite the section receiving it.
- **Smallest remedy:** Freeze all shortcut mutation controls and dismissal while an in-flight snapshot is being saved, or version the draft and close only when the completed request still owns it. Include reorder and icon picker controls in the same policy.
- **Validation needed:** Defer both save paths, attempt every row edit/action and Escape/Cancel during the pending request, then resolve success and failure. Confirm accepted edits are either included in a subsequent save or visibly retained.

### M25-F04 — P2 · Validation: Settings reports success after discarding an empty script shortcut

- **Anchor:** [shortcuts-section.tsx](../../web-ui/src/components/settings/shortcuts-section.tsx), lines 149–164 and 192–231; [runtime-settings-dialog.tsx](../../web-ui/src/components/settings/runtime-settings-dialog.tsx), lines 126–138.
- **Trigger:** Click **Add** under Script shortcuts and then Save before entering a command, or erase an existing shortcut's command and Save. Add creates `{ label: "Run", command: "" }`; the section has no validation and Save is enabled by the changed array.
- **Impact:** The dialog closes as though the shortcut was saved, but the row disappears from the returned config and persisted project config. Duplicate labels also remain accepted, making label-based top-bar selection ambiguous; the empty-command loss is sufficient for this finding.
- **Evidence:** The persistence boundary [runtime-config-normalizers.ts](../../src/config/runtime-config-normalizers.ts), lines 138–169, silently drops a shortcut with an empty label or command. Direct execution of `normalizeShortcuts([{label:"Run",command:"",icon:"play"}])` returned `[]`; [runtime-config.ts](../../src/config/runtime-config.ts), lines 175–205, returns normalized config after writing. By contrast, the first-shortcut path uses `validateNewShortcut` at [use-shortcut-actions.ts](../../web-ui/src/hooks/settings/use-shortcut-actions.ts), lines 156–177, and rejects empty commands.
- **Smallest remedy:** Apply the existing shortcut validation contract to Settings rows before enabling Save. Show field-level errors and either reject duplicate labels or define stable shortcut identity for selection.
- **Validation needed:** Add/erase whitespace-only commands and duplicate labels through Settings; assert no success/close for invalid input and a persisted, selectable row for valid input.

### M25-F05 — P2 · Default identity: renaming a built-in prompt shortcut restores its old entry

- **Anchor:** [prompt-shortcut-editor-dialog.tsx](../../web-ui/src/components/settings/prompt-shortcut-editor-dialog.tsx), lines 24–38, 71–73 and 153–164; server merge at [runtime-config-normalizers.ts](../../src/config/runtime-config-normalizers.ts), lines 291–299.
- **Trigger:** Change the built-in **Commit** row's label to another unique name and Save. The editor sends the renamed row but leaves `hiddenDefaultPromptShortcuts` unchanged because it updates that list only on confirmed deletion.
- **Impact:** The server interprets the renamed row as a custom shortcut and appends **Commit** again. The user's intended rename becomes two shortcuts; the original can still be invoked, and another edit is needed to hide it.
- **Evidence:** Direct execution of `normalizePromptShortcuts([{label:"Renamed commit",prompt:"my prompt"}])` produced `Renamed commit`, `Commit`, `Squash Merge`. The editor exposes the built-in label as an ordinary editable input, marks the original row as Default and has no rename-specific hidden-default update. Existing prompt editor tests exercise editing a custom row and deleting a row, not renaming a built-in.
- **Smallest remedy:** Give built-in rows stable default identity separate from their editable display label, or add the original built-in label to hidden defaults when that row is renamed. Keep explicit revert/delete behavior coherent after a rename.
- **Validation needed:** Rename both built-ins, save and reload, then test revert, hide and restore defaults; assert the intended number and ordering of shortcuts.

### M25-F06 — P2 · Input validation: inherited icon names produce an invalid React component

- **Anchor:** [runtime-shortcut-icons.ts](../../web-ui/src/components/shared/runtime-shortcut-icons.ts), lines 47–59; renderer at [top-bar-project-shortcut-control.tsx](../../web-ui/src/components/app/top-bar-project-shortcut-control.tsx), lines 210–229.
- **Trigger:** A saved project shortcut has `icon: "constructor"` or `icon: "__proto__"`, accepted by the string API schema and preserved by config normalization. `in` treats an inherited object property as a defined icon.
- **Impact:** `getRuntimeShortcutIconComponent` returns `undefined`, which the top-bar shortcut control and Settings icon row use as a JSX component. Rendering the project shortcut fails instead of falling back to a safe icon.
- **Evidence:** [shared.ts](../../src/core/api/shared.ts), lines 46–50, accepts any icon string; [runtime-config-normalizers.ts](../../src/config/runtime-config-normalizers.ts), lines 143–155, trims but does not restrict it. A disposable test called the real resolver with both names and observed `undefined` for each. Top-bar and Settings render the returned value as a component.
- **Smallest remedy:** Use an own-key check (`Object.hasOwn`) or a null-prototype icon map and validate aliases the same way. Ideally normalize persisted icons against the supported set at the config boundary.
- **Validation needed:** Load saved shortcuts with inherited-key and arbitrary invalid icons through config-to-top-bar rendering; assert fallback icons and no render error, while valid picker icons and aliases still work.

### M25-F07 — P2 · Visibility policy: a queued sound plays after the tab becomes active

- **Anchor:** [use-audible-notifications.ts](../../web-ui/src/hooks/notifications/use-audible-notifications.ts), lines 87–115 and 137–175.
- **Trigger:** With **Only when tab is hidden** enabled, a hook-driven review queues a sound while the window is hidden or unfocused. The user focuses the tab during its 500 ms settle window without a notification state/config update.
- **Impact:** The delayed sound plays while the user is looking at the board, contrary to the setting. The timer callback rechecks event and project suppression but never rechecks the global visibility predicate used when it queued the sound.
- **Evidence:** A disposable fake-timer test mounted the real hook with a running task, changed it to hook Review while hidden, then made `document.visibilityState` visible and `hasFocus()` true before flushing the settle timer. Audio still played once. Existing visibility tests hold focus constant across queue and flush.
- **Smallest remedy:** Re-evaluate `areSoundsSuppressed` with the latest master/only-hidden settings at `fireSound`, and cancel pending sounds on visibility/focus changes when appropriate. Keep the hook settle and event-priority behavior.
- **Validation needed:** Test hidden-to-focused and focused-to-hidden transitions during the hook window, alongside existing event upgrade, resume and suppression checks.

### M25-F08 — P3 · Maintainability: shortcut label suffix logic is duplicated

- **Anchor:** [shortcuts-section.tsx](../../web-ui/src/components/settings/shortcuts-section.tsx), lines 20–34; existing domain helper [shortcut-actions.ts](../../web-ui/src/hooks/settings/shortcut-actions.ts), lines 5–20.
- **Trigger/impact:** Settings Add and first-shortcut creation maintain separate implementations of the same trim/case-insensitive collision and numeric-suffix rule. The duplicate keeps a second source of shortcut naming policy in a presentation component and can drift when naming rules change.
- **Evidence:** Both functions build normalized label sets, return the base label if unused and search suffixes from 2 with identical comparisons. The tested domain helper already has production use in `validateNewShortcut`; the Settings version has one Add call site.
- **Smallest remedy:** Have Settings map rows to labels and call the existing pure `getNextShortcutLabel("Run", labels)`. Preserve its current Add label and scroll/focus behavior.
- **Validation needed:** Retain the helper's existing collision tests and check Settings Add for ordinary, case-folded and suffixed names.

## Uncertain candidates and overlap

- The focused-task and document-visibility hooks send fire-and-forget mutations; rapidly changing hints could reach the server out of order because requests carry no sequence. The server applies the latest arrival. This source trace does not establish an actual transport reorder or lasting user impact, so it is not scored. A controlled two-request transport/server check would decide it; the metadata server remains M14's primary scope.
- The review-ready title badge resets handled-event state after its event-count effect on a project change. The stream store clears the retained ready event on ordinary project transitions, so a real event-loss path was not established. No finding is counted.
- M01-F03 owns concurrent global-config read/modify/write overwrites. M17-F03/F04 own late config publication and stale read/save ordering. M19-F04 owns delayed shortcut terminal submission across task/project changes. M20 owns task-editor draft/Save behavior. The M25 findings above concern the local settings/editor inputs, normalization or notification policy and have separate remedies.
- Notification map flattening and sound-edge scans are linear in retained tasks. No representative profile or demonstrated user-visible bottleneck was obtained; no performance regression is claimed.
