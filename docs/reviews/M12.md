# M12 — Filesystem access, editing and search

Baseline: `fb9a34fbc41fb8464dd5133db066120c24eb866c`. Reviewed 2026-09-26. Application and test sources were not changed. This pass used the review-code-smells workflow alongside correctness, containment, concurrency and resource-lifecycle review.

## Scope and ownership

Read all 13 primary files in the exact M12 inventory. Traced Files RPC callers, Git invocation/result handling, startup and periodic cleanup, agent-exit cleanup, file-list invalidation and the working-tree fingerprint consumer. Read the session-lifecycle, runtime-state, architecture-guardrails and testing conventions. Inspected the installed `proper-lockfile` types and release implementation rather than assuming its ownership semantics.

The validated read helper has meaningful defenses: canonical containment, regular-file checks, matching descriptor/path identities, post-open validation and handle cleanup. File editing bounds reads and writes and detects an already-changed content hash. The findings below concern protections that are lost when authorizing mutations, foreign Git-lock ownership, and search result semantics. No separate style-only extraction or measured performance improvement was established.

## Findings

### M12-F01 — P2 · Correctness/lock ownership: cleanup deletes locks held by live Git writers

- **Anchor:** [lock-cleanup.ts](../../src/fs/lock-cleanup.ts), lines 250–259 and 277–282; sweep scope at 223–238. Production callers: [project-orphan-maintenance.ts](../../src/server/project-orphan-maintenance.ts), lines 27 and 83–88; [session-lifecycle.ts](../../src/terminal/session-lifecycle.ts), line 578.
- **Trigger:** A Git writer in a registered repository or any linked worktree holds `index.lock` for more than ten seconds. Alternatively, a managed agent exits while an independent Git writer holds even a fresh lock in that checkout.
- **Consequence:** The background sweep unlinks the active writer's lock, or the agent-exit path removes it without any age check. The live Git command can no longer publish its index and fails; another writer can also acquire the now-missing lock while the first remains alive. The sweep includes the main checkout and all common-directory worktrees, not just the exited agent's resources.
- **Evidence:** A disposable repository ran a real `git update-index --index-info` process with stdin deliberately held open. Its real index lock naturally aged for 10.1 seconds; no timestamps were forged. `cleanStaleGitIndexLocks` removed the lock while the process was still alive. Supplying valid index input then made Git exit nonzero with `Unable to write new index file`. A second live process with a fresh lock failed the same way after `cleanStaleIndexLockForWorktree`. Registry initialization starts the ten-second maintenance timer, startup invokes project cleanup, and the managed agent-exit handler always invokes the force variant. Neither age nor an agent's exit identifies the lock's actual writer. Existing cleanup tests check old/fresh timestamps, not an active Git owner.
- **Smallest remedy:** Stop deleting foreign Git index locks solely because of age or an unrelated process exit. Automatic removal needs evidence that the specific writer has terminated and that the same lock is still present; otherwise preserve the lock and surface an actionable locked-operation outcome. Increasing the threshold does not establish ownership.
- **Validation needed:** Retain real-process cases for an old live writer, a fresh independent writer during agent exit, and a linked worktree. Demonstrate any supported dead-writer cleanup separately, including lock replacement between inspection and removal. Concurrent index corruption was not attempted or claimed by this pass.

### M12-F02 — P2 · Correctness/path policy: aliases bypass protected-directory mutation checks

- **Anchor:** [save-workdir-file.ts](../../src/workdir/save-workdir-file.ts), lines 29–31; [mutate-workdir-entry.ts](../../src/workdir/mutate-workdir-entry.ts), lines 27–47; [read-workdir-file.ts](../../src/workdir/read-workdir-file.ts), lines 232–249. The lexical policy is [workdir-path-policy.ts](../../src/workdir/workdir-path-policy.ts), lines 41–53.
- **Trigger:** An ordinary relative path resolves through an in-worktree symlink to `.git`, `.hg`, `.svn` or `node_modules`. The canonical target is still inside the worktree, so containment succeeds, but its protected components are absent from the supplied path.
- **Consequence:** Files reports the target as editable and saves into protected metadata; create, rename and delete likewise authorize a parent alias without applying the protected-directory rule to the resolved parent. The same target is read-only and rejected when addressed directly. This bypasses the explicit Files mutation policy; it is not a claim of increased operating-system privileges.
- **Evidence:** A real fixture contained `.git/config` and `alias -> .git`. Reading `.git/config` returned `editable: false`; reading `alias/config` returned `editable: true`. Saving through the alias changed the actual `.git/config`, and `createWorkdirEntry("alias/new-metadata")` created a file inside `.git`. The test used the real containment, hashing, locking and write implementations. Existing tests cover direct protected names and outward symlinks, but not an inward alias to a protected target.
- **Smallest remedy:** Apply one mutation policy to both the supplied path and its canonical target or canonical parent relative to the approved root. Use that same decision for read-only presentation and actual mutation admission. Canonical identity also avoids relying solely on platform-name case rules for aliases.
- **Validation needed:** Cover file and directory symlink aliases for read/save/create/rename/delete, including protected destinations and legitimate in-root aliases. Add native case-insensitive filesystem and Windows-junction cases. Preserve the existing outside-root rejection.

### M12-F03 — P2 · Correctness/containment: parent replacement redirects a checked mutation outside the worktree

- **Anchor:** [mutate-workdir-entry.ts](../../src/workdir/mutate-workdir-entry.ts), lines 137–145; the same pre-lock resolution occurs at 74–82 and 101–125. Editor write handoff: [save-workdir-file.ts](../../src/workdir/save-workdir-file.ts), lines 46–64; pathname-based commit: [locked-file-system.ts](../../src/fs/locked-file-system.ts), lines 177–200.
- **Trigger:** A directory is renamed and replaced by a symlink after its canonical parent passed validation, while the operation is entering/waiting for its lock or before the editor's atomic writer commits. A checkout, agent or other local filesystem actor can change these directories without taking Quarterdeck's sidecar file lock.
- **Consequence:** Create/rename/delete reuse the unchecked lexical pathname after the lock boundary. Save validates and closes the original file descriptor, then reopens pathname operations for its temporary write and rename. Those operations can mutate an outside directory even though the requested path and initial read were inside the selected worktree.
- **Evidence:** Two deterministic actual-source tests gated existing asynchronous boundaries. For delete, the gate replaced `root/folder` immediately before entering the real `withLock`; `deleteWorkdirEntry("folder/victim.txt")` returned success, deleted `outside/victim.txt`, and preserved the original inside file. For save, the gate replaced the parent after content-hash validation but before the real atomic writer; the outside file became the submitted content while the original inside file remained unchanged. The second test restored the parent before releasing the original sidecar lock so teardown did not manufacture a compromised-lock error. Only scheduling was controlled; lock acquisition, filesystem deletion, temporary write and rename were real.
- **Smallest remedy:** Carry the approved parent identity into a shared mutation boundary, validate it after acquiring the lock, and make the actual create/delete/rename or atomic-save commit refuse a changed parent. Use canonical lock identities and a containment-preserving commit primitive; the editor's validated read descriptor must not be treated as authorization for a later pathname write. Merely repeating the original pre-lock check leaves the demonstrated wait window open.
- **Validation needed:** Keep controlled parent-swap cases for every mutation, both rename parents, and save after its initial read. Assert that no outside target is changed and that locks and temporary files are released. Exercise junction replacement on native Windows. These tests establish the exposed interleaving, not its frequency in ordinary user sessions or a complete hostile-filesystem sandbox guarantee.

### M12-F04 — P2 · Correctness/search errors: failed text searches are reported as successful empty results

- **Anchor:** [search-workdir-text.ts](../../src/workdir/search-workdir-text.ts), lines 35–52; result limiting occurs only at 55–72. The callee's buffer bound is [git-utils.ts](../../src/workdir/git-utils.ts), lines 11 and 95–103.
- **Trigger:** A valid query produces more than the Git runner's 10 MiB stdout limit, or Git rejects an invalid regular expression with exit code 128. The search special-cases exit code 2 as a bad request and converts every other failure to zero matches.
- **Consequence:** The caller receives `files: []`, `totalMatches: 0`, `truncated: false`, indistinguishable from a successful search with no matches. A low requested result limit does not protect against this: the entire Git output is buffered before the loop enforces that limit. A user can incorrectly conclude that existing text is absent or that an invalid pattern was accepted.
- **Evidence:** A tracked synthetic file with 16,000 matching lines exceeded the real Git runner's buffer. The raw result reported `maxBuffer`; `searchWorkdirText(..., { limit: 1 })` returned the empty-success response. Separately, searching `[` with `isRegex: true` made real Git exit 128 with an unbalanced-brackets error, yet the search helper again returned empty success. The ordinary ref-search test passes and does not cover either error path.
- **Smallest remedy:** Reserve the no-match response for Git's actual no-match exit status. Surface other failures through the existing typed API error boundary. Bound search collection before buffering all matches, or deliberately return a limited/truncated result through a streaming search boundary; simply raising the buffer cap postpones the failure.
- **Validation needed:** Assert explicit errors for invalid regex, timeout and output overflow, plus the real no-match control. If bounded streaming is added, request one result from a large matching input and require a valid first result with correct truncation and subprocess teardown. No repository-scale latency benchmark was run.

### M12-F05 — P3 · Correctness/search parsing: newline-containing filenames are truncated despite NUL framing

- **Anchor:** [search-workdir-text.ts](../../src/workdir/search-workdir-text.ts), lines 55–75.
- **Trigger:** A tracked POSIX filename contains a newline and its content matches a text query. Git's `--null` output preserves the filename, but the parser splits the whole response by newline before consuming the filename's NUL delimiter.
- **Consequence:** The returned path is only the suffix after the last filename newline. Selecting that result can target a nonexistent or different file. Ref browsing uses the same parser.
- **Evidence:** A real repository with `prefix\nactual.txt` and one matching content line produced a search result for `actual.txt`, which did not exist. The fixture used an actual newline in the filename; the escaped notation here is for readability. Git indexing and grep succeeded.
- **Smallest remedy:** Parse filename and line-number fields by their NUL framing first, then consume the content record terminator. Keep valid filename bytes out of line-based splitting.
- **Validation needed:** Add newline and carriage-return filenames, multiple adjacent records and ref-prefixed output; retain normal Unicode and leading-space cases. This is a lower-impact valid-filename edge case, not a general failure of ordinary text search.

### M12-F06 — P2 · Correctness/file search: staged deletion hides a recreated working-tree file

- **Anchor:** [search-workdir-files.ts](../../src/workdir/search-workdir-files.ts), lines 133–137 and 175–186.
- **Trigger:** A tracked file is staged for deletion and a new untracked file exists at the same path, including the ordinary `git rm --cached` case. Porcelain status contains both the staged deletion and an untracked entry.
- **Consequence:** The parser permanently puts the path in `deleted`, even when another status entry identifies its replacement. `ls-files --cached --others` supplies the existing file, but the final filter removes it from quick-open search. The file browser can still list and open it, so the two Files entry points disagree.
- **Evidence:** A disposable committed fixture ran `git rm note.txt`, recreated `note.txt`, and observed both `D  note.txt` and `?? note.txt`. The file existed, but `searchWorkdirFiles(..., "note")` returned an empty list. Existing tests cover a genuinely deleted tracked file and ordinary untracked files separately, not this simultaneous state.
- **Smallest remedy:** Distinguish working-tree absence from index deletion. An existing untracked replacement must override the staged-deletion filter; use the existing working-tree deletion result or explicit status reconciliation rather than treating either `D` column as conclusive absence.
- **Validation needed:** Cover staged deletion plus recreation, `git rm --cached` with the file retained, actual working-tree deletion, staged renames and cache invalidation. Require the replacement path to appear once with changed metadata.

## Uncertain candidates and existing-work overlap

- **Lock release failures:** `withLocks` releases sequentially, so a rejected release can skip later releases. The installed package can reject on lost ownership. No production caller-path case with a surviving second lock was exercised here; this remains a focused resource-cleanup check, not an additional finding.
- **Cache and traversal scale:** File-index/list caches retain entries for previously queried roots; expiry is checked when a root is revisited. Fingerprints issue one stat promise per unique input. No large-worktree/churn memory or concurrency measurement ran. The active [Files performance item](../todo.md) already calls for traversal/transfer/editor profiling; these observations do not justify an unmeasured optimization project.
- **External content races:** The hash guard catches changes already present when save reads the file. A separate external edit after that read may still race the final rename. F03 proves a parent-containment failure; this pass did not characterize all editor-versus-agent content-write interleavings or promise cross-process compare-and-swap semantics.
- **Ownership overlap:** F01 resolves the explicit M05 Git-lock-cleanup carry and belongs to this callee. M11 owns Git-diff reads that follow outward symlinks and Git pathspec handling; those are separate from M12's protected-target policy and post-validation write redirection. M10 owns task-worktree setup/removal and symlink construction. M13 owns RPC authentication/scope admission. The APIs were traced here only to establish callers, not re-reviewed in full.
- No matching active fix was found for F01–F06. The existing search-preview feature request and broad Files performance item do not address these reproduced correctness failures.

## Validation and limits

At the recorded baseline, one focused Vitest invocation passed **9 files / 83 tests**: eight existing suites (**76 tests**) for lock cleanup, locked filesystem, validated opening, path policy, read/save, mutations and both searches, plus seven temporary reproduction tests. One additional invalid-regex reproduction then passed in isolation; the earlier seven cases were skipped in that invocation. In total, **eight distinct reproduction tests passed**. Logs remain in ignored `.quarterdeck/review-validation/m12-validation.log` and `m12-regex-validation.log`.

The reproduction suite used real filesystem operations and disposable Git repositories/processes. Only the two parent-swap tests intercepted a method boundary to control scheduling before delegating to the real implementation. The live-lock case held a real Git subprocess on stdin and always stopped/reaped it; its age was observed through real elapsed time. Synthetic fixture commits were isolated from the project repository. Temporary harness source and fixture directories were removed after validation. New report links and whitespace were checked.

No production fixes, application commits, pushes, external tickets, runtime/dev instance, browser, Agent Lab or real provider were used. No full test suite, typecheck, native Windows/junction execution, performance benchmark or production timing measurement ran. The host checks prove backend behavior and the stated controlled interleavings, not visual UI effects or every platform's filesystem behavior. All 13 primary files were inspected; the cross-module traces do not substitute for those modules' own complete reviews.
