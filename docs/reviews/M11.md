## Findings

### M11-F01 — P1 · Data preservation: single-file operations interpret filenames as Git pathspecs

- **Anchor:** [git-sync.ts](../../src/workdir/git-sync.ts), lines 498–509; [git-stash.ts](../../src/workdir/git-stash.ts), lines 32–40; [git-conflict.ts](../../src/workdir/git-conflict.ts), lines 242–256.
- **Trigger:** Select a valid filename containing Git pathspec metacharacters, such as `selected*.txt` or `[draft].txt`, while another changed file matches that pattern. `validateGitPath` accepts these legitimate paths. `--` separates options but does not disable Git pathspec expansion.
- **Consequence:** Discard can delete or reset files the user did not select. Selected-file stash similarly moves additional work out of the checkout. The conflict choice uses the same nonliteral path construction and can select/stage more than the requested file.
- **Evidence:** Three checks ran the production functions against real disposable repositories. Discarding untracked `selected*.txt` deleted unselected `selected-other.txt`; discarding tracked `[draft].txt` reset unselected `d.txt`; stashing only `[draft].txt` also stashed `d.txt`. All returned success. Conflict resolution's same construction is source evidence, not a separate executed reproduction.
- **Smallest remedy:** Use literal pathspecs consistently for exact selected-file commands, as [git-selected-commit.ts](../../src/workdir/git-selected-commit.ts), lines 42–56, 74 and 83, already does. Retain explicit broad selection only for operations whose contract is “all files.”
- **Validation needed:** Wildcards, brackets and leading pathspec-magic syntax in tracked, staged and untracked filenames; assert every unselected file and index entry remains untouched, including conflict resolution.

### M11-F02 — P2 · File isolation: Git diff follows repository symlinks outside the project

- **Anchor:** [get-workdir-changes.ts](../../src/workdir/get-workdir-changes.ts), lines 181–185 and 607–614; [project-api-changes.ts](../../src/trpc/project-api-changes.ts), lines 213–219 and 246–255.
- **Trigger:** A changed/untracked path inside the repository is a symlink to a readable file outside the repository, and the client loads its diff. The RPC checks path syntax; the loader then calls ordinary `readFile(join(repoRoot, path))`.
- **Consequence:** A project-scoped diff response contains the external target's contents. This also renders the target text rather than Git's symlink blob representation. The Files reader already has a canonical containment and validated regular-file open boundary, but this alternate read path bypasses it.
- **Evidence:** A synthetic outside file and an in-repository symlink were created under a disposable parent. Calling the real `createChangesOps(...).loadFileDiff` returned `synthetic outside repository\n` in `newText`. The unused context was a throwing proxy, so the test exercised the production project-path branch, validation and diff helper without a runtime or HTTP server. No private user file was read.
- **Smallest remedy:** Establish a shared bounded, contained content-read policy for diffs using the existing [read-workdir-file.ts](../../src/workdir/read-workdir-file.ts), lines 120–162, primitives. Handle symlink entries explicitly according to Git blob semantics; do not dereference arbitrary targets.
- **Validation needed:** Outside, inside and dangling symlinks, parent links, regular files and path replacement during opening through the diff API. M12's write-path and search findings remain separate.

### M11-F03 — P2 · Operation ownership: failed new rebase requests abort an existing operation

- **Anchor:** [git-conflict.ts](../../src/workdir/git-conflict.ts), lines 368–400; the corresponding merge cleanup is at lines 449–472.
- **Trigger:** A rebase is paused, the user has edited and staged its conflict resolution, and another rebase request arrives before Continue. Git rejects starting a second rebase. Since the index now has no unmerged entries, the failure path treats that rejection as grounds to run `rebase --abort`.
- **Consequence:** The rejected request aborts the earlier operation and discards the user's staged resolution. The helper never establishes that it created the operation it is aborting. A second client, duplicate request or concurrent terminal operation can reach this state; the project wrappers provide diagnostics, not ownership/serialization.
- **Evidence:** A real conflicting rebase was resolved to `careful manual resolution\n` and staged. A production `runGitRebaseAction({onto:"main"})` returned failure, removed the active rebase and restored the original `feature\n` content. The merge path has the same unconditional-abort pattern; only rebase was reproduced.
- **Smallest remedy:** Reject an already-active operation before starting, coordinate mutations per checkout, and abort only an operation created by the current request. A precheck alone does not cover a concurrent external Git process; ambiguous failures should preserve existing state.
- **Validation needed:** Resolved/unresolved pre-existing merge/rebase states, duplicate requests and interleaved external operations. Keep newly created conflicts available for resolution and retain the original failure when cleanup is inappropriate.

### M11-F04 — P2 · Identity/concurrency: stash actions address a mutable list position

- **Anchor:** [git-stash.ts](../../src/workdir/git-stash.ts), lines 60, 96, 108, 129 and 149; [use-stash-list.ts](../../web-ui/src/hooks/git/use-stash-list.ts), lines 74–78 and 118–122.
- **Trigger:** A user selects a displayed stash, then another client, worktree or terminal pushes/pops a stash before the selected action executes. List entries expose only an index, and all operations reconstruct `stash@{index}` at execution time.
- **Consequence:** Drop deletes a different stash; Apply/Pop/Show likewise act on different content. Refreshing after the action cannot repair the wrong target, and a stash-count refresh does not establish identity.
- **Evidence:** The real sequence was push A → list A at index 0 → push B → drop the displayed index 0. Drop returned success, B disappeared and A remained. No Git calls were mocked.
- **Smallest remedy:** Return a stable stash commit identity with each entry and carry it into requests. Resolve/verify the intended entry before mutation; apply/show can use the immutable object. Drop/pop need coordinated identity-aware reflog mutation and explicit stale-request rejection rather than treating an index as an ID.
- **Validation needed:** Push/pop/drop between list and action, equal-count stack changes and concurrent clients/worktrees. A stale request must never remove a newer entry.

### M11-F05 — P2 · Checkpoint ownership: asynchronous completion reorders turns and crosses launches

- **Anchor:** [turn-checkpoints.ts](../../src/workdir/turn-checkpoints.ts), lines 30–31 and 74–86; [hooks-api.ts](../../src/trpc/hooks-api.ts), lines 311–324; [session-summary-store.ts](../../src/terminal/session-summary-store.ts), lines 454–468.
- **Trigger:** A checkpoint capture is still pending when a later ordinary Review transition queues another capture, or the task launch is replaced before the old capture completes. Both hook captures allocate `latestTurnCheckpoint.turn + 1` before either publishes, and completion applies by task ID alone. The underlying ref also contains only task and turn and is updated unconditionally.
- **Consequence:** Two captures can get the same turn/ref. If B finishes before A, the store then calls A “latest” and B “previous”; [project-api-changes.ts](../../src/trpc/project-api-changes.ts), lines 259–278, feeds that pair to Last Turn diff in reverse order. An old launch can also overwrite a replacement launch's checkpoint. The start handler has a `startedAt` completion guard, but shares turn allocation and offers no same-launch ordering guarantee.
- **Evidence:** Two synthetic checks used the real hook API, reducer and `InMemorySessionSummaryStore`, with native admission methods stubbed and only checkpoint capture deferred. Two successive Stop transitions separated by accepted UserPromptSubmit allocated `[1,1]`; resolving B then A left latest=A, previous=B with identical refs. A separate check replaced session identity/start time and installed turn 5 before resolving the old capture; the replacement then had old turn 1 as latest. These checks prove publication ownership, not real provider timing or atomic filesystem snapshots.
- **Smallest remedy:** Give checkpoint sequencing/publication one per-task owner shared by start and hook capture. Reserve unique turn/generation identities before asynchronous work, serialize the snapshot boundary as needed, and condition both ref and summary publication on the current launch and capture order. Clean up only refs whose ownership is still known.
- **Validation needed:** Slow initial capture, fast successive turns, reverse completion, restart while pending and deletion while pending, with actual Git refs as well as summary/diff consumers. M13 confirmed this ownership gap and defers this finding here.

### M11-F06 — P2 · Content fidelity: Git blob reads strip meaningful whitespace

- **Anchor:** [get-workdir-changes.ts](../../src/workdir/get-workdir-changes.ts), lines 165–176; [git-utils.ts](../../src/workdir/git-utils.ts), lines 149–154; [git-conflict.ts](../../src/workdir/git-conflict.ts), lines 149–158 and 186–194.
- **Trigger:** A file starts with indentation or ends with whitespace/newlines. Content readers use `runGit`/`getGitStdout` without `trimStdout:false`, so the default metadata-oriented trimming alters the blob.
- **Consequence:** HEAD-vs-worktree diffs show phantom boundary changes because only the Git side is trimmed. Ref-vs-ref and conflict views can hide real whitespace-only changes because both blobs are trimmed. The response is not a faithful representation of repository content.
- **Evidence:** With committed and working-tree bytes both `"  same text\n\n"`, the production file-diff helper returned oldText `"same text"` and newText `"  same text\n\n"`. The existing file-diff test explicitly expects the stripped trailing newline, so its passing result does not establish byte fidelity.
- **Smallest remedy:** Use raw stdout for content reads and keep trimming confined to metadata parsing. Preserve null/error semantics separately from an actually empty blob.
- **Validation needed:** Leading indentation, trailing spaces, final-newline changes, empty and whitespace-only files across HEAD/worktree, ref/ref and conflict content readers.

### M11-F07 — P2 · Compatibility: apply-backend rebases cannot be detected or aborted

- **Anchor:** [git-conflict.ts](../../src/workdir/git-conflict.ts), lines 81–111, 267–275 and 316–325.
- **Trigger:** Git uses the supported `rebase.backend=apply` configuration and a rebase conflicts. Git stores that operation under `rebase-apply`; detection checks only `rebase-merge`.
- **Consequence:** The initial rebase response reports its conflict through an explicit override, but later polling loses the operation. Abort returns `{ok:true}` as a no-op while the rebase remains active. Continue falls through to a merge-style `commit --no-edit` instead of `rebase --continue`.
- **Evidence:** Configured the apply backend in a real disposable repository and invoked the production rebase helper. The initial response had a rebase conflict; `.git/rebase-apply` existed; detection returned null. The production abort helper returned success and left that directory and rebase intact. Continue's wrong branch is source evidence, not a separately executed commit.
- **Smallest remedy:** Recognize both rebase backends through the resolved Git directory and preserve operation identity for Continue/Abort. Do not report successful completion/abort while a known operation still exists.
- **Validation needed:** Merge/apply backends, linked worktrees, resolved and unresolved steps, continuation and abort.

### M11-F08 — P2 · Conflict handling: choosing a deleted side cannot resolve a modify/delete conflict

- **Anchor:** [git-conflict.ts](../../src/workdir/git-conflict.ts), lines 149–158 and 242–260.
- **Trigger:** One side deletes a path and the other modifies it. The content API represents the absent stage as an empty string, while the resolution operation always runs `checkout --ours/--theirs` followed by `add`.
- **Consequence:** Choosing the deleted side fails because that stage has no blob to check out. The conflict stays unresolved and the file remains, although this is a valid choice offered by the conflict workflow. An absent stage is also indistinguishable from a genuinely empty file in the content contract.
- **Evidence:** A real modify/delete merge returned empty theirs content. Calling `resolveConflictFile(...,"theirs")` returned failure, `ls-files -u` remained nonempty and the file still existed. Existing deleted-side coverage checks reading the content, not applying the deletion.
- **Smallest remedy:** Read stage existence separately from content. For a deliberately selected absent stage, stage deletion with a literal path; retain normal checkout/add for an existing empty or nonempty blob.
- **Validation needed:** Both deletion directions for merge and rebase, empty-file versus absent-file distinction, and final index/working-tree state.

### M11-F09 — P2 · Argument handling: a sync branch value becomes a Git push option

- **Anchor:** [git-sync.ts](../../src/workdir/git-sync.ts), lines 25 and 46–53; [project-procedures.ts](../../src/trpc/project-procedures.ts), lines 94–106.
- **Trigger:** A project RPC request supplies a flag-shaped `branch`, such as `--all`. The schema accepts any string, and unlike neighboring branch actions this helper performs no branch validation before appending it to `git push origin`.
- **Consequence:** Git interprets the supplied value as an option, widening the push beyond the requested branch. Other flag/refspec values can alter operation semantics. This is an authenticated API input-validation defect; the current ordinary branch picker does not naturally produce a branch named `--all`, and no unauthenticated exploit is claimed.
- **Evidence:** Against a disposable local bare origin, `runGitSyncAction({action:"push",branch:"--all"})` returned success and published both `main` and the unselected local branch. No network remote or user repository was pushed.
- **Smallest remedy:** Validate and resolve an actual branch identity, reject option/refspec syntax where the contract is a branch, and place Git's end-of-options separator appropriately. Do not rely only on UI-generated input or shell-free execution.
- **Validation needed:** Reject leading flags, refspecs, invalid and missing branches; confirm a valid selected branch publishes only its intended ref. Coordinate validation at the Git owner and RPC schema.

### M11-F10 — P2 · Review completeness: stash previews omit saved untracked files

- **Anchor:** [git-stash.ts](../../src/workdir/git-stash.ts), lines 32 and 161–169.
- **Trigger:** Stash includes untracked content, as the production push helper always requests. The preview command uses `stash show -p` without asking Git to include that content.
- **Consequence:** An untracked-only stash has a successful but empty preview; mixed stashes hide their new files. Users cannot inspect all saved content before applying or deleting the entry.
- **Evidence:** Stashed a new file through the real helper. `stashShow` returned `{ok:true,diff:""}`, while the stash's third-parent blob contained `only saved content`. This was an actual Git fixture, not a mocked response.
- **Smallest remedy:** Include untracked changes in stash preview and preserve the distinction between an empty stash diff and unavailable/unsupported content.
- **Validation needed:** Untracked-only and mixed stashes, tracked deletions, binary untracked files and legacy stashes without a third parent.

### M11-F11 — P2 · History parsing: quoted filenames lose their commit patch

- **Anchor:** [git-history.ts](../../src/workdir/git-history.ts), lines 373–390 and 457–464.
- **Trigger:** A committed filename requires quoting in Git's patch header, such as a tab-containing filename. The name/status parser correctly reads NUL-separated paths, but the patch parser accepts only `diff --git a/... b/...` with unquoted paths. `core.quotepath=false` does not disable quoting control characters.
- **Consequence:** The changed file remains listed with metadata, but its patch is silently empty. History review misses content for legal repository paths, with no error in the successful response.
- **Evidence:** Committed `tab\tfile.txt` in a real repository. `getCommitDiff` returned that file with an empty patch while raw `git show` contained `+actual added content`. Existing UTF-8 filename tests cover a different case and do not establish quoted-header support.
- **Smallest remedy:** Parse Git's quoted path syntax correctly or obtain per-file patches using the already established exact path identity. Preserve rename pairing and avoid guessing filenames from ambiguous headers.
- **Validation needed:** Tabs, newlines, double quotes, backslashes, spaces and renames, with byte-exact paths and nonempty expected patches.

### M11-F12 — P3 · Maintainability: status probing duplicates existing shared parsers

- **Anchor:** [git-probe.ts](../../src/workdir/git-probe.ts), lines 27–56; [git-utils.ts](../../src/workdir/git-utils.ts), lines 386–417.
- **Evidence and cost:** `countLines` and `parseNumstatTotals` are duplicated implementations. The probe uses its private versions; workdir changes uses the exported line counter. The shared aggregate parser is exported but has no production caller because the probe copied it. This retains about 30 lines of duplicate parsing and two places to maintain the same line/binary-stat semantics.
- **Smallest remedy:** Import the existing helpers into `git-probe.ts` and remove its duplicate implementations. No new abstraction, cache or change in parsing policy is needed.
- **Validation needed:** Preserve current empty, binary and ordinary numstat behavior and untracked counts with focused parser/probe tests. This is source-established cleanup, not a measured performance defect or a claim of existing parser divergence.

## Uncertain candidates and overlap

- Ref-diff caching resolves hashes for its key but runs later commands against symbolic names. A concurrent ref move could mix metadata and cache identity; no controlled interleaving was executed, so this is not a scored cache-corruption claim. A gated ref-movement test would decide it.
- Cherry-pick parses non-NUL worktree porcelain paths and has best-effort cleanup after failure. Quoted directory names and cleanup refusal deserve a narrow fixture before claiming an additional defect. No temporary-worktree leak was demonstrated.
- Unbounded working-tree text/line-count reads, per-file `stat` fanout and repeated Git metadata commands may affect large repositories. No benchmark was run. The current [Files/Git performance backlog](../todo.md) already asks for profiling, so this review does not invent a measured regression or recommend replacing caches solely from their size.
- F12 intentionally preserves parser behavior; line-count policy and newline edge semantics should be decided separately rather than hidden in a cleanup.
- M01-F01 owns the squash-landing concurrent-target race. M01-F05 owns the shared POSIX SIGTERM-only timeout mechanism also used by `runGit`; this module adds no separate hanging-child finding.
- M10 owns archive failure/detached-commit loss and cross-project worktree/archive identity. M12 owns Files write containment and search-result suppression. M13 defers checkpoint publication and the sync argument case to this report; M14 owns stale worktree registration in metadata. These are not duplicated here.
- No active backlog item already specifies the correctness remedies in F01–F11. The broader Files/editor surface convergence item is related context for sharing safe reads, not a substitute for F02's containment fix.
