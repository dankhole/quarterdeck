## Findings

### M10-F01 — P1 · Data preservation: Trash deletes task files after restore-patch capture fails

- **Anchor:** [task-worktree-lifecycle.ts](../../src/workdir/task-worktree-lifecycle.ts), lines 356–371; [task-worktree-patch.ts](../../src/workdir/task-worktree-patch.ts), lines 112–123.
- **Trigger:** A valid dirty worktree is trashed and patch capture fails, for example when its atomic patch write fails or a Git diff subprocess fails. The catch intended to tolerate partially created directories also covers valid worktrees with valuable changes.
- **Consequence:** Archive ignores the error, force-removes the worktree and returns `{ok:true, removed:true}`. The managed Trash caller sees success and supplies no archive warning. There is no saved restore patch. Capture also deletes older task patches before writing the replacement, so the old saved version is not a fallback when that write fails.
- **Evidence:** A disposable real Git repository/worktree contained an uncommitted tracked change. Only the final `.patch` write was fault-injected. The real archive path returned success, the checkout disappeared, and `findTaskPatch` returned null. Git and removal were not mocked. No user checkout was affected.
- **Smallest remedy:** Require a successful durable capture for valid worktrees before removal. Distinguish a positively identified disposable partial directory from a failed capture of a registered checkout. Publish the new archive before retiring an older archive and surface failure while preserving task files.
- **Validation needed:** Failed diff, failed patch write and failed archive replacement must preserve the checkout and any earlier archive. Verify the lifecycle response exposes that failure and retry remains safe.

### M10-F02 — P1 · Data preservation: clean detached task commits disappear from Trash restore

- **Anchor:** [task-worktree-patch.ts](../../src/workdir/task-worktree-patch.ts), lines 81–95 and 112–115; [task-worktree-lifecycle.ts](../../src/workdir/task-worktree-lifecycle.ts), lines 174–176 and 266–295.
- **Trigger:** A task uses the supported detached-worktree path, commits its work without updating its base branch, then enters Trash with a clean worktree. This also applies when named-branch creation fell back to detached mode.
- **Consequence:** Capture computes a diff against the task's current HEAD. A clean checkout produces no patch and therefore no saved HEAD identity. After removal, restore selects the task's original base ref and silently recreates the pre-task content. The removed detached HEAD has no archive ref protecting it; this check proves immediate restore loss, not eventual garbage collection.
- **Evidence:** Created a real detached task worktree, committed changed `file.txt`, archived it and restored through the production ensure function. Both operations succeeded; no patch existed, restored HEAD differed from the task commit and the file contained the original base content. Managed restore passes `card.baseRef` and `card.branch`; it does not persist/use the prior `baseCommit` to compensate for the missing archive.
- **Smallest remedy:** Persist the checkout HEAD independently of whether a dirty patch exists, and protect it with an owned Git ref for the archive's lifetime. Restore that HEAD plus any dirty patch, with explicit conflict handling for a named branch that moved. Retire the archive/ref only after successful restore or permanent deletion.
- **Validation needed:** Clean detached commits, dirty changes on detached commits, an advanced base branch and repeated archive/restore. Verify archive refs retain commits across pruning before restore.

### M10-F03 — P2 · Ownership/isolation: project-local task IDs address global worktrees and patches

- **Anchor:** [task-worktree-lifecycle.ts](../../src/workdir/task-worktree-lifecycle.ts), lines 53–64, 127–140 and 67–82; [task-worktree-patch.ts](../../src/workdir/task-worktree-patch.ts), lines 13–18, 39–43 and 112–123; [task-worktree-identity.ts](../../src/workdir/task-worktree-identity.ts), lines 17–30.
- **Trigger:** Two projects have the same task ID. [task-id.ts](../../src/core/task-id.ts) normally creates five-character UUID prefixes and [task-board-mutations.ts](../../src/core/task-board-mutations.ts), lines 310–316, checks uniqueness only within the current board; explicit IDs are likewise board-scoped. Cross-project equality is valid input and can also happen naturally.
- **Consequence:** Worktree paths include the task ID and repository basename, with no project identity. Same-basename repositories reuse one checkout: backlink validation proves the checkout owns its Git admin entry but does not prove that entry belongs to the requested repository. Purging the other project's task falls through from failed Git removal to raw directory removal and deletes the first project's checkout. Even with different repository basenames, restore patches are globally keyed only by task ID, so capturing or purging one project's patch destroys another project's archive. Locks live in different Git common directories and do not establish shared ownership over this collision.
- **Evidence:** Two real independent `repo` directories with different committed content and the same task ID returned the exact same task path; ensuring project B returned project A's content. Purging B deleted A's checkout. A second real fixture with different repository basenames showed B's capture deleting A's patch and replacing it with B's changes. These are deterministic collision checks, not a claim that a random collision occurred in the user's data.
- **Smallest remedy:** Use `(project identity, task identity)` for worktree, archive and lock ownership, and verify the expected Git common directory before reuse/removal. Migrate existing artifacts with explicit ownership evidence; never claim a legacy artifact solely because its basename/task ID matches.
- **Validation needed:** Matching IDs across same/different repository basenames, independent concurrent operations, foreign valid registration rejection, and legacy archive migration without overwriting either project's data.

## Uncertain candidates and overlap

- Archive/purge recompute the default path while launch can reuse a persisted `workingDirectory`. A valid relocated worktree could therefore be left behind; establishing the supported path-migration caller is still needed before scoring this separately.
- Filesystem setup locks prevent deletion during setup, but do not establish PTY ownership. M05 identified lifecycle archive/purge outside the runtime task-resource coordinator. M13 owns the remaining caller/admission investigation; it is not counted again here.
- Copy traversal and legacy-link cleanup have filesystem mutation windows between checks and use. No concrete supported caller or race reproduction was established in this pass, so these are not security findings.
- Per-untracked-file diff subprocesses, recursive legacy cleanup and in-memory patch accumulation may matter for large worktrees. No benchmark was run; this report makes no measured performance-regression claim or file-size-only architecture recommendation.
- Checked the current backlog for worktree/archive overlap. These three data-preservation/ownership findings are distinct from already tracked work and M05's operation compensation failures. No fixes were applied.
