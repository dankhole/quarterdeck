## Findings

### M09-F01 — P2 · Process ownership: failed Claude initialization loses a still-live replacement PID

**Anchor:** [claude-structured-owner.ts](../../src/execution/claude-structured-owner.ts), lines 752–792, especially the late `onProcessStarted` at 792; failure handling at 851–859. Consequential caller: [task-execution-ownership-service.ts](../../src/execution/task-execution-ownership-service.ts), lines 571–574 and 1465–1505.

**Trigger and impact:** a Claude child starts, then initialization times out or its session/cwd/configuration fails validation, and closing the SDK does not confirm child exit within three seconds. The registry throws `StructuredOwnerStopUnconfirmedError`, but it has neither registered an owner nor called the callback that persists its PID. Ownership remains processless. A subsequent explicit restart consequently takes `reconstructWithoutStop` and starts another child before the first child's exit is established. Startup recovery has the same missing evidence. This defeats the required stop-before-replacement fence and loses the ability to target that first process through the ownership service.

**Evidence:** Codex publishes its process immediately before initialization; Claude only publishes after both initialization and all compatibility checks. A real coordinator/store plus stub-SDK check produced `lastFailure=stop_failed`, `ownerProcess=null`, no registry owner, and two successive SDK launch attempts. A separate process check used the **installed SDK 0.3.241 with a synthetic Node JSONL child**, not Claude: invalid init returned `StructuredOwnerStopUnconfirmedError`; the PID remained alive (`kill(pid, 0)` succeeded); publication count was zero and registry lookup was null. The child was explicitly killed and awaited. The installed SDK's transport allows two seconds before TERM and another five before KILL, so Quarterdeck's three-second wait can expire before SDK escalation finishes. No concurrent provider writes or history corruption were exercised or claimed.

**Smallest remedy:** capture and durably publish the spawned process identity before provider initialization/resume can proceed. Retain a stop-capable starting-owner record until exit is confirmed; initialization failure must not present a processless reconstructible state while that child may survive. Preserve the existing generation/session compare-and-set check.

**Validation needed:** retain the synthetic child test and cover initialization timeout, compatibility failure, publication failure, delayed exit and a second restart/recovery attempt. Assert that no replacement launches until the exact prior process is confirmed gone.

### M09-F02 — P2 · Permission preservation: enablement-only Claude arguments activate bypass during handoff

**Anchor:** [claude-structured-owner.ts](../../src/execution/claude-structured-owner.ts), lines 239–244 and 744–745.

**Trigger and impact:** an inherited Claude command contains `--allow-dangerously-skip-permissions` without selecting bypass mode. `validateClaudeNativeArgs` treats that enablement flag identically to `--dangerously-skip-permissions`, sets `permissionMode=bypassPermissions`, and supplies that active mode to the SDK. Handoff therefore changes the permission policy instead of preserving it. With a separately supplied ordinary mode, the same valid enablement argument instead creates a configuration conflict.

**Evidence:** native `inherit` preserves the configured flags in [agent-session-adapters.ts](../../src/terminal/agent-session-adapters.ts), lines 246–249; its existing test explicitly preserves plan mode plus the enablement flag. M08 confirmed this production path and does not duplicate this finding. The installed SDK types distinguish `permissionMode` from `allowDangerouslySkipPermissions` (sdk.d.ts, lines 1777–1798), and SDK argument construction emits them separately. A registry test with inherited enablement alone captured both `permissionMode: bypassPermissions` and `allowDangerouslySkipPermissions: true`, and accepted the returned owner. This proves option translation, not execution of an unapproved real tool.

**Smallest remedy:** track bypass enablement separately from the selected permission mode. Only explicit mode selection or the actual skip flag may activate bypass; preserve native inherit semantics and reject combinations only when they are genuinely incompatible.

**Validation needed:** capture SDK options for enablement alone, plan/default plus enablement, actual skip, explicit managed modes and argument-order variants; ensure native and structured modes agree.

### M09-F03 — P2 · Configuration preservation: accepted Claude settings files are silently omitted from the SDK launch

**Anchor:** [claude-structured-owner.ts](../../src/execution/claude-structured-owner.ts), lines 264–268 and 736–761; manifest construction at 622–640.

**Trigger and impact:** the configured native command supplies `--settings /path/custom-settings.json`. The structured adapter accepts and fingerprints its path, labels it as Quarterdeck hook settings, but never passes its contents or path to `query({ options })`. User flag-layer settings—including permission rules, sandbox settings or model choices—are silently removed. On first handoff there is no previous structured configuration fingerprint, so validation simply accepts the replacement's changed observed configuration.

**Evidence:** [task-session-start-service.ts](../../src/server/task-session-start-service.ts), lines 342–347, supplies resolved command arguments, not only generated hook arguments; [runtime-server.ts](../../src/server/runtime-server.ts), lines 218–246, uses that preparation for handoff. Therefore arbitrary configured `--settings` input reaches this parser. The installed SDK exposes `Options.settings` specifically as the CLI flag-settings equivalent (sdk.d.ts, lines 1960–1979). The synthetic registry test accepted a custom path while captured `options.settings` was undefined. `settingSources: [user, project, local]` does not include the missing flag layer.

**Smallest remedy:** distinguish Quarterdeck-generated hook settings from configured user settings. Preserve the latter through the SDK `settings` option, with narrowly scoped removal/replacement of Quarterdeck-owned hooks if needed; alternatively reject unsupported settings before stopping the native owner. Do not declare arbitrary paths to be owned hook settings.

**Validation needed:** supply a synthetic settings file with a distinctive ordinary setting and permission rule, verify effective preservation across handoff/restart, and separately test replacement of generated native hooks without duplicating them.

### M09-F04 — P2 · Recovery: crashed interaction receipts permanently block new commands

**Anchor:** [task-execution-ownership-service.ts](../../src/execution/task-execution-ownership-service.ts), `recoverProject`, lines 672–906; dispatch at [task-interaction-service.ts](../../src/execution/task-interaction-service.ts), lines 171–190. The durable reservation is [project-execution-ownership-store.ts](../../src/state/project-execution-ownership-store.ts), lines 553–565.

**Trigger and impact:** the runtime exits after `beginInteraction` persists a `pending` operation and before `finishInteraction`. Recovery reconstructs the exact owner and classifies its old turn, but never settles the abandoned interaction receipt. The journal rejects every new operation of the same task/kind as `busy`, including operations for a newer owner generation. Retrying the old operation only returns `turn_outcome_unknown`; it does not release the reservation. Further owner restarts preserve the stuck receipt. A crashed message can thus disable all subsequent explicit messages indefinitely; answer/stop reservations have the same shape.

**Evidence:** a real durable-store/service/coordinator check seeded the precise crash state with generation 3, recovered the owner to generation 4 with `turn_outcome_unknown`, and submitted a new explicit message. Recovery succeeded, but the new message returned `busy`; the old receipt still had `status=pending`. Provider start/resume/history behavior was a deterministic protocol stub. No production recovery path updates interactions, and journal pruning deliberately retains every pending receipt.

**Smallest remedy:** as part of fenced owner recovery/replacement, settle abandoned prior-generation interactions as `outcome_unknown` (or a stronger proven terminal outcome), preserving their idempotency receipts without retaining an active reservation. Never replay the old message. Distinguish an operation still running in the current runtime from one whose owner has been replaced.

**Validation needed:** restart across each boundary from durable begin through dispatch and completion persistence, then verify old-ID replay remains non-dispatching and a distinct new command is admitted. Include message, answer and stop kinds.

### M09-F05 — P2 · State projection: resolved structured interactions cannot restore Running through the real store

**Anchor:** [session-state-machine.ts](../../src/terminal/session-state-machine.ts), lines 1386–1423, reached from [task-execution-ownership-service.ts](../../src/execution/task-execution-ownership-service.ts), lines 1590–1602. Normalization: [task-session.ts](../../src/core/api/task-session.ts), lines 254–269.

**Trigger and impact:** an addressed structured question/approval resolves while its turn continues. The structured reducer returns Running and work evidence but retains an `outstandingInteraction` marked `response_submitted`. `InMemorySessionSummaryStore.applySessionEvent` always normalizes that patch; any outstanding interaction forces Review and clears the evidence. Thus the provider-owned resolved callback cannot actually resume Running, and the task stays in Review until completion or another interaction transition. Structured providers do not supply the native PTY proof that would retire this record later.

**Evidence:** production manager calls the same normalized store. The focused synthetic caller-path test first established structured Running, opened a Claude question, then resolved it. The reducer patch was `state=running`; the returned/stored summary was `awaiting_review/attention`, `response_submitted`, `nativeWorkEvidence=null`. Existing reducer-only assertions miss this difference. M06 raised the candidate; M09 owns the confirmed cross-boundary finding.

**Smallest remedy:** make the structured resolution contract explicit and consistent. If this callback is accepted resumption evidence, retire the exact resolved structured interaction in the same transition; if it only confirms submission, add the provider's real resumption event rather than returning a Running patch that normalization discards. Preserve native PTY response-pending semantics.

**Validation needed:** test through `TerminalSessionManager`/the real normalized store for both providers, including provider-resolved callbacks, local answer submission, subsequent work, completion and owner loss. Assert final classifier output and evidence, not just the reducer patch.

### M09-F06 — P2 · Interaction identity: reverse-order Codex answers leave an already-answered wait active

**Anchor:** [codex-structured-owner.ts](../../src/execution/codex-structured-owner.ts), lines 270–273; [session-state-machine.ts](../../src/terminal/session-state-machine.ts), lines 1344–1363 and 1386–1397.

**Trigger and impact:** Codex issues concurrent keyed callbacks A then B. Each request overwrites the singular summary interaction, so B is displayed. Answer B first: the owner suppresses its resolution because A remains pending. Answer A last: it emits resolution for A, which the reducer rejects because the stored prompt ID is B. All provider callbacks are answered, yet the authoritative summary still advertises B as `waiting`/Needs Input. Even fixing F05's normalization does not resolve this mismatched identity; while only A remains, the projection also continues advertising B.

**Evidence:** a synthetic protocol test crossed the actual client, Codex owner, ownership service, task coordinator and normalized store. Two `item/fileChange/requestApproval` callbacks were answered B then A. `owner.listPendingInteractions()` returned zero while the summary still contained B with `status=waiting`. The provider transport was stubbed; no claim is made about a measured real-provider callback frequency.

**Smallest remedy:** derive structured attention projection from the current keyed pending set after every request/resolution, choosing an actually pending representative when one remains and clearing it when none remain. Preserve the singular native foreground model; do not suppress a resolution solely because another keyed callback exists.

**Validation needed:** request/answer both orders, provider-side resolution, one callback failing/cancelling, and turn completion with callbacks still queued. Verify exact pending identities and the shared task indicator together.

## Uncertain candidates and disposition

- **Codex availability mismatch — confirmed limitation, no automatic-upgrade recommendation.** Native launch requires `>=0.157.0` (`agent-registry.ts:72`), while structured execution accepts exactly `0.149.1` and history through that version (`codex-app-server-protocol.ts:10`, `codex-structured-owner.ts:34–35,450–460`, ownership service 1040–1045). No installed version satisfies both current gates. The exact pin is an explicit compatibility contract and this feature is internal-only; changing the constant without protocol/history validation would be unsafe. Product ownership should decide whether to validate a current tuple or mark Codex structured handoff unavailable. Fake 0.149.1 tests are not evidence of current native-to-structured compatibility.
- **Startup native recovery versus pending ownership — not promoted.** The carried M05 candidate did not establish a valid pending structured-owner race: `project-registry.ts:679–695` excludes non-native/pending owners and non-PTY owners before queueing native recovery. A later mutation after selection would need a concrete production interleaving; none was demonstrated here. M05-F03 already owns successful native Restart replay effects. This pass does not certify all lifecycle/startup combinations.
- **Claude initialization timing — real-provider gate remains open.** Tests verify SDK interfaces and synthetic protocol behavior, not whether every accepted Claude 2.1.x native executable emits the required idle resume/init sequence or maintains the assumed exact-history compatibility. No provider was launched.
- **Interaction presentation loss — design follow-up.** `TaskAttentionRequest` flattens question text/options and omits Codex question IDs, per-question answer structure and MCP elicitation schema/URL. The internal owner needs those IDs/shapes to answer. There is no current presentation consumer to establish its full intended contract, so this is not counted separately; settle it before connecting a client.
