# Desktop acceptance gates

The supported release design is npm-owned desktop distribution: public ad-hoc-signed macOS (`adhoc-v1`) and unsigned Windows (`unsigned-v1`), without paid signing membership. Local packaged evidence does not establish every native acceptance gate below. Every new release must build and publicly verify macOS ARM64/x64 and Windows ARM64/x64 assets, regardless of `QUARTERDECK_DESKTOP_RELEASES`; there is no browser-only release path. Linux shared checks and internal headless testing remain, not a standalone graphical product. Apple signing/notarization and stable Developer ID continuity are optional-lane gates, not prerequisites for free desktop distribution.

Use [testing scope](./testing.md) to select checks and the [release runbook](./desktop-release.md) for packaging and acceptance procedures. Execution work belongs in the primary checkout's Chit backlog. This page is a compact gate summary; the [frozen candidate evidence](./history/desktop-validation-evidence.md) preserves exact identities, executed commands, failures, limitations, and cleanup receipts recorded through 2026-10-19. Those historical results apply only to their named artifacts and unchanged behavior, not automatically to the current tree.

## Open acceptance gates

### Windows candidate scope

On Windows 11 x64 (build 26200), local candidate `b2a9c7e3-95dd-424d-b1dc-66b0490ef738` (version `0.12.16`, dirty source based on `eb48ff97`) passed packaged Node 22.22.2 / ConPTY verification, with implicit `cmd.exe` current-directory lookup disabled. Quarterdeck's installer decoder extracted the actual Forge ZIP and the verifier checked its contents against the manifest. ZIP SHA-256: `e974cd27ce1567cfe9cb296da5a59f0ac148092130fad40230c13436a1396e9f`; manifest: `desktop/out/artifact-manifest-win32-x64.json`. This is an inspection-enabled local candidate, not a public release.

The isolated packaged smoke (`test-results/agent-lab/desktop-smoke-20261123T200649Z-d57ff2/`) exercised fake-provider ConPTY work via bare `node` in an agent shim, same-instance launch, renderer crash/recovery, and actual Chromium/crashpad job membership. A separate startup-recovery run (`test-results/agent-lab/desktop-smoke-20261123T201258Z-628255/`) covered refusing unclean custody, cancellation leaving startup blocked, and recovery after explicit confirmation. Both runs recorded graceful Quit without fallback, replacement refusal while live, successful replacement and uninstall, preserved synthetic user state, and no remaining processes in `windows-installation-lifecycle.json` and `desktop-manifest.json`. Native fault-injection tests separately cover killed monitors, durable launch markers, transactional recovery, and Explorer-brokered external PowerShell on hosts with a registered automation desktop. The hosted Windows ARM64 runner can have a shell window without that registration. In that case the native test uses a separate COM lookup to confirm the missing prerequisite, then requires the production helper to refuse without starting a worker. That exercises refusal, not a successful update; the latter still needs an interactive ARM64 desktop.

The packaged Windows focus regression check failed before the Settings focus fix and passed in both the narrow scenario and full smoke on x64 candidate `660a467f-40b8-4f3a-b9c9-d59f249e4ebc` (dirty source based on `837b16e6`). The full run's `test-results/agent-lab/desktop-smoke-20261123T204617Z-f3b523/windows-terminal-focus.json` records input acknowledgements from the same task PTY before and after Escape, without refocusing. The run quit gracefully without fallback or leftover processes. The [physical Ctrl+V check](windows-native-smoke.md#manual-physical-ctrlv-acceptance) remains unrun on a disposable Windows desktop.

Windows implementation is enabled. Public publication and actual npm N-to-N+1 updating still require a new immutable release; this candidate cannot replace published `0.12.16` assets. Native ARM64 build/lifecycle checks are required by the Windows CI/release matrix and were not executed on this x64 host. Minimum Windows 10 hardware, SmartScreen/user approval, visible OS interaction, and real-provider compatibility require their own evidence. Synthetic Start menu links and profile directories do not prove a real user's shell experience.

## Recording a gate result

Keep a gate result concise: source SHA and dirty status, product/build identity, architecture/OS, artifact hashes, exact scenario or command, result, evidence location, and cleanup outcome. Release candidates require clean immutable source. Preserve failed and partial results with their limits; do not infer a passing gate from them or substitute fake evidence for a failed real-provider check.

Use the repo-owned functional-testing skill and isolated Agent Lab for packaged functional claims. Always stop the run, inspect cleanup, use synthetic data, and reserve screenshots for visual claims. The lab is not proof of signing, production installation admission, hardware/OS coverage, actual Dock aliases, or elapsed daily use. Current operating procedures belong in [desktop architecture](./desktop.md), [environment resolution](./desktop-environment.md), and the [release runbook](./desktop-release.md); verbose historical receipts remain in the archive.
