# Desktop acceptance gates

The macOS desktop implementation has local source and unsigned ARM64 packaged evidence. Public distribution remains gated by the unperformed checks below. An implemented workflow, a configured runner, or an unsigned synthetic run does not establish signed release readiness.

Use [testing scope](./testing.md) to select checks and the [release runbook](./desktop-release.md) for packaging and acceptance procedures. Execution work belongs in the primary checkout's Chit backlog. This page is a compact gate summary; the [frozen candidate evidence](./history/desktop-validation-evidence.md) preserves exact identities, executed commands, failures, limitations, and cleanup receipts recorded through 2026-10-19. Those historical results apply only to their named artifacts and unchanged behavior, not automatically to the current tree.

## Open acceptance gates

These requirements survive the archived design plans. Close a gate only with evidence for the relevant final candidate; retain unsupported or untested combinations explicitly.

| Gate | Required evidence |
| --- | --- |
| Signing and notarization | Provision the protected `desktop-signing` environment. Verify native ARM64 and Intel app/DMG notarization, nested signatures/team, staples, hardened runtime, entitlements, release fuses, final manifests and checksums. |
| Clean-user Gatekeeper and Keychain continuity | Download signed artifacts with quarantine intact, install and launch online/offline with Gatekeeper enabled, and retain encrypted state across signed N-to-N+1 replacement without renewed identity-related Keychain consent. Follow [Keychain continuity](./desktop-release.md#keychain-continuity); mock-keychain lab runs do not cover it. |
| Native Intel and minimum macOS | Native Intel build, launch, PTY and lifecycle evidence; downloaded installation and core workflows on the declared macOS 13 minimum for supported architectures. Change the declared floor if it cannot be supported and verified. Current-host ARM64 execution and cross-builds cannot establish these gates. |
| Public unified installation | Matching signed ARM/Intel assets available through the exact anonymous installer URLs before npm publication; fresh global npm install, matching CLI and Finder/Dock launch, default supported npm lifecycle policy, and independently verified immutable release identity. |
| Signed npm N-to-N+1 update | Actual macOS Terminal presentation and exact-version update in the recorded prefix; normal draft/session cancellation and clean shutdown; offline/corrupt/missing downloads, disabled hooks, permissions/full-disk failures, interruption/repair, owner changes, and ready-pair verification. Preserve projects, profiles, drafts and provider identity. No forced process termination or mixed-pair startup. |
| Production launch/replacement race | Actual Finder/Dock launch versus replacement, including already-loaded old native bootstrap and surviving bundle-dependent helpers. The synthetic native race establishes only its recorded fixture. No process may execute mixed/replaced bundle bytes; live or unverifiable use blocks replacement. |
| Legacy copies and Dock migration | Verify an actual old Dock alias and its replacement target. Retain unknown, modified or running copies; unguarded legacy copies require explicit safe manual/offline migration. Synthetic direct-path launch does not prove alias migration. No ordinary installation rewrites the Dock or deletes uncertain apps. |
| Native OS experience | Actual folder-picker cancellation/focus, clipboard text/images, notification permission/click/replay and hidden delivery, desktop/browser audio deduplication, physical Dock interaction, display removal/fullscreen, sleep/wake, and VoiceOver. Hidden or simulated effects do not prove OS presentation. |
| Supported providers | Narrow, explicitly authorized packaged checks for Claude and the exact Pi release in `src/config/agent-registry.ts`, including trust, interaction, hooks, approvals, stop and exact resume. Keep Codex evidence scoped to its tested version and scenario; explicit Deny and natural completion were not tested in the recorded check. |
| Performance and sustained use | Comparable fixtures with responsive input/navigation, bounded startup failure, no idle busy loop or continuing process/memory growth across repeated task/window cycles. Existing navigation/idle samples are bounded observations; input/startup/growth remain unmeasured. Complete five working days on a named candidate with user-controlled real projects, multiple agents, close/reopen, overnight sleep, reconnect and an update, without unresolved data-loss, duplicate-agent, shutdown or installation blockers. |
| Final shared/platform regression | Required Linux/macOS/Windows build, root/web checks and packed npm/native platform smoke on the final reconciled source and actual distributables. Local browser and earlier candidate tests do not establish the final cross-platform result. |

## Recording a gate result

Keep a gate result concise: source SHA and dirty status, product/build identity, architecture/OS, artifact hashes, exact scenario or command, result, evidence location, and cleanup outcome. Release candidates require clean immutable source. Preserve failed and partial results with their limits; do not infer a passing gate from them or substitute fake evidence for a failed real-provider check.

Use the repo-owned functional-testing skill and isolated Agent Lab for packaged functional claims. Always stop the run, inspect cleanup, use synthetic data, and reserve screenshots for visual claims. The lab is not proof of signing, production installation admission, hardware/OS coverage, actual Dock aliases, or elapsed daily use. Current operating procedures belong in [desktop architecture](./desktop.md), [environment resolution](./desktop-environment.md), and the [release runbook](./desktop-release.md); verbose historical receipts remain in the archive.
