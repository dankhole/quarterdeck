## 2026-08-23 — Codex-first task-title generation

Task-title generation no longer depends on the configured OpenAI-compatible helper endpoint as its primary path. The title generator owns one simple provider policy: `codex` by default, `llm` when explicitly selected, or `local`, with every remote provider degrading directly to the deterministic local title. Codex and LiteLLM therefore remain sibling mechanisms rather than a hidden retry chain across unrelated failure domains. `QUARTERDECK_TITLE_PROVIDER=llm|local` changes policy without changing the title-generation API; branch names, commit messages, and optional summary polish retain their existing lightweight-helper ownership.

The Codex mechanism launches `codex exec --ephemeral` with saved authentication, read-only sandboxing, no user config or repository rules, and an isolated temporary working directory. CLI and HTTP generation share provider-neutral response cleanup. Codex uses the same core Windows command resolver as agent probes and the same core timeout termination owner as shortcut processes; its promise settles at the 20-second deadline even if a process ignores termination, while Windows `.cmd` descendants receive tree cleanup and detached stdio cannot hold the runtime open. Tests force local title generation globally so integration fixtures cannot discover the developer's real Codex binary or spend account usage; provider tests opt into mocked paths. Notable files: `src/title/codex-client.ts`, `src/title/generation-response.ts`, `src/title/title-generator.ts`, `src/core/windows-cmd-launch.ts`, `src/core/process-termination.ts`, and `vitest.config.ts`. ## 2026-08-23 — Bounded startup chat recovery

Fresh runtime startup could launch every interrupted task concurrently, before orphan-agent cleanup completed, through a registry-only path that skipped the worktree/agent preparation used by manual Restart. A PTY spawn was treated as success even when the underlying chat never initialized, while a clean early resume exit could silently replace the targeted conversation with a fresh prompt. Dogfood history showed interrupted sessions launching within milliseconds of one another; manually restarting the affected cards consistently recovered them.

Startup recovery now uses one global serialized coordinator and a two-phase shared task-start service. After orphan cleanup it prepares the task exactly once—resolving the prior agent, command, missing worktree, launch settings, and original stored resume target—then retries only clones of that frozen launch request. Deterministic preparation failures are surfaced immediately instead of repeated. The first process gets a conservative 45-second readiness window to accommodate busy runtime startup, while the second gets 20 seconds and can only be left running with a warning; structured logs include preparation, launch, readiness, and limit timings so dogfood can tune those values from evidence. Readiness requires a native hook tied to the exact spawned session instance and, when stored, the same conversation id. Mismatched hook metadata is rejected before it can replace that id, while hook accounting remains independent from launch admission.

Early exit, identity mismatch, launch failure, or first-attempt readiness timeout permits one exact stop-and-wait retry; explicit start/stop/input cancels ownership, unsafe PTY stop aborts the retry, and no path launches a third process. Exhausted recovery is applied through the terminal session state machine rather than a server-owned summary patch. A final non-zero targeted exit clears the id so the next manual Restart can use best-effort recovery, while a short post-hook stabilization check catches sessions that identify themselves and immediately die. Reconciliation ignores only the transient coordinator-owned window, and automatic startup recovery never invokes or races the legacy fresh-prompt/crash fallbacks. Notable files: `src/server/startup-session-recovery.ts`, `src/server/task-session-start-service.ts`, `src/server/project-registry.ts`, `src/terminal/session-launch-readiness.ts`, and the terminal lifecycle/reconciliation modules. Validation includes coordinator slow-start/frozen-retry coverage, a persisted-card registry-to-launch integration test, the root test suite, TypeScript, Biome, the agent-instruction bridge, and `git diff --check`.

## 2026-08-21 — Interactive hook lifecycle reconciliation

Dogfooding the replay-safe hook path exposed two lifecycle gaps above transport. Codex has no approval-resolved hook before an approved command completes, so a long command could remain visually review-ready until `PostToolUse`; additionally, sound detection only watched active-to-stopped column changes, so an already-stopped review card becoming approval-required was silent. A submitted carriage return now becomes a `user.responded` state-machine event only when the centralized indicator says the session genuinely needs input. The same direct Codex submission establishes an ordering boundary that rejects older permission observations arriving later. Ordinary review-card input, cursor navigation, protocol traffic, and PTY output remain state-neutral, while the existing single-key permission behavior for Claude and Pi is preserved.

Manual `/compact` now uses Codex's documented `PreCompact`/`PostCompact` hooks matched specifically on `manual`, giving the operation a paired running/review lifecycle without letting automatic mid-turn compaction stop active work. Compact hook chronology is tracked so replay cannot apply a delayed start after its finish. Audible notification state now tracks semantic event priority as well as task column, allowing review-to-permission and other stronger stopped-state edges to alert once while initial/unchanged state remains silent.

The blank terminal seen during the same dogfood pass was a separate presentation race: the control socket could restore a replacement PTY before the React `sessionStartedAt` effect reset xterm, after which no further restore was guaranteed. Pooled task resets now request the authoritative snapshot immediately; the existing socket coordinator either queues that request behind an in-flight restore or sends it after the earlier restore. Server-side inspection of the affected live task confirmed a populated 62 KB mirror while the UI had shown a blank pane. Notable files: `src/codex-hooks.ts`, `src/terminal/session-input-pipeline.ts`, `src/terminal/session-state-machine.ts`, `src/terminal/hook-event-order.ts`, `web-ui/src/hooks/notifications/*`, and `web-ui/src/terminal/use-persistent-terminal-session.ts`. ## 2026-08-21 — Replay-safe native hook delivery

Dogfooding exposed a native-hook delivery gap where Codex could visibly finish a turn or wait for approval while Quarterdeck remained in the previous state. The hook CLI's nominal retry budget also exceeded Codex's five-second command deadline, so a second attempt could be killed before completing. Reliable Codex transitions that carry native turn identity now write a private, minimal, ten-minute outbox record before making two bounded HTTP attempts; the runtime replays pending records and acknowledges them only after they are handled or safely classified as stale. Conversation text, tool input, and transcript paths are not stored in the outbox. Other hook sources keep the bounded direct retry without taking on replay semantics their payloads cannot safely order.

Replay safety is tied to the actual spawned process: each task launch receives a new session-instance id, while native Codex `turn_id` plus canonical `tool_name` chronology provides causal ordering within that process (`PermissionRequest` does not document `tool_use_id`, so Quarterdeck does not assume it). Duplicate deliveries, events from replaced processes, older observations, completed-turn events, and unrelated parallel tool completions cannot regress task state. Payloads without the new metadata preserve the previous behavior, and PTY output remains explicitly outside lifecycle inference. Notable files: `src/commands/hooks.ts`, `src/hook-transition-outbox.ts`, `src/terminal/hook-event-order.ts`, `src/terminal/session-lifecycle.ts`, and `src/trpc/hooks-api.ts`. Validation: focused hook/order/outbox tests, all 1,081 root tests, all 1,060 web tests, root and web typechecks, full Biome checks, the agent-instruction bridge check, and `git diff --check`.

## 2026-08-11 — Runtime session delivery classification

Runtime session ingest remains immediate and the active project still receives every coalesced summary update, including activity text. The delivery layer now compares each summary with the last store snapshot and only updates cross-project notification memory when the shared semantic task indicator changes; it only rebuilds project-list counts when a session crosses the `awaiting_review` boundary that can reproject an in-progress card into Review. ## 2026-08-07 — Claude restore geometry and rendering investigation

Claude task terminals now use the same pre-restore forced geometry update as Codex. The resize message is sent before `request_restore`, and a same-size Unix resize still emits `SIGWINCH`, so Claude redraws against the attached browser dimensions before the server mirror snapshot is applied. Other agents and shell terminals keep the normal restore path. Quarterdeck's injected Claude status line is now strictly opt-in: the global default is off, low-level launches require an explicit `true`, and Settings exposes the control under Harnesses.
