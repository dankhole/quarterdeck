## 2026-08-23 — Unified automatic diagnostics and lab evidence

Quarterdeck's diagnostic evidence previously lived in unrelated places: a console-thresholded runtime ring, a browser panel-owned buffer, terminal console dumps, and agent-lab state/log snapshots. Most evidence had to be enabled before reproducing a failure, a new agent had no stable way to discover a live runtime, and keeping the old UI while adding a flight recorder would have created two competing capture and filtering models.

The runtime now creates a private versioned descriptor plus an always-on bounded recorder before startup cleanup. Essential structured lifecycle records, warnings/errors, explicit marks, and recorder-health events flow through one redacting envelope into a 2,000-record memory tail and four rotating 2 MiB JSONL segments; journal writes are queued, batched, priority-preserving, and failure-isolated. An unwritable descriptor or journal degrades discovery/persistence without preventing Quarterdeck startup, and startup retains only the newest three dead stopped, failed, or unfinalized crashed instances. Console verbosity remains separate. Subsystems expose read-only bounded snapshot providers rather than diagnostic code reaching into private mutable state, and doctor findings only report evidence. Correlation covers runtime, task/session, browser client/connection, hook delivery, API request, terminal transport, and Git operation boundaries. Authenticated loopback routes and `quarterdeck diagnostics list|status|doctor|capture|watch|record|mark` let a later agent inspect the active or most recent retained instance without becoming a board client or mutating runtime ownership state.

The browser recorder now starts with the app rather than the panel, batches through a connection-scoped capability, and retains a bounded reconnect tail. The always-visible Diagnostics panel is a viewer and controller: opening it does not alter capture, while explicit deep recording is scoped, expires after at most 15 minutes, and still applies the default redaction/prohibition policy. The old runtime/browser debug-log ring, WebSocket messages, frontend hooks/domain modules, and panel were deleted. In the isolated lab, the same recorder switches automatically to the rich synthetic profile; every lifecycle checkpoint is a canonical bundle and indexes fixture state, Git state/diffs, logs, browser artifacts, terminal viewport evidence, and a before/after-marked Playwright action transcript. Production capture does not inherit those content exceptions. Notable files: `src/diagnostics/*`, `src/commands/diagnostics.ts`, runtime/terminal/project diagnostic producers, `web-ui/src/diagnostics/*`, `web-ui/src/components/diagnostics/*`, `scripts/agent-lab/*`, and `scripts/agent-browser.ts`. Validation includes sanitizer, recorder/journal, descriptor, bundle, authenticated HTTP, CLI, provider/doctor, browser recorder, terminal-provider, and lab unit coverage; root/web TypeScript and Biome; focused runtime/web tests; and an isolated live lab smoke. ## 2026-08-23 — Task close/reopen lifecycle serialization

Dogfooding exposed a cross-layer race when a task was trashed and restored before the earlier trash workflow finished. Restore waited for the old PTY exit, recreated the task worktree, and launched the replacement conversation, but the still-pending trash cleanup could then delete that newly active worktree. Codex remained alive yet rejected every new turn with `invalid cwd`; because no completion hook followed, the card stayed in Running. Trashing and restoring the task a second time repaired it by recreating the checkout after the stale cleanup had settled.

The browser now owns one keyed FIFO boundary for every task operation that creates, stops, or removes task resources. It covers the full trash cleanup and client-state commit and is shared by start, restore, restart, hard delete, and clear-trash paths without serializing unrelated tasks. The runtime composition root owns a second injected coordinator for task start/stop/worktree ensure/delete RPCs across clients and UI remounts. Both depend on the same `TaskResourceOperationRunner` port and coordinator implementation, but deliberately do not share mutable cross-layer state. The audit also found that stop-request normalization discarded `waitForExit`, making the intended safety wait a no-op. Stop now returns a typed outcome, and browser workflows continue cleanup, replacement launch, or permanent card removal only after a confirmed exit or an already-inactive session. Deletion remains refused while that task has an active, starting, auto-restarting, or startup-recovering session. Finally, the ten-second reconciliation sweep checks live sessions' `sessionLaunchPath`; a vanished directory routes through `SessionTransitionController` to error review, clears misleading hook activity, records an actionable warning, suppresses auto-restart, and requests PTY stop without claiming the process exited before its real exit callback. The invariant is that an older close may never delete a newer launch directory, cleanup may never follow an unconfirmed stop, permanent deletion may not release its task lock before committing client state, and a surviving process with an invalid cwd may never remain indefinitely Running. Notable files: `src/core/keyed-operation-coordinator.ts`, `src/core/task-resource-operation-coordinator.ts`, the board lifecycle hooks, `src/trpc/project-api-state.ts`, and the terminal reconciliation modules. Validation after merging local `main`: 1,145 root tests, 1,070 web tests, root and web typechecks, the web production build, targeted Biome checks, the agent-instruction bridge check, and `git diff --check`. The isolated lab started and stopped successfully during the original investigation. The Playwright CLI and Chromium were installed afterward, the browser binary cache was moved to the primary checkout for reuse by linked worktrees, and a wrapper-level browser launch/close smoke test passed. Commit: pending.

## 2026-08-23 — Agent Lab native-UI isolation boundary

Agent Lab previously relied on a disposable environment but left host integrations enabled. On macOS, `projects.pickDirectory` therefore found `osascript` and launched a native folder dialog outside Playwright's DOM, hanging remote automation until a human intervened. Binary presence was being treated as evidence of an interactive desktop, and the UI had to infer headless limitations by matching human-readable error strings.

Runtime launch configuration now owns an explicit `nativeUiAvailable` capability. All server-side picker, path opening, external-host URL opening, and Open-in-IDE operations go through one injected host-integration service that checks the capability before touching a launcher and returns typed failure reasons. Open in IDE no longer accepts browser-supplied shell text: the public contract carries a validated target ID, the server derives the trusted project path from request scope, and the host driver resolves trusted executable/argument arrays (including the shared escaped command-shim adapter where Windows requires it). Browser clipboard and notification audio actions use an injected matching gate that starts fail-closed and is configured only by the server's launch-derived runtime response. Ordinary and xterm links stay inside the isolated browser, where Playwright observes them and the lab's loopback-only network policy applies, rather than being mislabeled as host-native UI.

Agent Lab derives the runtime flag from its disabled launch capability, and the browser receives that same capability through the runtime-config response after starting fail-closed. The lab shadows known native picker/open/IDE commands with recording fakes, fails shutdown if any fake was invoked, and provides a second synthetic repository for the Add Project manual-path test. The key invariant is that launcher discovery may select an implementation only after launch configuration has authorized native UI; it must never establish the capability itself. Validation covers fail-closed injected spies for every audited integration class, typed Open-in-IDE request/path ownership and direct-argv resolution, enabled macOS picker behavior, TypeScript/Biome checks, and a Playwright lab run that added the second repository with an empty forbidden-launch log.

## 2026-08-23 — Bounded startup chat recovery

Fresh runtime startup could launch every interrupted task concurrently, before orphan-agent cleanup completed, through a registry-only path that skipped the worktree/agent preparation used by manual Restart. A PTY spawn was treated as success even when the underlying chat never initialized, while a clean early resume exit could silently replace the targeted conversation with a fresh prompt. Dogfood history showed interrupted sessions launching within milliseconds of one another; manually restarting the affected cards consistently recovered them.

Startup recovery now uses one global serialized coordinator and a two-phase shared task-start service. After orphan cleanup it prepares the task exactly once—resolving the prior agent, command, missing worktree, launch settings, and original stored resume target—then retries only clones of that frozen launch request. Deterministic preparation failures are surfaced immediately instead of repeated. The first process gets a conservative 45-second readiness window to accommodate busy runtime startup, while the second gets 20 seconds and can only be left running with a warning; structured logs include preparation, launch, readiness, and limit timings so dogfood can tune those values from evidence. Readiness requires a native hook tied to the exact spawned session instance and, when stored, the same conversation id. Mismatched hook metadata is rejected before it can replace that id, while hook accounting remains independent from launch admission.

Early exit, identity mismatch, launch failure, or first-attempt readiness timeout permits one exact stop-and-wait retry; explicit start/stop/input cancels ownership, unsafe PTY stop aborts the retry, and no path launches a third process. Exhausted recovery is applied through the terminal session state machine rather than a server-owned summary patch. A final non-zero targeted exit clears the id so the next manual Restart can use best-effort recovery, while a short post-hook stabilization check catches sessions that identify themselves and immediately die. Reconciliation ignores only the transient coordinator-owned window, and automatic startup recovery never invokes or races the legacy fresh-prompt/crash fallbacks. Notable files: `src/server/startup-session-recovery.ts`, `src/server/task-session-start-service.ts`, `src/server/project-registry.ts`, `src/terminal/session-launch-readiness.ts`, and the terminal lifecycle/reconciliation modules. Validation includes coordinator slow-start/frozen-retry coverage, a persisted-card registry-to-launch integration test, the root test suite, TypeScript, Biome, the agent-instruction bridge, and `git diff --check`.

## 2026-08-21 — Replay-safe native hook delivery

Dogfooding exposed a native-hook delivery gap where Codex could visibly finish a turn or wait for approval while Quarterdeck remained in the previous state. The hook CLI's nominal retry budget also exceeded Codex's five-second command deadline, so a second attempt could be killed before completing. Reliable Codex transitions that carry native turn identity now write a private, minimal, ten-minute outbox record before making two bounded HTTP attempts; the runtime replays pending records and acknowledges them only after they are handled or safely classified as stale. Conversation text, tool input, and transcript paths are not stored in the outbox. Other hook sources keep the bounded direct retry without taking on replay semantics their payloads cannot safely order.

Replay safety is tied to the actual spawned process: each task launch receives a new session-instance id, while native Codex `turn_id` plus canonical `tool_name` chronology provides causal ordering within that process (`PermissionRequest` does not document `tool_use_id`, so Quarterdeck does not assume it). Duplicate deliveries, events from replaced processes, older observations, completed-turn events, and unrelated parallel tool completions cannot regress task state. Payloads without the new metadata preserve the previous behavior, and PTY output remains explicitly outside lifecycle inference.
