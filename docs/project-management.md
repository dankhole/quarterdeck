# Project names, availability, and relocation

Project identity is the indexed `projectId`, independent of the project folder and its display name. The project state directory, board, tasks, groups, and session history retain that identity through naming and location changes.

## User behavior

- An unavailable folder remains in the project list and its saved board remains readable. Show **Folder unavailable** with **Locate folder…** and **Check again**. Unavailability never authorizes deleting project state.
- **Rename project…** sets an optional display name; clearing it restores the folder name. It has no filesystem or session effects.
- **Locate folder…** reconnects the existing project to a selected directory. It validates the directory and project mode, rejects another project's registered path, and repairs owned Git worktree links.
- **Rename folder on disk…** accepts one new folder name and derives the sibling destination on the server. It rejects existing destinations and does not implement a cross-volume copy/delete fallback. Registered descendant projects prevent this operation; externally moved descendants can each be located separately.
- Location changes stop task agents and shells. They preserve resume identities and leave sessions stopped for explicit restart.
- Location changes require exclusive use of the saved state by one runtime. Main Git checkouts and folder projects are supported; linked Git project roots need their Git layout repaired outside this operation.

## Ownership

1. The project index owns the optional display name, location, directory identity when available, and a metadata revision separate from board revisions. New metadata upgrades the index to version 4 so older runtimes cannot silently strip creation-time evidence. Existing version 1, 2, and 3 indexes remain readable.
2. Saved-state loading by project ID is independent of Git and root-directory availability and retains the existing project-state transaction boundary. Runtime availability observation controls filesystem and process admission, not retention. Native terminal input and provider hook ingest report already-running processes and change only runtime state, so they skip the per-request directory and Git probe; project admission, scope revalidation, and a pending relocation journal still fence them. Startup outbox replay applies the same journal fence and leaves those hooks pending.
3. One project-wide operation gate drains existing work and fences new operations during relocation. Every admitted operation revalidates its scope after waiting. Task lifecycle and durable board changes retain their existing owners.
4. A relocation filesystem service validates paths and exact worktree ownership, performs the rename and Git repair, and owns a bounded journal in stable Quarterdeck state. Runtime orchestration stops execution owners, shells, metadata/code-navigation work, and persistence writers before applying relocation.
5. Existing managed worktrees keep their physical paths, even when their folder label reflects the former project name. Persisted task paths govern later archive, restore, and deletion. Paths within the old project root are rebased at directory boundaries; opaque provider identities are never rewritten.
6. The runtime refreshes remembered paths, managers, configuration, and metadata before publishing authoritative project state and summaries. The browser preserves project/task identity, invalidates old path scopes, guards dirty editor buffers before requested moves, and preserves recovery drafts when paths change externally.

Management endpoints are `projects.rename`, `projects.locate`, `projects.renameFolder`, and `projects.checkAvailability`. Location requests capture the expected current path. Results carry the updated summary and authoritative state when needed. Availability and metadata ordering must not depend on board revision. These required operations are part of the [browser/runtime compatibility contract](../DEVELOPMENT.md#browserruntime-compatibility).

## Failure and identity rules

Validate before stopping sessions, then revalidate under exclusive admission. Passive availability checks and managed disk renames require the known directory identity to match. Explicit Locate permits an identity change, including a remounted drive or a move across volumes, after structural validation of the selected folder. Any existing task worktrees require exact administrative-link evidence; matching Git remotes or commits is never proof of worktree ownership. The selected directory's current identity then guards the remaining operation and recovery.

The relocation journal records the old and new locations and filesystem identity before effects. Interrupted operations are resolved before startup recovery. Failures preserve task files and saved state; ambiguous recovery remains blocked with an actionable error. Recovery must neither create a second project nor launch a task against the old location.

On macOS, new directory identities record the inode and native nanosecond creation time as well as the device number. Matching creation-time evidence and inode tolerate device-number changes across mounts or restarts; a changed inode or creation time rejects a replacement directory. Other platforms and legacy records without creation-time evidence continue to require the exact device and inode. Creation time is filesystem evidence, not a volume UUID: a cloned volume preserving both inode and creation time cannot be distinguished by this fingerprint, and a deliberately changed creation time conservatively requires Locate.

After runtime admission, startup upgrades accessible legacy records under the project-index lock only when their existing identity still matches. Projects without historical identity can acquire it; pending or unreadable relocation journals are skipped. An already-mismatched legacy record cannot safely acquire creation-time evidence automatically: use **Locate folder…**, including selecting the same path, to explicitly reconnect it once. This preserves its project ID, board, and provider resume identities. New relocation journals use version 2; version 1 journals remain readable and retain strict legacy matching.

Locate can retry a pending rename using its exact journaled destination even when the filesystem move has not happened yet. Recovery still verifies the recorded source identity before moving it; selecting an unrelated destination cannot redirect the pending operation.

Destination existence and identity are checked immediately before the filesystem rename and identity is checked afterward. Node's portable rename API has no atomic no-replace option; an unrelated process creating an empty destination between the check and rename remains a platform limitation.

## Diagnosing availability

Git projects require both directory access and a successful Git root check; folder projects bypass Git. The root check is tri-state. A definite failure (not a repository, root mismatch, Git not installed, permission denied) makes a Git project unavailable while folder projects remain accessible. An indeterminate one proves nothing about the repository: a timeout, launch fence, cancelled or overlong process-queue wait, a kill by a signal the runtime did not send (for example the OOM killer), a resource-exhaustion spawn error (`EAGAIN`, `EMFILE`, `ENFILE`, `ENOMEM`), any other end without an exit status, and on Windows spawn `EPERM`/`EACCES` or an NTSTATUS crash code. Resource pressure on the folder checks themselves (`EMFILE`, `ENFILE`, `EAGAIN`, `EBUSY`, `ENOMEM`) is indeterminate too. An indeterminate observation never marks the project unavailable or touches the project index.

Instead it reports the last definite verdict recorded for the exact same project scope (folder path, folder-only mode, and directory identity). After an indeterminate Git probe the folder checks have just passed, so only an `available` or `not_git_repository` verdict carries forward; an earlier missing, relocation-pending, or invalid-location finding was disproved. After an indeterminate folder check, any same-scope verdict carries forward. Without eligible evidence (the first observation, a scope change without a rebind, or a disproved finding), an accessible folder is provisionally available and an unreadable relocation journal stays relocation pending. Neither substitute is recorded, so the next definite answer is compared only with real evidence, and the runtime re-probes in the background after 1, 3, and 10 seconds. If indeterminacy persists, a carried-forward or provisional answer can go stale; launches never rely on it, and a Git operation against the path still fails with its own definite error. Projects saved before directory-identity tracking have weaker evidence, since their scope match compares only path and folder-only mode.

Directory, identity, and relocation-journal checks run on every availability read. Only the Git root answer is reused: for 10 seconds by request scope checks, snapshots, and publication, and indefinitely by project-list summaries and the startup recovery gate, which never start a Git probe for an already-observed project. Concurrent readers share one probe. Explicit **Check again**, relocation rebinds, and task launch admission always probe again. Launch admission requires a definite answer: after one retry it fails with a retryable "Git is busy" error rather than "Folder unavailable". **Check again** reports "Folder check could not complete; the system may be busy. Try again." when its own probe was indeterminate, and adding a folder whose probe is indeterminate fails with a similar retry message instead of offering to initialize Git over a repository that could not be confirmed.

Published branch information follows the same rule. When any of its Git commands is indeterminate, the runtime reuses the project's last successfully loaded branch and HEAD information, or empty information if none has loaded yet, instead of publishing an empty branch list or reporting a missing repository. Indeterminate results are never cached as fresh, and Git is not re-run for that project for 5 seconds afterward. Routine cache invalidation (Git mutations, metadata polling) keeps the remembered information as that fallback; a definite "not a repository" answer discards it.

Startup validation runs before the runtime accepts connections, spends one Git probe per project through the same reuse cache, and never retries an indeterminate probe there: retrying would multiply pre-listen latency by the number of indeterminate projects. Its definite verdicts become the carry-forward evidence for later observations. A provisionally available project is hydrated and its recovery queued; each recovered launch still passes admission. A project that is unavailable, definitely or provisionally, is skipped without pruning saved state and records `project.startup_availability_failed` with its `reason`, or with `indeterminate: true` and no reason.

Git processes started by the runtime share a limit of eight. Foreground work (availability, request-path commands) is admitted before explicit user actions and background metadata, inspection, and fetches, and two slots are reserved for foreground work. Queue wait does not count toward a command's timeout, but a foreground command that waits more than 15 seconds fails as indeterminate. The timeout guard, shared with agent availability probes, checks after pending I/O, so a process that already exited during an event-loop stall keeps its own result. A process still running at its timeout receives SIGTERM (a tree kill on Windows), then SIGKILL after 2 seconds. Pipes a descendant keeps open after the process exits are released after 1 second, so the command settles with its own exit status, and a process that cannot be reaped is abandoned as timed out 3 seconds after its timeout. Either way its slot is released. The `git_processes` diagnostic snapshot shows active and queued counts.

Compare launch environments and retained `project.git_validation_failed` diagnostic events before treating the saved path as missing or relocating it. Those events retain bounded failure categories, process error/exit codes, and project identity without Git output, environment values, or repository paths. A `timed_out` or `queue_timed_out` failure kind, or a `command_failed` event with a resource-exhaustion error code, usually indicates runtime or system load rather than a missing repository.

Availability is re-checked often (request scope checks, snapshots, publication, background re-probes), so repeated identical probe failures for a project are coalesced: only the first occurrence of a failure signature (`failureKind`, `errorCode`, `exitCode`, `terminatedBySignal`) records `project.git_validation_failed`, and repeats are counted in a `suppressedCount` reported, alongside that same signature, when the streak closes (`project.git_validation_streak_ended`) or, for a long-running streak, at most once every ten minutes while it continues (`project.git_validation_streak_heartbeat`). The `project_git_validation` diagnostic snapshot provider reports currently active streaks, including their failure signature and time since last observed, for live investigation.

For macOS desktop-only failures under protected folders such as Desktop, also check the installed app with `codesign --verify --deep --strict /path/to/Quarterdeck.app` and correlate macOS permission events with the helper's Git process. An invalid app signature can cause macOS to deny access without presenting a usable permission request. See the [local desktop candidate build](./desktop-release.md#local-unsigned-candidate); shared settings cannot grant a native app filesystem permission.

## Validation boundaries

Focused filesystem and runtime tests cover missing-folder retention, name persistence, stale requests, duplicate destinations, project-wide exclusion, confirmed session shutdown, exact Git repair, stable worktree paths, journal interruption, and startup recovery. Frontend tests cover dialogs, unavailable read-only state, metadata ordering, dirty buffers, and same-ID path invalidation.

A deterministic Agent Lab scenario covers the browser/runtime boundary: external rename, unavailable reconnect and cold restart, Locate, display rename, disk rename, retained tasks and worktree contents, and explicit fake-agent restart. Use focused filesystem tests for interruption boundaries and exact worktree ownership. Real providers are unnecessary for this path-management contract.
